### 이탈 — S1의 "칩 3열" 모델이 실측과 두 번 어긋났다

1. 계획은 **모바일 카드 내부 가용폭 ~295px**을 전제로 `minmax(84px)`면 3열(`3×84+2×8=268 ≤ 295`)이라고 계산했다. 배포 후 실측 **237px**. 차액 ~58px의 정체는 **좌측 번호 컬럼**(`numeralStyle` width 38 + gap 12 = 50px) — 이게 제목 옆이 아니라 **카드 전체 높이에 걸쳐 자리 잡는 flex 열**이라 칩 그리드·본문 폭까지 같이 좁혔다. → `minmax(84px)` 적용 후에도 `cols=2` 그대로.
2. 번호를 제목 행에 인라인으로 접어 289px을 확보하니 3열이 성립했다(트랙 91px). **그런데 카드가 오히려 커졌다** — 000660 3번 카드 384→**431px**. 원인: **카드 높이의 실제 동인은 열 수가 아니라 칩 내부 텍스트 줄바꿈**. 트랙 91px에서 `현재가(20일 고점 대비)` label과 `$185.06 (-14.8%)` 값이 2줄로 접혀 **칩 45→94px**, 4칩은 3열에서도 2행이므로 그리드가 2행×94=196px이 됐다(2열 115px에서는 label 1줄, 2행×64=128px).

**최종 구현은 계획의 문자적 기준("칩 3열")을 의도적으로 이탈**해 칩 수에 맞춘 열 수로 갔다 — `repeat(${n <= 3 ? n : 2}, minmax(0, 1fr))`. ≤3칩=1행(3열), 4칩=2열 2행이지만 번호 컬럼을 접어 확보한 폭 덕에 트랙 115→140px로 넓어져 label·값이 전부 1줄. 결과 라이브 6장 **329·348·377 / 348·352·370** — baseline(344·384·391 / 362·366·384) 대비 전부 −14~−36px.

### 이탈 — 완료기준이 non-goal과 모순돼 검증 불가였다

계획은 S1 기준에 `카드 높이 300px 내외`를 적고 동시에 non-goal에 `3칩 1행(카드 250px대) 실증을 위한 재발행 없음`을 적었다. 현 발행물은 **전부 4칩**이라 어떤 렌더로도 2행이고, 300px는 3칩(=S2 반영된 다음 발행)에서만 성립한다. 즉 이번 UAT로 검증 가능한 최대치는 "baseline 대비 유의미한 감소"였고 그건 달성했다. **완료기준 자체가 자기 non-goal 때문에 구조적으로 통과 불가**였다는 점이 계획의 결함.

### 잔가지 2건

- 칩 그리드 주석을 JSX 표현식(`{cond && (`) 안에 `{/* */}`로 넣어 **oxc 파싱 실패** — 표현식 밖으로 이동. vitest가 즉시 포착.
- `match.test.js` 첫 문구 `'EMA200을 지지선으로'`가 **다른 용어(`지지선`)를 포함**해 단언 실패 — 코드가 아니라 테스트 문구 문제(`EMA200`은 정확히 매칭됨). 용어집 매처를 테스트할 땐 **문구에 다른 용어가 섞이지 않게** 중립 문장을 쓸 것.

## 학습

### 다음에 다르게 할 것

1. **렌더 파라미터(minmax·열 수·폭 임계값)를 정하는 슬라이스는 계획 단계에서 실측 1회를 근거로 삼을 것.** 가용폭을 "카드 폭 − 패딩"으로 추정하면 flex 형제(번호 컬럼 등)가 먹는 폭을 놓친다. 이번엔 계획이 295px로 추정한 실제 값이 237px이었고, 그 58px 오차가 S1 전체를 무효화해 배포 후 두 번 재작업했다. `getBoundingClientRect()` 프로브 한 번이면 계획 단계에서 잡혔다.
2. **"열/칸을 늘리면 압축된다"는 직관을 검증 없이 완료기준으로 쓰지 말 것.** 그리드 셀 높이의 동인은 열 수가 아니라 셀 내부 텍스트 줄바꿈이라, 열을 늘리면 트랙이 좁아져 오히려 커지는 역전 지점이 있다. 완료기준은 대리지표(열 수)가 아니라 **목표 자체(카드 높이)** 로 쓰고, 대리지표는 수단으로만 적을 것.
3. **fg-ask 단계에서 "이 완료기준이 이번 UAT 데이터로 검증 가능한가"를 non-goal과 대조할 것.** S1 기준(300px)과 non-goal(재발행 없음)이 서로 모순이라 통과 자체가 불가능했다. 완료기준을 적을 때 "무엇으로 이걸 재는가 / 그 데이터가 이번 범위에 있는가"를 한 줄로 붙이면 이 모순이 계획 단계에서 드러난다.
4. **UAT 프로브는 리터럴이 아니라 규칙을 단언할 것.** `cols === 3` 하드코딩은 구현이 정당하게 `≤3칩→n열 / 4칩→2열`로 바뀌자 거짓 실패를 냈다. `cols === (chips <= 3 ? chips : 2)` + `label 전부 1줄`처럼 **불변식**을 단언해야 정당한 변경에 살아남고 진짜 회귀만 잡는다.
5. **라이브 데이터가 없는 목표 상태는 단위테스트로 못박을 것.** 3칩 1행 규칙은 현 발행물이 전부 4칩이라 라이브로 못 봤다 — jsdom에서 인라인 `gridTemplateColumns`를 metrics 2/3/4개에 대해 단언해 규칙을 고정했다. "다음 발행부터 적용"인 변경은 이 패턴이 유일한 즉시 검증 수단.
