# 2026-10-07 — 심층 리포트 렌즈 후속 3/3: 10종목 루틴 재발행 + 라이브 확인 (일괄 승급)

## 계획 대비 실제
- 계획대로 된 것: 10종목 전부 새 계약으로 재발행 — 렌즈 3 `basis` 10/10(forward 4·yoy_quarter 6), KR 3종목 `input`, 민감도 정중앙 4/4가 ±10% 안(직전 CRCL +53.8%·005930 +19.7% → −5.5%·−0.1%). 회당 2종목 × 5회 병렬 발사로 ~5분에 끝났다.
- 어긋난 것:
  - **US 7종목 렌즈 8이 전부 na.** `cached_risk_free_pct`가 `_mc_load`의 `{data, fetched_at}` 봉투를 안 벗겨 task#368부터 항상 None이었다. 루틴이 US 금리를 늘 보내서 운영에서 한 번도 안 쓰였고, 테스트는 함수 자체를 mock해 못 잡았다. task#371의 「US 캐시 우선·원자료 생략」이 그 경로를 처음 실행시켰다. 계획 DoD는 「캐시 부재 시 input이면 기록」만 예고했다 — *값이 없음*과 *리더가 깨짐*은 다른 실패다.
  - 수리: 실제 봉투 모양 회귀 테스트(red 확인) → 1줄 수정 → 배포 → 컨테이너 실측 5.269 → US 7종목만 2회차 발사(상한 2 이내). 재계획 라운드 1/3 사용.
  - **m278 게이지 경계 라벨 겹침**(C6 pass→fail): 재발행 데이터의 금액 라벨(67px)이 트랙 178px의 37%라 고정 28% 스태거 문턱이 못 막았다. 렌더 후 rect 실측 판정으로 교체. 새 데이터 + 2/3에서 추가한 m278 뷰포트가 처음 만나 드러났다.

## 배움
- 다음엔 다르게:
  - 소스 우선순위를 바꾸는 계획은 **새 1순위 소스를 착수 시 컨테이너에서 1회 호출**해 값을 확인하는 슬라이스를 S1에 둔다. 이번엔 재발행 뒤에야 알았고, 그 사이 US 7종목이 ~5분간 회색으로 서빙됐다.
  - 고정 % 문턱으로 라벨 겹침을 막지 말고 실측할 것 — 라벨 폭은 단위 문자열 길이와 뷰포트에 따라 달라진다.
  - 재발행 대기 중엔 drive 마커를 잠시 내려 Stop 훅이 헛돌지 않게 했고, 진행은 프로세스 수 + DB 상태로 판정했다(0바이트 로그로 판정 안 함 — task#300). 잘 작동했다.
  - 새 배지 프로브는 재발행 **전** 실행에서 양성 표본 0을 「미검증」으로 보고했고, 후엔 11·10·4건 — 표본 카운터가 공허한 통과를 막았다.
