# 2026-08-22 — 10차 확정분 1/7: 인증·계약 4건(B72·B73·B74·B19) + 앱 전역 예외 핸들러

## 계획 vs 실제
- **계획대로 된 것**: pytest baseline 1758이 계획서 수치와 일치. 4결함 판정에서 `recorded-decision` 0건 → fork wall 없이 진행. 파일 소유권 3그룹 병렬(α `routers/auth.py` · β `main.py` · γ `backend/auth.py`)에서 형제 침범 0.
- **어긋난 것**:
  1. **S2가 계획의 2배로 커졌다 — 그리고 그것이 최대 산출이다.** 계획은 거절·`access_token` 부재 2경로만 지목했는데 적대 검토가 토큰교환 *이후* **3경로**를 실제로 재현했다: `/user/emails`가 에러 dict면 `for e in emails`가 **키 문자열을 순회**해 `AttributeError` · `/user`가 에러 dict면 `profile["id"]`가 `KeyError` · 모든 이메일이 unverified이고 프로필 이메일이 private이면 `email=None`이 `users.email NOT NULL` 위반. **즉 B72가 없애려던 raw 500이 같은 함수 안에 3개 더 있었다.**
  2. **B74의 정본이 「이미 기록된 결정」이었다.** 계획은 「5가 맞는지 6이 맞는지는 코드가 답한다」로 열어 뒀는데, S1이 `ADR-0025`가 경계로 **「`ALL_MENUS` 5키 불변」을 명시**하고 done 계획 4건의 비목표가 같은 문장을 반복함을 찾았다. 5로 통일하는 것은 결정을 *되돌리는* 게 아니라 **구현하는** 것이었고, 6항목을 리터럴로 못박은 `test_auth_me.py`가 그 결정과 어긋난 잔존물이었다(forge 도입 이전 커밋, 대응 계획서 부재 → `incidental-assertion`).
  3. **감시 소스가 4개가 아니라 5개였다.** 4소스 대조 테스트를 짜자마자 검토가 이빨 검사로 구멍을 실증했다 — 네 곳에서 `settings`를 **동시에** 지우면 넷이 서로 같으니 **9 passed로 통과**한다. `settings`의 실제 소비처는 `navSections.js`의 `perm:`이 아니라 `Masthead.jsx`·`MobileTopActions.jsx`의 `menuPermissions.includes('settings')` **리터럴**이었다.
  4. **처방을 검토자 제안과 의도적으로 다르게 골랐다.** 검토자는 `status_code` 일괄 검사를 제안했으나 그러면 `/user/emails`만 403이고 프로필 이메일이 공개된 사용자의 **성공 가능한 로그인을 막는다**. 판정을 **본문 형태**로 하고, 느슨해진 대가를 되받는 **대조군 축**을 쌍으로 뒀다.
  5. 검토자가 놓친 문서 결함 2건을 수복 단계가 같은 클래스로 함께 고쳤다(`INTEGRATIONS.md`의 거짓 서술, `API_SPEC.md` Admin 절 예시의 `oauth_provider` **선재 누락**).
