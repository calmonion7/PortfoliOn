## 학습

- **다음에 다르게 할 것**

  1. **레이스 가드를 한 함수에 넣을 때 형제 비동기 경로를 전수 세라.** → **CLAUDE.md 가토로 승급**(아래 문서 갱신).
     원인은 *이름*이었다 — 계획이 B27을 "`fetchPage`의 결함"으로 이름 지어 두었고 그 이름이 시야를 함수 하나로 좁혔다.

  2. **계획의 슬라이스 *서술*과 계획의 *완료기준*이 다른 수를 말하면, 옳은 쪽은 완료기준이다 — 착수 시 완료기준 명령을
     직접 돌려 세라.** 계획 S2는 이전 대상을 3곳으로 열거했지만 DoD는 `grep -c "/api/watchlist" → 0건`이었고,
     실제로는 4곳이었다(모달 CTA). 서술을 믿고 3곳만 고쳤으면 **완료기준이 red인 채로 "슬라이스 완료"가 됐을 것**이다.
     이건 가토 ⑥ 가족(계획을 믿지 말고 착수 시 직접 grep — task#230·231·232, #237, #253)의 **4번째 관측**인데,
     앞의 셋이 "계획이 *빠뜨렸다*"였다면 이번은 "계획이 *잘못 셌다*"이다. 사용자 판단으로 이번엔 회고에만 남긴다.
     같은 자리에서 또 밟으면 그때 승급할 것. **실천은 한 줄이다 — 착수 시 각 슬라이스의 완료기준 명령을 그대로 실행해
     baseline 수를 찍고, 그 수가 슬라이스 서술의 대상 수와 일치하는지 본다.**

  3. **프로브 FAIL을 볼 때 세 번째 갈래를 넣어라 — 「구현 결함인가 / 프로브 결함인가」 앞에 「대상이 최신인가」.**
     프로브 작성 에이전트가 작성 직후 시험 실행을 했고 그 결과(`got="☆" want="보유중"` 8 FAIL)가 `result.json`으로
     남았는데, 그건 **빌드 전이라 라이브가 옛 번들을 서빙 중**이어서였다. 나중에 그 파일을 읽은 적대적 리뷰 렌즈가
     **BLOCKING 구현 결함으로 오귀속**했고, 반영 에이전트가 `HEAD == origin/main`(둘 다 `e9b162c`) 실측으로 정정했다.
     가토 ⑧ⓘ가 "대상이 *틀린* 경우"라면 이건 "대상이 *낡은* 경우"다. 이 프로젝트는 프론트 검증이 배포에 의존하므로
     (빌드=즉시 라이브) 구조적으로 재발한다. **실천 2가지**: ⓐ 프로브 출력에 **서빙 번들 해시를 찍고**(uat273은 실제로
     `[pc] 서빙 번들: index-BH-VlddN.js`를 출력한다) 로컬 빌드 해시와 대조한다 ⓑ **빌드 전 잠정 실행 산출물은 남기지
     말거나 파일명·본문에 `PRE-BUILD` 라벨을 박는다** — 디스크에 남은 결과는 맥락 없이 읽힌다.
     사용자 판단으로 이번엔 회고에만 남긴다.

  4. **워크플로우 파형에서 논리적 독립 ≠ 파일 독립.** 계획은 S2(이전)와 S4(레이스 가드)를 "독립"으로 표시했지만 둘 다
     `Ranking.jsx`다. 병렬 에이전트에 나눠 주면 같은 파일을 동시 편집해 충돌한다 → 한 에이전트가 순차 수행하도록 묶었다.
     계획의 `depends:` 표기는 *논리* 의존성이니, 워크플로우를 짤 때 **슬라이스별 대상 파일 집합의 교집합**을 따로 볼 것.

  5. **배포성 동작(commit/push/build)은 서브에이전트에 주지 말 것.** 워크플로우 프롬프트에서 명시 금지하고 메인 세션이
     `commit+push → build → 프로브` 순서로 처리했다. 서브에이전트가 배포하면 순서를 통제할 수 없고, 실제로 이탈 4가
     그 예방의 값을 보여줬다(프로브가 옛 번들을 쟀고, 그게 *메인 세션이 통제하는 순서* 밖이었으면 오진으로 굳었을 것이다).
