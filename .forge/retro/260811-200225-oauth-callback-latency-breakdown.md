# 2026-08-11 — 콜백 `0→req` 2383ms의 정체를 가른다 (task#289)

fg-loop 드라이브가 자동 스킵한 회고의 **유예 승급**(batch promotion, 2026-08-11 일괄). 실행일 2026-08-10.

**결론: 조건부 처방이 미발동 — 코드 변경 0이 정상 종료였다.** 핸들러 순비용 202.6ms(하한 500ms 미달) · 단일 최대 처방가능 성분 146.4ms(하한 300ms 미달), 두 조건 AND 둘 다 미달.

## 계획 vs 실제

**계획대로 된 것**

- 계측 2종 신설(라이브 지연 프로브 + in-container 마이크로벤치), 판정 하한 대조, **미발동 시 처방 안 함**을 그대로 이행.
- 프로브 34/34 ALL PASS ×2런, 커버리지 축별 동일, DB count 3테이블 before/after 불변.
- 문서 4종 전부 "변경 없음"을 **근거와 함께** 기록(확인 없이 "없음"이라 쓰지 않음).

**핵심 수치** — 핸들러 순비용 202.6ms 중 구글 토큰 교환이 **99.9%**(그중 커넥션 재사용으로 제거 가능한 TLS 핸드셰이크분 146.4ms = 72.3%), DB 3연산 1.5ms(0.7%), 커밋 최대 7회 0.8ms(0.4%). 체감 전체(6192/6807ms) 대비 우리 핸들러 몫은 **3.0~3.3%**이고 최선의 처방으로 제거 가능한 최대치는 **2.1~2.4%**다. 가토 ⑧ⓙ가 경고한 "2.7% 구간을 최적화할 뻔한 함정"의 **세 번째 사례**이며 이번에는 **처방 전에 계측해서** 피했다.

**일탈**

1. **⭐ S2-2가 계획대로면 프로덕션에 실제로 썼다.** 계획은 "서비스 함수 3개를 단일 트랜잭션에서 실행 후 **ROLLBACK**"을 지시했으나 `services/db.py::get_connection`은 정상 종료 시 `conn.commit()`하고 `execute()`/`query()`도 각자 커밋한다 — **롤백이 원리적으로 불가능**하다. 착수 전 확인에서 잡아 동등 SQL 직접 실행으로 대체했다. 그대로 실행했으면 **가짜 user·기본권한·refresh_token이 커밋**됐다.
2. **계획·초기 체크의 "302"가 틀린 전제였다** — `RedirectResponse` 기본은 **307**이다(라이브 1콜로 확인). 302로 단언했으면 정상 구현에 거짓 FAIL이 났다.
3. **축을 2개 → 3개로 보강했다** — 계획의 ⓐ(정적)만으로 빼면 ⓒ에 nginx→backend 프록시 홉 + FastAPI 오버헤드가 섞여 **핸들러를 과대평가**한다. 같은 라우터의 공개·무DB·무외부호출 엔드포인트를 ⓐ′로 넣어 구글 교환을 직접 격리했다. 결과적으로 ⓒ₁(200ms)과 S2 콜드 실측(197.7ms)이 **독립 경로에서 ~1% 이내로 일치**해 상호 검증이 됐다(계획에 없던 이득).
4. **적대적 리뷰가 프로브 결함 2건을 잡아 즉시 수정**(단언 27→34) — ⓐ축에 상태코드 단언이 하나도 없어 CF 봇완화/WAF 챌린지가 끼어도 전부 PASS하며 ⓒ₂만 오염되는 문제, 하드스톱 3경로가 무쓰기 게이트를 비활성화하는 문제(`hardStop()` 통합 + 결함 주입으로 이빨 실증). auth 표면 적대적 리뷰가 **5연속**으로 값을 했다.
5. **HIGH 1건을 보강 측정으로 닫았다** — "DB 1.4ms는 커밋 비용을 구조적으로 0으로 측정한 하한값"이라는 지적에 커밋 1회 0.12ms를 실측(n=20)해 7회라도 0.8ms임을 확인하고, run.md 서술을 "무시 가능"→"커밋 제외 하한값 + 별도 실측"으로 정정했다.
6. **성공/실패 경로 비대칭을 논증으로 닫았다** — 2번째 게이트 조건의 유일한 후보인 커넥션 재사용 이득은 TLS 핸드셰이크 회피분이라 **구글의 서버측 처리시간과 무관하게 119~146ms로 고정**된다. 구글 성공 경로가 아무리 느려도 그 증가분은 *우리가 제거할 수 없는* 성분이므로 2번째 조건은 어떤 가정에서도 충족될 수 없다.
7. **S5.2(줄번호 drift)가 S4 의존이라 사실상 N/A** — task#288 회고의 "슬라이스 의존성은 항목 단위로 확인하라"가 또 맞았다.

## 배운 것

**다음에 다르게 할 것**

1. **「무쓰기」를 표방하는 계측이라도 그 무쓰기를 실제로 만드는 메커니즘을 코드로 확인할 것.** `ROLLBACK`·`dry-run`·`--check` 같은 단어는 그 자체로 보증이 아니다. 이 저장소에서 프로덕션 DB에 닿는 계측의 무쓰기는 ⓐ 읽기 전용 SQL이거나 ⓑ 전제조건 미충족으로 핸들러가 조기 반환(403/404/400/422)이어야 성립하고, 세 번째 방법은 없다. → **CLAUDE.md ⑧ⓢ에 선행 사례로 승급.**
2. 승급 안 함 — **`RedirectResponse` 기본은 302가 아니라 307**이다. 프로브가 상태코드를 리터럴로 단언할 때 값을 추정하지 말고 1콜 찍어 확인할 것(⑧ⓘ의 작은 사례).
3. 승급 안 함 — **감산 측정에서는 "빼는 쪽"에 같은 홉을 태운 축을 하나 더 만들어라.** 정적 자원만으로 빼면 프록시 홉·프레임워크 오버헤드가 목표 성분에 섞인다. 같은 라우터의 공개·무DB 엔드포인트가 그 자리에 딱 맞는다(⑧ⓙ의 실천 사례).
4. 승급 안 함 — **미확정으로 남긴 것을 이름으로 적는 것**이 판정을 견고하게 했다(구글 성공 경로 교환시간 · 실제 쓰기 커밋의 WAL fsync · 데스크톱 관측점의 절대값). 특히 세 번째는 "프로브가 준 것은 구조이지 크기가 아니다"(task#288)를 지킨 것이다.

## 후속 큐

- 커넥션 재사용(`AsyncClient` 재사용)으로 146ms를 줄일 수는 있으나 **체감 전체의 2.1~2.4%**라 하한 미달로 미발동. 다른 이유(안정성·코드 정리)로 하게 되면 그때 근거를 새로 세울 것 — 이 회고의 수치를 "성능 근거"로 재활용하지 말 것.
