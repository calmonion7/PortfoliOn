# 2026-07-31 — 구글/깃허브 로그인 후 뒤로가기 IdP 차단(히스토리 되감기) (task#252, 일괄 승급 회고)

`fg-next all` 드라이브가 회고를 자동 스킵해 봉인했고, 이 파일은 그 지연 승급이다. 원료: `done/2026-07-31-oauth-back-history-rewind/run.md`.

## 계획 ↔ 실제

- **계획대로**: `startOAuth(provider)` 단일화 + `location.replace`→`href`(의도된 push) + 랜딩에서 `returnFromOAuth()`가 delta를 계산해 `history.go(-delta)`. 전체이동 4곳의 최종 형태를 grep으로 확인(401·폼로그인=replace / OAuth=push / 폴백=replace). vitest 254 green(신규 8건), 라이브 프로브 10 PASS.
- **mutation으로 이빨 확인**: 되감기 조건을 `if (false && …)`로 깨뜨려 `delta 3 → go(-3)` 단언이 실제로 실패함을 보고 원복. 통과만 보고 넘기지 않았다.
- **거짓이 된 서술 정정**: `back-to-login-guard.test.jsx`의 헤더 주석·describe가 "전체이동 진입점은 push가 아니라 replace"였는데 이제 진입점마다 다르다. 구글 버튼을 단언하는 테스트가 없어 **깨지지 않으면서 거짓이 되는** 자리였다(task#249 가토의 적용 사례).

- **Divergences (8건 중 재사용 가치가 있는 것)**:
  1. **D1 — 되감기 로직을 인라인이 아니라 `utils/oauthHistory.js` 모듈로 뺐다.** 이유가 둘인데 두 번째가 중요하다: 이 코드베이스는 **테스트에서 App을 import하지 않는 관례**라(#245 회고 기록), 인라인이면 4분기를 실제 코드로 단언할 수 없다. **테스트 가능성이 코드 배치를 결정한다** — #245가 가드를 훅으로 뺀 것과 같은 이유.
  2. **D2 — Playwright `route.fulfill`의 302로는 가짜 IdP에 도달할 수 없다.** 302를 반환하면 **그 리다이렉트가 만든 요청이 라우팅을 타지 않아** DNS 실패(`chrome-error://chromewebdata/`)로 끝난다. 대조 실험으로 확정했다 — 직접 `goto`와 스크립트 `location.replace`는 정상 인터셉트된다. 해법: 시작 엔드포인트를 `location.replace`로 떠나는 HTML로(replace라 엔트리를 늘리지 않아 302와 히스토리 의미가 동일). "그럴듯한 결론(도구 한계)"으로 접지 않고 대조로 갈랐다.
  3. **D3 — 계측기가 엉뚱한 오리진의 저장소를 읽었다.** 1차 실행이 `history.go 0건`을 냈다. 로그를 `goBack()` **뒤에** 읽어서 착지한 IdP/센티넬 오리진의 sessionStorage를 읽고 있었다(우리 오리진의 go 호출은 거기 없다). **목표 단언 6건은 모두 PASS였으므로 그대로 두면 "되감기가 안 돌았는데 왜 통과했나"를 설명 못 하는 커버리지가 남는다.** 착지 직후(우리 오리진)에서 읽도록 옮겨 `go 1건(n=-3)`·`랜딩 len 6`·`base 3`으로 정합. **가토 ⑧ⓘ의 계측기 자기적용판** — 크로스오리진 프로브에서 "어느 오리진의 저장소를 읽고 있는가"는 판정 축과 독립이라 틀려도 통과한다.
  4. **D5 — 대조군 arm을 앱의 폴백 경로로 만들었다.** 랜딩 문서 시작 시 기준값을 지우면 `returnFromOAuth`가 `replace('/')`를 타므로 되감기 도입 전 동작이 재현된다. 결과: 대조군 back → IdP, 되감기 arm back → 센티넬. **판별력 실증**(⑧ⓔ) — 이게 없으면 목표 PASS는 "프로브가 원래 IdP를 못 보는 것"과 구별되지 않는다. 별도 하니스를 짓지 않고 **앱 자신의 폴백을 대조군으로 재사용**한 게 값싼 해법이었다.
  5. **D6 — `base`가 예상 2가 아니라 3이었다**(새 페이지의 `about:blank` 엔트리). 산수가 상대값(delta)이라 무영향. 단언을 절대값(`delta === 3`)이 아니라 **결과**(back 착지가 센티넬)로 잡아둔 것이 옳았음이 확인됐다.
  6. **D4 — 실토큰을 쓴 이유**: 가짜 토큰이면 실 API가 401 → `api.js` 인터셉터가 `replace('/')` → 되감기와 무관하게 로그인 화면으로 튀어 프로브가 엉뚱한 이유로 깨진다.
  7. **D7 — 넣지 않은 가드**: `markOAuthStart`의 storage throw. 스토리지가 던지는 환경이면 `localStorage` 토큰 인증 자체가 성립하지 않아 앱을 못 쓴다 → 사실상 불가능한 시나리오(조직지침 "impossible scenarios 에러핸들링 금지").
  8. **D8 — 모바일 별도 프로브 생략 근거**: 모바일·PC 버튼이 **같은 핸들러 참조**를 쓰므로 되감기 경로가 뷰포트 독립임을 grep으로 확인.

## 배운 것

- **다음엔 다르게**:
  1. **크로스오리진 프로브는 "지금 어느 오리진에서 읽는가"를 명시적으로 관리할 것.** `page.evaluate`의 저장소 접근은 현재 문서 오리진에 묶이므로, 내비게이션 전후로 읽는 시점이 곧 대상 오리진을 바꾼다. 목표 단언이 전부 PASS여도 커버리지가 0이면 그건 계측 실패다.
  2. **`route.fulfill`로 302를 반환하지 말 것** — 그 리다이렉트의 후속 요청은 인터셉트되지 않는다. 스크립트 `location.replace`로 대체하면 히스토리 의미를 보존하면서 라우팅을 탄다.
  3. **대조군은 새로 짓기 전에 앱의 폴백 경로를 먼저 보라.** 기준값 하나를 지워 "도입 전 동작"을 재현할 수 있으면 그게 가장 값싼 판별력 실증이다.
  4. **테스트 가능성을 코드 배치의 근거로 쓸 것.** "App을 import하지 않는다"는 이 코드베이스의 관례가 곧 로직을 훅·유틸로 빼야 하는 이유다(#245와 2번째).
- **남는 한계(의도적)**: ① **실 구글 플로우는 우리가 검증 불가**(테스트 계정에 구글 계정 없음) — 검증된 것은 "가짜 IdP가 만든 크로스오리진 엔트리를 되감기가 정확히 뛰어넘는다"이고 남은 미지수는 구글이 만드는 엔트리 *수*뿐이었다(delta가 그 수를 측정하므로 값에 의존하지 않는다). **이 게이트는 닫혔다** — 2026-07-31 사용자 실기기 확인(안드로이드 Chrome에서 구글 로그인 → 뒤로가기 정상, STATUS `verified:`에 기록). delta 방식이 실제 IdP 엔트리 수에 무관하게 동작함이 실증됐다. ② **bfcache 착지 변형 미측정**(task#246, 3엔진 대조군으로 Playwright 불가 확정) — 실측된 것은 되감기 후 문서 재실행 경로이고, 라이브 `/`가 `no-store`라 이게 기본 경로다.
- **후속(당시 미수정 → task#253이 해소)**: `?error=`·소진 코드 분기가 유효 토큰을 무시하고 세션을 죽이는 결함.
