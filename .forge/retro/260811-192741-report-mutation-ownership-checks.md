# 2026-08-11 — 리포트 변경 엔드포인트 2건(B50)에 「소유권 OR admin」 게이트

fg-loop 드라이브가 회고를 자동 스킵한 채 봉인한 태스크의 **유예 회고**(batch promotion). 1차 실행이 `verified: failed` → **fork wall** → 사용자 결정 → **in-place 수리 r1**로 해소된 이례적 경로였다.

## 계획 vs 실제

**계획대로 된 것**

- 착수 시 계획 전제 재확인이 대부분 일치했다(결함 2건 유지 · test 계정 role=user·26종목 · 스냅샷 0인 티커 정확히 2건 · `test_consensus_router.py` 3호출부와 stale 주석 · `불필요` 1건 · 줄번호 포인터 0). 계획이 스스로 "작성 시점 스냅샷이니 다시 세라"고 지시해 둔 것이 값을 했다.
- red-first가 정직하게 보고됐다 — 통과 케이스(ⓑⓒ)가 구현 전에도 PASS임을 꾸미지 않고 그대로 적었다.
- 의존성 교체 후 **선제 override 없이 스위트를 먼저 돌려 실제로 깨지는 것만** 고쳤다(예측 그대로 3건).
- 서브에이전트 금지(git 되돌리기·commit/push·프론트 빌드) **0위반** — task#288·#279 처방의 3번째 양성 사례.
- 줄번호 drift: 보정 0 · 표본 0 · 빈 표본 3 · 선재 0(`ed98f72` 이후 앵커 규율 유지 확인).

**일탈 (발산 높음)**

1. **⭐ 계획 근거 3의 「`backfill_consensus` 프론트 소비처 없음(grep 0)」이 거짓이었다.** `ConsensusChart.jsx:54`가 호출하고 그 「백필」 버튼에 role 게이팅이 전무하다 → `require_admin` 배포 시 전 비admin이 **자기 보유 종목에서도** 403(기능 회귀). 계획은 형제 `refresh_analyst`에 대해 정확히 반대 논리를 적어 두었으므로, **결론이 갈린 지점의 사실 주장 하나가 틀렸던 것**이다. 왜 계획의 grep이 0이었는지는 **미확정으로 남긴다**(추정 귀속 금지).
2. **근거 4·5의 「비admin은 정상 UI로 남의 종목 상세에 못 간다」도 거짓.** `Ranking.jsx::onRowClick` → 모달 → `ReportDetailTabs`가 지원되는 내비게이션이다. S1 게이트 자체는 옳고, 잘못된 것은 버튼을 그대로 둔 채 배포한다는 판단이었다.
3. **근거 11의 owner-pass 메커니즘이 프로덕션 공유 테이블에 쓴다.** `POST /api/watchlist`의 신규 티커 분기가 background 리포트 자동생성을 발동 → 계획 자신의 「어긋나면 즉시 중단」과 모순(계획 내부 모순).
4. **계획이 "ADR 3요건 미충족"으로 판단한 것이 fork로 뒤집혔다** — 처방이 「기존 관례의 적용」에서 「관례로부터의 의도적 이탈」로 바뀌었다.

**수리 r1에서 한 것**: 두 엔드포인트를 공통 헬퍼 `_require_owner_or_admin`으로 통일 · 테스트를 엔드포인트당 4케이스(총 8)로 재작성 · 이빨 2주입 대칭 성립 · 문서 정정(거짓 전제 → **반례 경고**로 전환) · 프로브 재설계 · 배포 `71ddca4` → 라이브 ALL PASS 34/34 ×2런 · 쓰기 0.

## 배운 것

**다음에 다르게 할 것**

1. **계획이 「없음」·「0건」·「grep 0」 같은 *부재*를 근거로 쓰면 착수 시 그 grep을 직접 한 번 돌릴 것.** 부재 주장은 존재 주장보다 검증이 싸고 틀리기 쉽다. 탐지 휴리스틱: **한 계획 안에서 같은 사실관계에 다른 결론이 나오면 전제를 의심한다.** → CLAUDE.md 승급.
2. **프로브 대상을 고를 때 「이 프로브가 FAIL하면 무엇이 남는가」를 물을 것.** 스냅샷 보유 티커를 쓰면 가드 부재 시 프로덕션을 오염시키고, 스냅샷 0 티커를 쓰면 판별력은 같은데 쓰기가 0이다. 그리고 **쓰기 위험이 없어야 배포 전 라이브 red-first를 돌릴 수 있다** — 안전 규칙이자 red-first의 전제조건. → CLAUDE.md 승급.
3. **중복될 가드를 헬퍼로 뽑으면 이빨 검증이 대칭이 된다.**(승급 안 함 — 적용 범위가 좁다) 1차의 주입2는 한 테스트가 assert가 아니라 conftest 실DB 가드로 실패해 "FAIL은 맞지만 메커니즘이 다르다"는 얼룩을 남겼는데, 단일 헬퍼에 주입하니 11건이 전부 순수 assert로 갈렸다. 일반화하면 **결함 주입의 대상이 하나면 판정도 하나의 축으로 정렬된다.**
4. **회고가 지목한 체크는 다음 사이클을 기다리지 말고 그 사이클의 체크 집합에 넣을 것.**(승급 안 함 — 가토 ⑥에 양성사례 2건 존재, 3번째) 1차 회고가 "다음 auth 게이팅 체크 집합에는 프론트 소비처 대조를 넣어야 한다"고 적었고, 그것을 같은 사이클의 **C10으로 즉시 승급**했다. 결과: 소비처 2건·둘 다 role 게이팅 0이 즉시 나왔다 — **적대적 리뷰가 아니라 체크가 잡을 수 있는 결함이었다.**

**fg-loop 운영에 대한 관찰**(승급 안 함)

- **fork wall이 제 역할을 했다.** 「올바른 처방이 계획의 그릴링 결정을 뒤집는다」는 정확히 사람의 몫이고, 자동 fix-forward로 넘겼으면 계획을 존중해 회귀를 배포했거나 스코프를 임의로 넓혔을 것이다.
- **사람의 fork 결정이 정지조건 체크 자체를 다시 쓰게 만들 수 있다.** 구 C3는 기각된 설계(`require_admin`)를 인코딩하고 있어서 그대로 두면 "체크는 통과하는데 목표는 무너지는" 상태가 고착된다. 체크 재작성은 사람이 그 계약을 고른 직후에만 정당하다.
- **드라이브에서 적대적 리뷰가 안 도는 것이 이 태스크의 최대 잔여 리스크였다.** 1차의 HIGH 2건을 잡은 것이 정확히 그 리뷰였는데, r1분은 fg-loop 계약상 돌지 않아 메인 세션 코드 직독으로 갈음했다. auth 표면에서 리뷰가 값을 한 것이 이제 7연속이다.
