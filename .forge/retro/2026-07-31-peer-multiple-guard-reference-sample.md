# 2026-07-31 — 피어 멀티플 가드 판정축을 "peer 전체 + 자사" 기준 표본으로 교정 (task#249)

> 봉인 시 `fg-next all`이 자동 스킵한 회고를 사용자 요청으로 뒤늦게 승급(2026-07-31, Batch promotion).

## 계획 vs 실제

- **계획대로 된 것**:
  - 판정축 교체(leave-one-out → 값 있는 peer 전체 + 자사)와 생략 임계 이동(나머지 `<2` → 표본 `<3`)이 설계 그대로 들어갔다. 밴드 `[1/5, 5]`·결측 처리·`rd_intensity` 제외·`median <= 0` 생략은 무변경.
  - 계획의 "알려진 함정"이 **거의 전부 정확했다**. 특히 "기존 테스트 3건이 의도적으로 깨진다(전수 확인 완료)"가 정확히 그 3건이었고 **그 밖의 파손 0**이었다 — 착수 전 전수 확인이 실제로 값을 했다.
  - "표본은 지표마다 한 번만 계산되므로 #248의 `drops` 스냅샷 장치가 구조적으로 불필요해진다"는 예측이 맞았다. 판정 루프가 2단(판정→일괄적용)에서 1단으로 줄어 **코드가 짧아지는 방향**이었다.
  - TDD로 red를 **값으로** 관측한 뒤 구현했다(7건). 실패 로그가 구 판정축의 메커니즘을 그대로 증언했다: `(P0 pbr: value=3.48 median=46.955 ratio=0.07)`.
  - 배선 e2e를 통과 확인만 하지 않고 **가드 호출을 임시 제거해 뮤테이션 검증**했다 → `assert 100.0 is None`.
  - 전체 스위트 1458 passed · 스위트 후 `git status` 부수효과 0 · 라이브 프로브 12단언 ALL PASS.

- **이탈**:
  1. **워크플로우를 쓰지 않고 직접 실행했다.** 슬라이스 3개가 직렬 의존(S2·S3이 S1에 depends)이고 백엔드 함수 1개 + 테스트 + 프로브 + 문서 1줄 규모라, fg-run 제약("단일 에이전트로 충분하면 워크플로우 생략")과 eco 잣대에 해당했다. 팬아웃 이득이 없었다.
  2. **라이브 칩 값이 −64.9%로 나왔다(계획 DoD는 "약 −57%").** 판정 실패가 아니라 **판별 변동**이다 — 자사 PBR이 그릴링 시점 2.88에서 실행 시점 2.33으로 내려갔고, 가드 후 peer 중앙값 6.642는 계획의 6.64와 일치한다(`2.88/6.642−1 = −56.6%` vs `2.33/6.642−1 = −64.9%` — 산식 동일, 입력만 이동).
  3. **`psr` 칩도 −50.7% → −61.2%로 움직였다.** 계획에 명시되지 않은 부수 효과지만 정상이다(TSM `psr` 0.4711이 결측되며 peer 중앙값이 7.1 → 9.02로 올라간 결과 — 가드 전 −50.7%가 오값에 오염된 수치였다).
  4. **`even_sample_median` 테스트가 예상보다 한 축 더 깨졌다.** 계획은 "표본이 홀수가 됨"만 예고했는데 실제 red는 새로 넣은 `D=30.0` 행이 **구 판정축에서 결측**되는 형태(`assert [2.0, 4.0, 10.0, None, 200.0] == [..., 30.0, ...]`)였다. 재설계가 의도대로 동작한 증거이고 수정은 불필요.
  5. **통과하는 테스트의 stale 주석을 1건 더 발견했다** — 계획이 지목한 `never_judges_self_row` 외에 `excludes_none_from_target_and_sample`의 `median(10,11,12)=11 → 90.9×`가 새 판정축에서 `median(10,11,12,1000)=11.5 → 87.0×`로 바뀌어 거짓이 됐다. 코드 변경 없이 통과하므로 스위트가 잡지 못했다.
  6. **peer 원값이 그릴링 실측과 미세하게 달라졌다** — MU pbr 9.80 → 9.804, 자사 2.88 → 2.33(TSM 84.11·000660 3.48은 동일). 표본 median이 사실상 같아 판정 결과는 계획 예측과 완전히 일치.

## 배운 것

- **다음에 다르게 할 것**:
  1. **판정축·계산식을 바꾸면 "깨지는 테스트"와 별개로 "그 축을 *서술하는* 테스트"를 전수 확인할 것.** 이탈 5번이 그 사례다. `git grep`으로 축의 옛 표현(여기선 `나머지 peer`·`median(` 산식 주석)을 훑어야 잡힌다 — 스위트는 주석·docstring에 원리적으로 블라인드하고, 초록으로 통과하면서 **반대 사실을 증언하는 테스트**가 남는다. 기존 규칙 "선제 수정 금지, 스위트를 먼저 돌려 실제로 깨지는 것만 고친다"(#230·231·232)의 **보완항**이다 — 그 규칙은 *깨지는 것*을 다루고 이건 *안 깨지는 것*을 다룬다. **CLAUDE.md 승급.**
  2. **라이브 프로브는 완료기준이 지목한 지표만 찍지 말고 전 지표를 before/after로 출력할 것.** 이탈 3번이 그 사례다. 목표는 `pbr` 칩이었는데 4지표 칩을 모두 찍은 덕에 `psr` 칩 이동이 드러났다 — `pbr`만 찍었으면 조용히 지나갔고, 사용자가 "psr 칩이 왜 바뀌었냐"고 물었을 때 설명할 근거가 없었을 것이다. 프로브 신뢰성 ⑧ 계열의 다음 항. **CLAUDE.md 승급.**
  3. **회고 제약이 계획의 *지시*로 옮겨지면 실제로 오판을 막는다 — 이번엔 성공했다.** DoD의 "약 −57%"를 그대로 게이트로 걸었다면 정상 구현이 FAIL 났을 텐데, 같은 계획서가 "판마다 값이 달라지므로 **리터럴이 아니라 배수 불변식으로 단언할 것**"을 명시해 둔 덕에 프로브를 "칩이 표시되는가(유효 peer ≥ 2)"로 걸고 값은 출력만 했다. #237 D2·#247이 "회고 제약이 계획으로 이월되지 않는다"고 **두 번 관측한 계열의 첫 성공 관측**이다. 실천의 요점: 제약을 배경지식이 아니라 **완료기준의 문구 자체**에 심을 것("−57%인지 확인" ❌ → "칩이 표시되고 값을 출력" ✅).
  4. **용어를 먼저 쪼개면 실행이 밋밋해진다.** 이번 결함의 뿌리는 `판정 대상`과 `기준 표본`을 한 문장에 섞어 자사를 양쪽에서 뺀 것이었고, 그릴링에서 그 둘을 신설·분리한 뒤에는 실행 중 흔들린 개념이 **하나도 없었다**. 용어 분리가 그릴링의 산출물로서 실제 코드 결함을 예방한 사례.
  5. **워크플로우 생략 판단 기준** — 슬라이스가 전부 직렬 의존이고 파일 4개 이하 규모면 직접 실행이 맞다. 팬아웃은 독립 슬라이스가 3개 이상일 때 값을 한다.
