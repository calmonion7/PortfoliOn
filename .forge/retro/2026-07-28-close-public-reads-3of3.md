## 계획 대비 실제

- **계획대로**: S1(401 단언 11건 + `X-API-Key` 200 positive + 잘못된 키 401, red 확인) → S2(`report.py` 9 + `stocks.py` 2, **`{date_str}`만 `get_current_user_or_api_key`**) → S4 전 항목. 백엔드 1372 passed. **계획의 11개 목록이 정확히 일치**(2/3과 달리 오류 0 — 착수 전 배선 열거를 했기 때문).
- **Cowork 분기 재확인**: Cowork가 문서화한 read는 4개(`/api/stocks`·`/api/report/list`·`{date_str}`·`backlog/pending`). 대상 11개 중 Cowork read는 `{date_str}` **하나**이고 `{ticker}/backlog`는 Cowork의 **PUT**(쓰기) 대상이라 read는 `get_current_user`로 충분 — 계획 예측 적중.
- **괴리 ①(최대 가치) — 감사 스크립트를 계획 밖 산출물로 신설했다.** 계획 S4는 "AST 감사 재실행"을 완료기준으로만 적었고 재현 가능한 도구가 없었다(1/3의 감사는 일회성 조사). → `scripts/audit_unauth_endpoints.py` 신설: **AST 파싱이 아니라 라이브 `app`의 라우트를 돌며 각 엔드포인트 함수 default가 4개 인증 의존성 중 하나인지 검사**(데코레이터·주입 실수까지 잡힘). 착수 시점엔 진짜 대상 목록 확정에 썼고(계획 11개 일치 확인 + `us-supply`·`us-insider`가 이미 `_or_api_key`임을 확인해 헛작업 방지), 종료 시점엔 완료 게이트로 썼다.
- **괴리 ② — S3가 또 no-op.** 계획은 "14파일, 3부 중 가장 무겁다"로 예상했으나 전체 스위트가 곧바로 green. 대상 경로를 호출하는 8파일이 **이미** 필요한 override를 갖고 있었다(형제 read가 먼저 인증돼 있던 덕). 계획이 경고한 **"`_or_api_key`는 별개 키" 함정도 선재 대응**돼 있었다(`test_report_router.py`가 4개 키를 모두 override하고 상세 경로를 실제 호출).
- **괴리 ③ — 감사 스크립트가 로컬에선 맞고 컨테이너에선 총계 0을 냈다.** 배포 이미지의 FastAPI 0.138.1은 include된 라우트를 `_IncludedRouter`로 감싸 `.path`도 `.routes`도 노출하지 않고 `original_router`만 준다(로컬 `.venv` 구버전은 평탄). 첫 컨테이너 실행이 `전체 /api 엔드포인트: 0` — **하마터면 "문제 없음"으로 오독할 수 있는 거짓 통과**였다. `_walk()`가 양쪽을 재귀 하강하도록 고쳐 두 환경 모두 138/9.
- **괴리 ④ — 프론트 프로브가 정상 화면에 거짓 FAIL.** 모든 화면에 "대상 경로 호출 ≥1"을 요구했으나 심층 리포트(`/analyst-reports`)는 대상 11개가 아닌 `/api/analyst-reports`만 부르므로 호출 0이 정상 → `expectTargets` 플래그로 화면별 기대를 분리.
- **괴리 ⑤ — 상세 진입은 "특정 종목 고집"을 버려야 열렸다.** 상세는 `location.state`로 열려 딥링크가 없고 API 목록의 첫 KR 종목(`112610`)은 탭·정렬에 따라 화면에 없다(스크롤 8회 실패). → 목록의 티커를 순회하며 **화면에 보이는 첫 카드**를 클릭하도록 바꿔 성공(COST). 브라우저 커버 2종 → 7종.
- **자기 뒷정리**: `get_stock_news` docstring의 "공개 read"를 "인증 필요(ADR-0029)"로 정정.

## 학습

### 3부작 종합 (CLAUDE.md 가토로 승급한 4건)

1. **로컬 `.venv` ≠ Docker — 같은 패키지의 *버전 차이*가 API 형태를 바꾼다.** 기존 가토는 "`lxml`이 로컬엔 없다"는 *패키지 유무* 얘기였는데, 이건 FastAPI 버전차가 `app.routes` 구조를 바꿔 스크립트가 조용히 0을 내는 변종. **라이브 게이트를 자칭하는 스크립트는 배포 환경에서도 돌려 숫자가 나오는지 확인할 것**(0을 정상으로 오독하기 쉽다).
2. **로컬 pytest가 추적 대상 정적 데이터를 라이브 스크레이프로 덮어쓴다.** conftest `_block_real_db`는 DB write만 막고 파일 write는 막지 않는다 — task#169(prod DB 오염)의 *추적 파일판*. 전체 스위트 실행 후 `git status`로 부수효과를 확인할 것.
3. **auth 의존성 추가 시 "감사 대상 파일 수 ≠ 작업량".** S3 3연속(4→3, 5→0, 14→0). 기존 가토는 "전수 grep해 override를 추가"로 읽히지만 형제 read가 먼저 인증돼 override가 선재하는 경우가 많다. **전체 스위트를 먼저 돌려 실제로 깨지는 것만** 고치는 순서가 정확하고 빠르다(선제 추가는 중복 위험).
4. **인증 게이팅 변경은 문서 auth 표기 drift를 대량 노출한다.** 3부 합계 `**Auth:** 불필요` **8곳**(1/3:3, 2/3:4, 3/3:1)이 오표기로 남아 변경 즉시 틀린 문서가 됐다. `test_api_doc_sync.py`는 엔드포인트 *존재*만 보므로 auth 산문은 자동검출 밖 → 착수 시 `grep -n '\*\*Auth:\*\* 불필요' API_SPEC.md`를 돌리고 **문서 갱신을 슬라이스로 명시**할 것(3부 계획 전부 빠져 있었다).

### 이 부 고유

- **계획서의 사실 주장은 실행 전에 배선을 열거해 확정한다** — 2/3은 계획 경로 4개가 틀렸고 3/3은 열거로 오류 0. 차이를 만든 것은 이 한 가지다. 나아가 **"완료기준으로 적힌 감사"는 실행 가능한 스크립트로 먼저 만들어라** — 착수 시 대상 확정과 종료 시 게이트를 한 도구로 겸할 수 있고, 이번엔 그게 헛작업(이미 인증된 2경로)까지 걸러냈다.
- **검증 도구의 판정 기준을 대상별로 나눠야 거짓 FAIL을 피한다** — CLAUDE.md task#228의 "검증 도구에서 규약을 어기면 정상 구현을 되돌리게 된다"가 재현됐다(이미 문서화된 가족이라 별도 승급 없음).
- **`X-API-Key` 경로는 positive + negative를 함께 단언** — 정상키 200만 보면 "키를 무조건 통과시키는 구멍"을 못 잡는다. 잘못된 키 401까지 테스트·스모크 양쪽에 넣었다.
