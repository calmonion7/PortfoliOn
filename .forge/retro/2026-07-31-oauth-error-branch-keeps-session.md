# 2026-07-31 — OAuth 에러·소진 코드 착지가 유효한 세션을 죽이는 결함 수정 (task#253, 일괄 승급 회고)

`fg-next all` 드라이브가 회고를 자동 스킵해 봉인했고, 이 파일은 그 지연 승급이다. 원료: `done/2026-07-31-oauth-error-branch-keeps-session/run.md`.

## 계획 ↔ 실제

- **계획대로**: S1에서 App의 세션 부트스트랩 45줄을 `hooks/useAuthBootstrap.js`로 **로직 무변경 이동**(기존 254 green이 그대로 통과 = 이동이 아무것도 바꾸지 않았음의 증거), S2에서 훅 내부 `resolveStored()` 하나를 정상 경로까지 **4곳이 공유**하게 해 세 실패 분기(`?error=` · 코드교환 400 · `.catch`)가 저장 토큰으로 세션을 해석하게 했다. 백엔드 0변경·문서 무변경.
- **S3 mutation으로 이빨 확인**: `resolveStored()`를 `setSession(null)`로 되돌리자 **정확히 목표 3건만 실패**하고 "토큰 없음" 대칭 케이스는 통과 유지 → 수정이 *토큰이 있을 때만* 동작을 바꿨음을 실증. 원복 후 262 green.

- **Divergences**:
  1. **D1 — S4(라이브 UAT) ↔ S5(빌드·배포) 순서를 역전시켰다. 계획의 지시로는 계획의 완료기준을 달성할 수 없었다.** nginx가 `frontend/dist`를 직접 서빙하므로 **빌드 전에는 라이브에 옛 번들이 떠 있다** → S4의 완료기준("신규 프로브 전 단언 PASS")이 원리적으로 달성 불가다. 착수 시 지시↔완료기준을 대조해 그 자리에서 순서를 보강했다(commit+push → build → 프로브).
     - 이것은 **CLAUDE.md 가토 ⑥의 3번째 관측**이지만 성격이 다르다. 앞의 두 사례(#237 recharts height, #230·231·232 문서 슬라이스)는 "회고에 적어둔 제약이 계획의 *지시*로 이월되지 않았다"였는데, 이번은 이월 실패가 아니라 **계획이 배포를 검증의 *후속*으로 배치**한 것이다. 이 프로젝트는 프론트 검증이 배포에 의존하는 구조(빌드=즉시 라이브)이므로, **프론트 라이브 UAT를 포함하는 계획은 빌드가 UAT보다 앞에 와야 한다.**
     - 부수: commit+push를 build보다 **먼저** 묶었다 — 2분 폴러가 `LOCAL != origin/main`이면 `reset --hard`를 하므로 tracked 편집(App.jsx)이 날아갈 창을 최소화해야 했다.
  2. **D2 — 소진 코드 arm을 모킹이 아니라 라이브 백엔드의 실제 400으로 밟았다.** `?oauth=uat253-used-code`로 착지시켜 라이브 `/api/auth/oauth/token`이 실제로 400을 반환하게 했다(지배적 트리거 = 1회용 코드 재실행과 완전히 같은 경로). 응답 상태를 **메커니즘 커버리지로 별도 출력**(⑧ⓖ)해 `[400, 400]`을 관측하고, 400이 안 잡히면 "그 PASS는 400 경로를 실증하지 못한다"고 프로브가 스스로 말하게 적어 뒀다. 목표 단언(앱 유지)은 상태코드와 무관하게 항상 검사.
  3. **D3 — 단위테스트를 계획의 5분기가 아니라 8건으로 썼다.** 추가한 **④-b**(코드교환 실패 + 토큰 **없음** → null)는 선택이 아니라 필요였다 — mutation에서 "토큰 없음 대칭 케이스가 여전히 통과하는지"를 봐야 수정이 토큰 있을 때만 동작을 바꿨다고 말할 수 있다(⑧ⓗ "단언하지 않는 형제까지 관측 범위에").
  4. **D4 — 계획에 없던 로그아웃 라이브 확인을 추가했다(자체 리뷰 산물).** auth는 위험 영역이라 fg-run §3 자체 리뷰를 붙였고, 거기서 **훅 추출로 출처가 바뀐 배선 중 프로브가 안 밟은 것 = 로그아웃**(`setSession`이 이제 훅에서 나온다)을 식별했다. #252·#253 프로브는 로그인·세션 렌더만 밟는다. 임시 스크립트로 실측 PASS.
  5. **D5 — S3 grep 정정 대상 0건**(계획이 "0건일 수도 있다"고 예상한 대로). `oauth_denied|oauth_failed` 서술은 백엔드 코드와 codebase 지도뿐이고 "에러면 세션 없음"을 단정하는 주석·테스트 문구는 없었다.

## 배운 것

- **다음엔 다르게**:
  1. **프론트 라이브 UAT 슬라이스는 빌드·배포보다 뒤에 배치할 것.** 이 프로젝트는 nginx가 `dist`를 직접 서빙하므로 "빌드 = 즉시 라이브"이고, 따라서 빌드 없이 도는 라이브 프로브는 **옛 번들을 잰다**. 계획 작성 시 "이 완료기준을 재려면 무엇이 먼저 라이브여야 하는가"를 한 줄 확인하면 잡힌다. (실제로 task#254에서는 이 순서를 역이용해 **빌드 전 실행으로 red-first를 라이브에서 확보**했다 — 순서를 알면 무기가 된다.)
  2. **순수 이동(리팩터) 슬라이스의 완료기준은 "기존 테스트가 무변경으로 통과"로 잡을 것.** 그게 이동이 아무것도 바꾸지 않았다는 유일한 증거다.
  3. **훅·모듈 추출은 "출처가 바뀐 배선"의 목록을 만들고 프로브 커버리지와 대조할 것.** 로그아웃처럼 조용히 빠지는 경로가 생긴다.
  4. **분기 주석에 "지배적 트리거"를 적을 것.** `?error=`를 "사용자가 구글에서 거절함"으로만 읽으면 세션 유지가 과보호처럼 보인다 — 실제 지배적 트리거가 뒤로가기 재실행임을 알아야 왜 유지가 옳은지 이해된다.
- **남은 것 / 주의**: 정상 성공 경로는 `returnFromOAuth()` 후 `authLoading`을 false로 두지 않는다(문서 교체를 전제한 #252 설계 보존). 되감기와 replace가 **둘 다** 불발하면 빈 화면이 될 수 있으나 이번 변경이 만든 위험은 아니다.
- **후속 후보(계획이 명시적 제외)**: 로그아웃 상태에서 OAuth 실패 이유 표시. 구글에서 취소하면 지금도 이유 없이 로그인 화면만 뜬다 — `LoginPage`가 props를 안 받고 `ToastProvider`가 로그인 트리 안에만 있어 배선이 늘어난다.
