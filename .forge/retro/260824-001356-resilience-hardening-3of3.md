# 2026-08-24 — bcrypt 엔드포인트 레이트리밋: 인메모리 슬라이딩 윈도우 (B20)

task#337 · fg-loop 무인 드라이브 3/3 · 커밋 `374217b` · 일괄 승급으로 뒤늦게 작성

## 계획 대비 실제

- **계획대로 된 것**: 착수 시 실측 6항(Dockerfile `--workers` 없음 · bcrypt 호출 위치 · 레이트리밋 라이브러리 0건 ·
  login/register 순서 · nginx `limit_req` 0건 + `X-Real-IP $remote_addr`만 · 기존 테스트 2건)이 **전부 계획과 일치**했다.
  S3(배선)이 계획대로 본문 첫 줄에 들어갔고 S1-3(bcrypt 미호출) 축이 그 순서를 강제했다.
  S5(라이브 스모크)에서 배포 후 `/api/auth/login` 오답 1회 → **401**(429 아님)으로 오차단 없음을 확인했다.
- **이탈**:
  1. **ADR의 *전제*가 거짓이었다(적대 검토 HIGH ×2 + LOW ×1이 독립 지목).** 아래 학습 1.
  2. **`threading.Lock`이 필수였다 — 계획에 없었다.** 아래 학습 2.
  3. **red-first 8종 중 2종이 배선 전에 이미 통과**했다(임계 미달 정상경로 · 모듈 직접 호출 키캡).
     fault-injection으로 이빨을 확인하고 **회귀 가드임을 알고 남겼다.**
  4. **문서가 「해소」로 거짓을 말할 뻔했다** — S4가 B20 해소 각주에 「`127.0.0.1`로 좁혀 전제를 강제했다」를 적었는데
     오케스트레이터가 그 인프라 변경을 되돌렸으므로 문장이 사실과 반대가 됐다. 각주를 고치고 `B82`를 신규 등록했다.
  5. **정지조건 C8③이 정직한 신규 기록과 충돌**했고 감사 패턴 자체가 거짓 경보를 냈다. 아래 학습 3·4.

## 학습

- **다음에 다르게**:
  1. **ADR이 기록한 *트레이드오프*와 ADR이 전제한 *사실*을 구별하라 — 후자가 거짓이면 그것은 결함이다.**
     적대 검토 프롬프트에 「ADR에 기록된 트레이드오프를 결함으로 재발견하지 말 것」을 넣을 때
     **「단 그 *전제*가 거짓이 된 경우는 결함이다」를 반드시 쌍으로 넣을 것** — 이번엔 그 한 줄이 있었고 그것이 최대 발견을 만들었다.
     실측: ADR은 `X-Forwarded-For` 배제와 「폴백이 한 버킷인 것은 의도된 페일클로즈」를 **「공개 경로는 Cloudflare 전용」**으로 정당화하는데,
     `nginx.conf`의 `/api/` 블록이 `CF-Connecting-IP`를 **한 번도 참조·제거하지 않고** `docker-compose.yml`·`deploy.sh`가
     포트를 `0.0.0.0:80`에 게시하므로 **터널을 우회해 직접 닿는 클라이언트가 헤더를 돌려 두 임계를 무력화**한다.
     **역방향이 더 나쁘다** — 피해자의 실제 IP를 넣어 버킷을 소진시키면 그 사용자가 창 종료까지 429를 받는다
     (**B20 도입이 새로 만든 표적 차단 벡터**다. 도입 전에는 아무도 남을 잠글 수 없었다).
     → 닫지 않고 **`B82`로 등록**했다. 수복이 만든 `127.0.0.1` 축소는 기술적으로 안전함까지 확인됐으나
     (`cloudflared`가 `localhost:80`만 사용 · nginx 443 블록은 주석 처리돼 비활성 · ACME는 터널 경유)
     **사용자 머신의 네트워크 노출을 바꾸는 결정**이라 무인 드라이브가 단독으로 넘을 문턱이 아니라고 판정해 되돌렸다.
     → ADR 보정 + 가토 승급.
  2. **「단일 프로세스」가 「경합 없음」을 뜻하지 않는다.** ADR의 단일 프로세스 가정은 **워커 수**의 이야기이고,
     같은 프로세스 안의 **스레드풀 병렬성**은 그 가정이 덮지 않는다. `login`·`register`가 `async def`가 아니라 **`def`**라
     Starlette가 `run_in_threadpool`로 실제 OS 스레드에서 병렬 실행하므로, 락 없는 판정-후-기록이 **3가지로** 깨진다:
     ⓐ 과다 허용(20스레드 강제 동시 진입에서 `allowed=13`, limit=10) ⓑ 만료 prune의 `popleft`가 빈 deque에서
     **IndexError → 로그인 500**(20스레드 중 19건) ⓒ 신규 키 버킷 생성의 확인-후-대입으로 기록 소실.
     검토가 barrier를 심어 셋 다 강제 재현했고 `threading.Lock`으로 원자화 + 동시성 회귀 2건을 추가했다. → 가토 승급.
  3. **원장·목록 감사는 개수가 아니라 정체성으로 판정하라 — 개수는 양방향으로 틀린다.**
     C8③을 「§0 B행 수 == 6」으로 썼는데 ⓐ 드라이브가 새 결함을 정직하게 적으면(`B82`) 7이 되어 **영원히 FAIL**하고
     ⓑ 반대로 **형제를 하나 지우고 새 행을 하나 더해도 6이라 통과**한다.
     → 「선재 형제 6행 전부 존재 + 추가분은 이 드라이브의 신규 발견분」으로 다시 썼다(느슨화가 아니라 강화). → 가토 승급.
  4. **볼드 마크업이 감사 정규식을 깨뜨린다.** `^\| *(\*\*)?B[0-9]+ *\|`가 `| **B49** |`의 **뒤쪽 `**`** 때문에 매치하지 않아
     **B49가 사라진 것처럼** 보였다(거짓 경보). `\*{0,2}B[0-9]+\*{0,2}`로 넓혀 재측정하고 **7행을 눈으로 열거**해 확인했다.
     같은 라운드에서 `ls .forge/retro | grep -c resilience`도 무관한 옛 회고 2건을 잡아 오탐을 냈다.
     → 위 3과 같은 가토 항목에 부수로 기록.
  5. **LOW 기각이 옳았던 사례를 기록으로 남긴다.** 「`register`의 판정이 이메일 중복확인보다 앞이라 bcrypt에 닿지도 않는
     저비용 400 경로가 같은 예산을 소진한다」는 지적을 기각했다 — 판정을 뒤로 옮기면 **「이미 등록됨」이 무제한 속도로 노출돼
     이메일 열거(enumeration) 오라클**이 생긴다. 예산 절약(이득)보다 계정 존재 조회(손실)가 크다.

- **확인된 것 (keep)**:
  - **라이브 스모크를 「임계를 넘기지 않는 형태」로 설계한 것이 옳았다** — 오답 1회로 401을 확인하는 것만으로
    「오차단 없음」이 증명되고, 429 경로의 증거는 pytest가 가진다. 임계를 라이브에서 넘기면 사용자 자신의 IP가 차단된다.
  - **배포 후 포트 바인딩 폴링**(task#250)이 값을 했다 — 배포 success 뒤 8초 내 개방을 확인하고 스모크를 돌렸다.
  - 컨테이너에서 `services.rate_limit`을 임포트해 `_lock` 심볼 존재를 확인한 것이 **수복본이 실제로 배포됐다**는 값싼 증거였다.
