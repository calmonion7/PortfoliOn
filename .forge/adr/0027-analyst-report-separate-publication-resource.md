# ADR-0027 — 애널리스트 리포트는 enrich/스냅샷과 분리된 발행물 리소스

- 상태: 채택 (2026-08-21 개정 — 아래 개정 노트 3건)
- 날짜: 2026-07-25
- 관련: task#211(백엔드 발행 파이프라인), task#212(프론트 문서 페이지), task#222(목록 정체성·삭제 예외), task#324(화면 경계 재배치), ADR-0028(자동화 파이프라인), ADR-0047(리포트 계열 경계)

> **개정 노트 3 (2026-08-21, task#324 — ADR-0047 적용)**: **화면 근거만 이관하고 데이터층은 손대지 않는다.**
> ① 개정 노트 2 ①이 정한 「목록의 정체성 = 종목당 최신 1건」의 *데이터 계약*(`DISTINCT ON (ticker)`)은 그대로다.
> 바뀐 것은 **그 목록이 놓이는 화면의 성격**이다 — 사용자 대면 발행물 목록은 폐지되고 그 자리를
> `/analyst-reports` = **admin 발행 관리 화면**이 대신한다(비-admin은 `/reports`로 리다이렉트).
> 사용자가 발행물을 읽는 경로는 **그 종목 리포트 상세의 「심층 리포트」 탭**이다(발행물 있는 종목만 탭이 뜬다).
> 근거는 ADR-0047의 「병합 가능성은 키의 관계가 정한다」 — 발행물은 종목 축에 1:N이므로 목록을 따로 두는 것이
> 같은 종목을 두 화면에서 찾게 만든다. nav 항목 「심층 리포트」는 제거되고 그 경로들은 「리포트」 항목이 흡수한다.
> ② **삭제 수단(개정 노트 2 ②)은 무력화되지 않는다** — `DELETE /api/analyst-reports/{ticker}`(`require_admin`)와
> 자동 발행 대상 지정·해제·즉시 발행 지시 **3종 전부 그 admin 화면에 그대로 남는다.** 리다이렉트가 admin에게는
> 걸리지 않는다는 대조군을 테스트로 못박았다(비-admin만 리다이렉트 · 권한 확정 전에는 어느 쪽으로도 보내지 않음).
> ③ 문서 단독 라우트 `/analyst-report/:ticker/:date`는 **유지**된다(딥링크·공유·과거 판 진입). 다만 복귀 지점은
> 목록이 아니라 **그 종목 리포트 상세**다(`location.state.ticker` 관례, task#131). 백엔드·API·스키마·루틴 프롬프트의
> 「애널리스트 리포트」 표기는 **전부 미변경**이다 — 이 태스크의 백엔드 변경은 0줄이다(사용자 대면 이름만 「심층 리포트」).

> **개정 노트 2 (2026-07-26, task#222)**: 두 대목을 수정한다.
> ① **발행물 목록의 정체성 = 종목당 최신 1건**(`GET /api/analyst-reports`가 `DISTINCT ON (ticker)` 최신 판만 반환). 과거 판(이력)은 **문서 상세에서 이동**해 본다(`GET /api/analyst-reports/{ticker}`가 전 판 유지 — 소비처가 목록/이력으로 정확히 갈리므로 플래그 없이 분기별 동작). 판 누적 보관 자체는 그대로 유효하며 바뀐 건 *목록의 단위*다 — 판을 나열하면 단위가 종목이 아니라 판이 되어 "지금 어떤 종목을 어떻게 보는가"가 묻힌다. 이 응답은 [[루틴]]의 7일 가드레일 판단 재료이기도 한데(ADR-0028 §3), 최신 1건이 오히려 그 판단에 정확한 형태다.
> ② **"발행 후 불변"에 삭제 예외를 둔다** — `DELETE /api/analyst-reports/{ticker}`(**`require_admin`**, API key 제외)로 admin이 **종목 단위 전 판**을 지울 수 있다. 근거: 발행물과 대상 지정(`analyst_target`)은 별개 저장소라 대상에서 해제해도 발행물이 목록에 계속 남고, 정리 수단이 전무하면 매번 프로덕션 SQL이 된다. 다만 **판 단위 삭제는 만들지 않는다** — 잘못된 판 하나는 새 판 발행으로 덮는 것이 불변 문서 원칙이며, 삭제는 "이 종목 발행물을 통째로 없앤다"는 관리 행위로만 남긴다. 루틴에 삭제 권한을 주지 않는 이유는 오삭제 리스크뿐이고 삭제할 이유가 없다는 것(wrong<missing).
>
> **개정 노트 1 (2026-07-25, task#213)**: "발행: Cowork 온디맨드 전용, 자동 선정·배치 발행 없음"은 원칙이 아니라 **당시 자동화 수단 부재(Anthropic API 계정 불가)의 우회**였음이 확인됨. Claude Code 루틴 API 트리거로 수단이 생겨 **자동 발행을 허용**한다 — 단 무제한이 아니라 루틴 재량 + 가드레일(보유 종목 중 최신 발행 7일+ 경과 또는 유의미한 변화 종목만, 회당 최대 2종목, ADR-0028 §3). 발행물 리소스 구조(별도 테이블·라우터·불변 누적·서버 데이터 블록 첨부)는 그대로 유효.

## 맥락

사용자는 "증권사 애널리스트 리포트 수준"의 심층 분석을 원하지만, **전 종목이 아니라 선별 종목만** 대상으로, **기존 리포트와 별개의 새 페이지**로 원한다. 기존 파이프라인은 두 저장소뿐이다:

- **스냅샷**(`snapshots` 테이블) — 전 종목·매일 자동 생성·시장 데이터 박제. 최신 데이터가 정체성.
- **enrich 필드**(`tickers` 컬럼: moat·insights 등) — 종목당 **최신 상태 1개**만 유지, Cowork가 덮어쓰기.

애널리스트 리포트는 성격이 다르다: 발행 시점이 고정된 **판단 문서**(발행물)로, 발행일·과거 판 열람이 정체성이고 다음 날 자동으로 덮이면 안 된다.

## 결정

**별도 리소스로 만든다**: 신규 `analyst_reports` 테이블(ticker+발행일 단위 누적) + 신규 라우터(기존 `/api/report` 라우터에 얹지 않음).

- **발행**: Cowork 온디맨드 (admin/API key 쓰기 전용). 자동 선정·배치 발행 없음.
- **하이브리드 생산**: 판단·서사(논지·투자포인트·적정주가 밴드·리스크)는 Cowork 텍스트, **숫자 블록(발행 시점 시세·forward 추정치·피어 멀티플·PER 밴드·컨센서스 목표가)은 서버가 발행 순간 자동 첨부**해 문서를 자기완결적으로 박제한다.
- **데이터 블록의 원천은 그 종목의 최신 스냅샷 발췌**(+PER 밴드는 스냅샷 재무 시계열로 신규 계산) — 발행 요청 경로에서 외부 API 라이브 fetch를 하지 않는다(배치-백킹 원칙, task#48/49/50 계열).
- 열람은 로그인 사용자 전체(스냅샷과 동일 공유 모델).

## 근거

- **enrich 필드에 얹기**를 기각: 종목당 최신 1개 모델이라 발행물 누적이 불가능하고, 전 종목용 컬럼에 선별 종목만 채우는 어색함. 신규 필드마다 6계층 배선 비용도 문서 1개 단위 발행과 안 맞는다.
- **기존 `/api/report` 라우터에 얹기**를 기각: 그 라우터는 catch-all `GET /{ticker}/{date_str}`가 있어 신규 경로가 ticker로 오인 라우팅되는 전례(task 수주잔고 라우트 버그)가 있다. 별도 prefix가 안전.
- **Cowork가 숫자까지 전부 작성**을 기각: 수주잔고 ×100 오저장 전례 — 숫자는 서버가 이미 보유한 검증된 재료(스냅샷)에서 채우는 게 일관성 보장.

## 결과

- 신규 테이블·라우터·문서(API_SPEC + CLAUDE_COWORK_API) 배선 비용 발생. 스키마는 `app_schema.sql` + `main._migrate` 쌍 필수(ADR-0006).
- 발행 전제조건: 그 종목의 스냅샷이 존재해야 한다(없으면 발행 거부 — 데이터 블록을 채울 수 없으므로).
- 문서는 발행 후 불변(immutable)이 기본 — 수정이 필요하면 새 판을 발행한다.
