# 자동 배포 트리거 = 배포 기록 SHA 대조, 실패는 1회로 끝 — `deploy.sh` 종료코드 2/1 계약

- 상태: 채택 (Accepted)
- 관련: task#382(B84 해소), task#377(옛 트리 배포 거부·폴러 ff 전용), task#369(러너 x86 offline), 루트 `CLAUDE.md` Deployment 절

## 맥락

러너가 offline인 동안 자동 배포 경로가 없었다. launchd 폴러(`scripts/auto-deploy-poll.sh`)가 배포를 못 한 원인은 세 겹이었다. ⓐ 폴러가 잡은 잠금을 `deploy.sh`가 보고 종료했다. ⓑ launchd PATH에 npm·docker가 없었다. ⓒ 트리거가 「HEAD가 origin보다 뒤처짐」뿐이라 **이 체크아웃에서 commit+push하면 HEAD == origin이 되어 아무 일도 일어나지 않았다** — ⓐⓑ를 고쳐도 우리 push는 배포되지 않는 구조였다.

## 결정

1. **트리거는 git 상태가 아니라 「무엇이 배포됐는가」의 기록이다.** `deploy.sh`가 성공 끝에 배포한 SHA를 저장소 밖 `~/.portfolion-deployed-sha`(`DEPLOY_MARKER`)에 쓰고, 폴러는 `origin/main`이 그것과 다르면 배포한다(같음 → 바로, 뒤처짐 → ff 후, 앞섬·갈라짐 → 손대지 않음). 러너·수동 `deploy.sh`도 같은 기록을 쓰므로 어느 경로로 배포됐든 중복 배포가 없다.
2. **`deploy.sh` 종료코드가 재시도 여부를 가르는 계약이다.** `2` = 사전 거부(컨테이너를 건드리기 전 — 잠금·미커밋·fetch 실패·앞섬/갈라짐·ff 실패) → 다음 폴에서 재시도. `1` = 그 뒤의 모든 실패 — 도구가 어떤 코드로 죽든 `trap 'exit 1' ERR`로 1로 정규화한다(`set -e`는 도구 종료코드를 그대로 흘리므로, 정규화하지 않으면 빌드 중 exit 2가 「거부」로 오독돼 재시도 루프가 된다).
3. **실패는 1회로 끝낸다.** 폴러는 실패한 SHA를 `~/.portfolion-deploy-failed-sha`에 쓰고 그 커밋을 다시 시도하지 않는다. 새 push가 오거나 사람이 수동 `deploy.sh`로 성공하면 풀린다.
4. **잠금은 `deploy.sh`만 잡는다.** 폴러는 잠금이 있으면 skip만 한다.

## 고려한 대안

- **트리거 = HEAD 뒤처짐 유지 + in-checkout push는 사람이 수동 배포** — 지금까지의 상태. 매 push마다 손 배포가 필요했다. 기각.
- **트리거 = 컨테이너 이미지 라벨이나 서빙 번들 해시와 대조** — 「실제로 라이브인 것」을 재는 장점이 있지만 백엔드·프론트를 각각 따로 판정해야 하고 nginx stuck 같은 일시 장애가 「미배포」로 읽혀 재배포를 부른다. 기각 — 기록 파일은 「무엇을 배포하기로 성공했는가」만 말하고, 그 이상은 라이브 스모크의 몫이다.
- **실패도 매 폴 재시도** — 일시 장애(네트워크·도커 데몬)에서 자동 회복하는 장점이 있지만, 결정적 빌드 실패면 2분마다 백엔드를 내려 ~5분씩 다운되는 영구 장애 루프가 된다. 기각 — 실패 커밋이 새 push까지 미배포로 남는 대가를 받아들였다.
- **재시도 N회 후 중단** — 위 둘의 절충이지만 실패 카운트 상태가 하나 더 생기고, 결정적 실패에서도 N번 장애를 낸다. 기각.

## 결과

- 배포 판정은 폴러 로그 `Deploy complete: <SHA>`·`배포된 커밋:` 줄과 기록 파일로 한다. 러너가 offline이어도 미배포가 아니므로, `gh run list`의 `queued`/24h `cancelled`만으로 「배포 안 됨」을 단정하지 말 것.
- 기록 파일이 없는 새 머신에서는 폴러가 현재 origin을 즉시 배포한다(의도된 동작).
- 폴러를 편집할 땐 launchd가 작업트리 판을 2분마다 실행하므로 기록 == origin(no-op) 상태에서 할 것.
- 회귀 가드: `scripts/test_deploy_guard.py`(30축). 실패 1회 정책의 라이브 재현은 운영을 고의로 내리는 일이라 하지 않는다.

## 보정 (2026-10-10, task#384)

이 결정은 「러너·수동 `deploy.sh`도 같은 기록을 쓰므로 중복 배포가 없다」는 결과를 전제했지만, **러너 쪽에서는 성립하지 않았다.** 당시 `.github/workflows/deploy.yml`은 기록을 보지 않고 작업트리를 `origin/main`에 강제로 맞춘 뒤 `deploy.sh`를 무조건 실행했다. 그래서 러너가 되살아나면 ⓐ 폴러가 이미 배포한 커밋을 다시 배포하고 ⓑ 폴러 배포와 겹치면 잠금 때문에 exit 2로 잡이 빨갛게 실패하며 ⓒ task#377이 폴러에서 없앤 「미커밋 편집·push 안 한 커밋 소실」이 러너 경로로 되살아날 수 있었다. 러너가 x86 바이너리로 offline이었기 때문에 발현되지 않았을 뿐이다.

task#384가 러너 잡을 `scripts/runner-deploy.sh`로 분리해 이 결정의 트리거를 러너에도 적용했다. 기록 == `origin/main`이면 「이미 배포됨」으로 exit 0이다. 다르면 `deploy.sh`를 부르고 그 종료코드를 그대로 돌려준다. 잠금이 있으면 풀릴 때까지(기본 15분, `RUNNER_LOCK_WAIT_SEC`) 기다린 뒤 기록을 **다시** 대조한다. 작업트리는 되돌리지 않는다(`deploy.sh`가 fetch·ff-only·거부를 맡는다). 수동 `bash deploy.sh`는 기록과 무관한 강제 재배포로 남긴다 — 기록 skip은 러너 래퍼에만 둔다.

라이브 확인: arm64 러너 복구 후 `da8eb68`의 run은 「이미 배포됨」(폴러가 먼저 배포)이었고, `7f44458`의 run은 러너가 `배포된 커밋: 7f44458`로 실배포했다. 회귀 가드는 `scripts/test_deploy_guard.py`의 러너 축 9건(축마다 주입으로 이빨 확인)이다.
