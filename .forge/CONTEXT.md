# PortfoliOn — 도메인 용어집 (CONTEXT)

이 문서는 용어집입니다. 구현 세부사항이 아니라 "우리가 같은 단어로 같은 것을 가리키는가"만 다룹니다.

## 배치 (Batch)

데이터를 생성/갱신하는 **이름 붙은 작업**으로, 스케줄러 크론 잡 1개와 1:1 대응한다. 실행 1회(run)마다 **트리거 종류**를 가진다:
- **자동(auto)** — APScheduler 크론으로 백그라운드 실행 (`scheduler.py`)
- **수동(manual)** — 사용자가 설정화면 버튼으로 실행

한 배치는 두 트리거를 모두 가질 수 있다 (예: 리포트 생성·구루 크롤·컨센서스·레버리지·대차). 따라서 자동/수동은 배치의 고정 속성이 아니라 **실행(run)의 속성**이다. 하나의 크론이 여러 데이터셋을 만들어도 배치는 하나로 센다. 단, 한 크론이 만드는 데이터셋들이 **시장별로 깔끔히 갈라지면**([[배치 시장 분류]]) 시장별 형제 배치로 분리한다(daily_report·earnings·monthly).

현재 자동 배치: daily_report_kr·daily_report_us(2026-06 시장별 분리 — 아래 [[장마감]] 참조), earnings_kr·earnings_us(KR Top2 / M7 분리), monthly_kr·monthly_us(KR수출 / FRED 경제지표 분리), guru_crawl, daily_digest, leverage_fetch, lending_fetch, kr_rankings_fetch, us_rankings_fetch, investor_trend_fetch, short_sell_fetch, backlog_fetch.

## 배치 현황 (Batch Status)

모든 배치를 한 화면에서 보는 뷰. 배치별로 다음을 표시한다:
- **주기** — 실행 스케줄(크론)을 사람이 읽는 문구로
- **사용처** — 그 배치가 만든 데이터를 소비하는 UI 위치
- **다음 실행** — 다음 자동 실행 예정 시각 (APScheduler에서 실시간 조회)
- **실행 이력** — 최근 실행 기록(성공/실패), 각 줄에 자동/수동 태그

## 배치 시장 분류 (Batch Market Classification)

각 [[배치]]가 다루는 데이터가 어느 시장에 귀속되는지의 분류. **국내 / 해외 / 공통** 셋이며, [[배치 현황]] 허브의 시장 서브탭이 이 축으로 나뉜다(탭 안은 기존 category 섹션 유지). 판정 기준은 **데이터의 출처·주체 국가**다(사용처 시장이 아니다):

- **국내(KR)** — KR 소스/대상: DART·KOFIA·키움 기반 (backlog·leverage·lending·kr_rankings·investor_trend·short_sell·daily_report_kr·earnings_kr(KR Top2)·monthly_kr(KR수출)).
- **해외(US)** — US 소스/대상: yfinance S&P·M7·FRED (daily_report_us·us_rankings·earnings_us(M7)·monthly_us(FRED 경제지표)). FRED 경제지표는 양 시장 투자판단에 쓰는 매크로지만 **출처가 미 연준이라 해외**로 둔다(출처국 기준의 일관 적용).
- **공통(both/global)** — 한 단위(종목·유저) 안에서 KR·US가 엉켜 시장 귀속이 불가능하거나 글로벌인 배치: consensus(daily_report에 내장, 종목 market별 분기), daily_digest(유저 포트폴리오 KR+US 합산), guru_crawl(dataroma 글로벌).

데이터가 시장별로 깔끔히 갈라지는 배치만 시장별 형제로 **분리**한다(earnings·monthly는 한 크론이 시장별 독립 함수 2개를 호출하던 구조라 분리 가능). consensus·digest는 분리 불가라 공통에 남는다. 정본 경계·분리 규칙은 ADR-0013.
_Avoid_: "사용처가 양 시장이면 공통"(아니다 — 출처국 기준), "US 데이터는 다 해외"(맞지만 매크로/지수도 출처국으로 판정)

## 스케줄 패턴 (Schedule Pattern)

한 배치의 자동 실행 주기를 표현하는 형태. 4가지가 있다:
- **일배치(daily)** — 매일 지정 시각에 1회
- **주배치(weekly)** — 지정 요일(복수 가능)의 지정 시각
- **월배치(monthly)** — 매월 지정 일(day-of-month)의 지정 시각
- **인터벌(interval)** — 지정 시간대 안에서 N분마다 반복 (예: 장중 랭킹)

배치별로 패턴을 자유롭게 고를 수 있고, 편집은 admin [[액션]]만 가능하다(열람은 모두). **타임존은 패턴의 일부가 아니라 배치 고정 속성**이다(편집 불가, 기본 Asia/Seoul, us_rankings만 America/New_York). 인터벌엔 폭주 방지 가드레일이 있다(최소 5분, 중복 실행 방지).

## 장마감 (Market Close)

리포트 [[배치]]가 "오늘 데이터"를 잡는 기준 시점. 시장마다 다르다:
- **KR** — 정규장(KRX)은 15:30에 단일가로 공식 종가가 확정되지만, 이 서비스는 NXT(넥스트레이드) 연장세션(~20:00)까지 보는 통합(SOR) 시세를 쓰므로 **장마감 = 20:00**으로 본다. 일봉 종가는 15:30 KRX 종가로 동일하나, 스냅샷 **현재가**는 20:00 NXT 가격을 반영한다.
- **US** — 16:00 ET. 한국시간으로는 새벽 05:00(서머타임)~06:00(겨울)이라 KST 아침에 마감 직후가 된다.

**시장별 리포트 생성 시각**: 가장 신선한 데이터를 박제하려면 각 시장 장마감 직후에 그 시장 종목만 생성한다 — KR은 20:30 KST, US는 07:00 KST(둘 다 Asia/Seoul). 단일 08:00 배치는 US엔 신선했지만 KR은 개장 전이라 어제 종가가 박제되던 문제를 해소한다.

**기대 리포트 날짜**: 어떤 종목의 "최신 리포트가 있어야 할 날짜". 시장별·시각인지로 계산한다(KR은 20:30 전이면 직전 영업일, 후면 당일; US는 07:00 기준). 종목 최신 스냅샷이 이 날짜보다 오래되면 "미생성"으로 본다.

## 사용처 (Usage / Consumer)

한 배치가 만든 출력 데이터를 **소비하는 UI 위치**(페이지/탭). 예: `kr_rankings_fetch` → 랭킹 탭, `earnings_refresh` → Market Hub. 한 배치가 여러 사용처를 가질 수 있다.

## 실행 이력 (Execution Log)

배치 실행의 시작/종료/성공·실패/에러 기록. 배치별 **최근 N건(잡당 20건)**만 보관하며, 초과분은 insert 시 자동 삭제한다(별도 정리 크론 없음). 저장소는 `job_runs` 테이블.

## 액션 (Action) / 열람 (View)

- **열람** — 배치 현황을 보는 것. 권한 보유 사용자 누구나 가능(읽기 전용).
- **액션** — 스케줄 편집·지금 실행·백필 등 상태를 바꾸는 조작. **admin만** 가능(UI 숨김 + API 게이트).

## 미생성 (Ungenerated)

리포트 목록에서 **마지막 daily_report [[배치]] 스케줄일을 기준으로 뒤처진 종목**들의 탭/분류. 정본 정의는 "**최신 리포트 날짜가 그 스케줄일보다 이전이거나, 리포트가 아예 없는** 종목"이다. 즉 스케줄일보다 더 최신 리포트(예: 주말 수동 생성분)가 있으면 미생성이 **아니다**.
_Avoid_: "정확히 그 스케줄일의 리포트가 없으면 미생성"(틀림 — 더 최신 리포트가 있어도 미생성으로 오분류됨). ETF 여부와 무관(ETF도 일반 종목과 동일 기준).

## 그외 종목 (Other-User Stock)

관리자가 리포트 목록을 `scope=all`로 볼 때만 보이는 탭/분류. 정본 정의는 "**다른 사용자의 보유/관심(user_stocks)에는 있으나 관리자 본인의 목록엔 없는** 종목"이다(`is_mine=false`). 목록은 ticker 단위로 합산되므로 그외 한 항목이 여러 사용자에게 동시에 속할 수 있다. 관리자의 **삭제**는 그 ticker를 **모든 사용자의 user_stocks에서 제거**하는 것을 뜻한다(다른 사용자 항목 포함, 보유·관심 양쪽). 스냅샷(리포트 데이터)은 건드리지 않아 보이지 않는 고아로 남는다. 본인 목록엔 없으므로 그외 종목엔 수정·승격 액션이 의미가 없다(삭제만 노출).
_Avoid_: "내 목록에서만 제거"(틀림 — 본인 목록엔 애초에 없음), 리포트/스냅샷 삭제와 혼동(그외 삭제는 소유만 제거).

## 추적 상태 (Tracked Status)

어떤 종목이 **내 보유·관심 목록에 어떻게 들어 있는가**를 가리키는 4값 상태다: **보유(holding)** · **관심(watchlist)** · **미추적(none)** · **모름(unknown)**. 앞의 셋은 서버가 답을 준 *사실*이고, **모름은 답을 못 받은 상태**(추적상태 조회 실패)다 — 이 넷째 값이 정의의 핵심이다. 조회가 성공하고 결과가 비어 있으면 그건 **미추적**이지 모름이 아니다.

모름과 미추적을 같은 것으로 취급하면 화면이 **잘못된 동사**를 제시한다: 이미 관심에 있는 종목에 「☆ 추가」를 보여 누르면 중복 추가가 되고(제거하려던 의도와 반대), 이미 추적 중인 종목을 검색하면 리포트가 아니라 추가 모달로 보낸다. 그래서 규칙은 **모름이면 액션을 제시하지 않는다**(어포던스 비활성 + 사유 표시)이며, 이는 프로젝트의 `wrong < missing` 원칙을 어포던스에 적용한 것이다.

같은 원리가 **보유**에도 적용된다 — 이미 보유 중인 종목에 「☆ 추가」는 의미 없는 동사이고, 누르면 서버가 `already_exists`로 거절한다(보유·관심을 한 네임스페이스로 검사하므로). 그래서 보유도 액션 없이 상태만 표시한다. 규칙을 일반화하면 **액션이 무의미한 상태(모름·보유)에는 액션을 제시하지 않는다**이다.

_Avoid_: "조회 실패 = 미추적"(이 혼동이 정확히 결함이다), "빈 결과 = 모름"(빈 결과는 사실이다), "보유는 관심의 상위집합"(별개 값이다 — 보유 종목은 관심 목록에 없다), [[그외 종목]]과 혼동(그건 *다른 사용자*의 소유 여부이지 내 목록의 조회 성패가 아니다).

## 수주잔고 (Order Backlog)

정기보고서 "수주상황" 표의 **기말 잔여 수주액** — 아직 납품·매출로 인식되지 않은, 앞으로 실현될 수주분. 산식상 `수주총액 − 기납품액`(또는 `기초수주잔액 + 신규증감 − 기납품액 = 기말수주잔고`)이다. 다중엔티티 지주사(예: 한화에어로)는 공시 수주상황 표의 **연결 합계를 정본 수주잔고**로 하고, **[[사업부문 분해]]**로 모회사 본체분과 자회사분(한화오션·한화시스템 등)을 구분해 보여준다. (별도 상장 자회사가 섞여 생기는 이중계상은 종목 표시가 아니라 포트폴리오 합산 단계의 문제로 따로 다룬다.)
_Avoid_: 수주총액(누계라 다름), 백로그(영문 혼용)

## 수주총액 (Cumulative Order Total)

계약 체결 기준 **누계 총 수주금액**. 잔고가 아니라 누계이므로 수주잔고보다 항상 크거나 같다(예: 한화 162조 vs 수주잔고 116조). 자동 추출에서 이 값을 수주잔고로 잘못 잡으면 크게 과대계상된다.
_Avoid_: 수주잔고와 혼용

## 기납품액 (Delivered Amount)

수주총액 중 **이미 납품·매출로 인식된 금액**. `수주총액 − 기납품액 = 수주잔고`. 검산 게이트의 핵심 항.

## 사업부문 분해 (Segment Breakdown)

다중엔티티/다부문 종목의 [[수주잔고]]를 **사업부문(항공·방산·해양 등) 단위로 나눈 배열**. 각 부문은 1개 이상 법인의 합이며(예: 방산 = 한화에어로 방산 + 한화시스템 방산), 법인별 내역을 함께 보유한다. **부문 합 = 연결 수주잔고**(이 등식이 다중엔티티 자동추출의 검산 게이트). 모회사 본체와 자회사분을 한 화면에서 구분하기 위한 표현.

## 키움 시세 소스 (Kiwoom Market Source)

오너의 키움 개인계좌 자격증명(서버측 단일 키)으로 받는 **KR 시장데이터** 소스. "키움 연동"은 이 한정된 의미다 — 유저별 키움 로그인도, 계좌·주문 연동도 아니다. 경계는 셋: **KR 전용**(키움엔 US 종목이 없어 US는 계속 yfinance), **읽기전용**(시세·차트·수급·랭킹 조회만, 계좌·주문 TR 미사용), **공용 데이터**(유저 무관, 시장 공통). KR 컨센서스/목표가/상세재무는 키움에 없거나 빈약해 기존 소스(FnGuide·Naver)를 유지한다. 정본 경계는 ADR-0009.

**KR 시세의 기본 venue는 통합(SOR `_AL`)** — 현재가·차트를 통합 코드로 받아 KRX+넥스트레이드(NXT)의 합성 BBO 통합호가가 되고, NXT 확장시간(08:00~20:00 KST)까지 포함한다(비-NXT 종목은 통합이 KRX로 자동 폴백). 즉 "KR 시세"는 KRX 단독이 아니라 통합값을 가리킨다(랭킹은 Naver 유지·미채택, 수급은 KRX 기반). 정본은 ADR-0010.
_Avoid_: "키움 연동 = 모든 시세를 키움으로"(US는 불가), "내 계좌 연동"(읽기전용 시세만, 잔고/주문 아님)

## 백업 시세 소스 (KIS / 한국투자증권)

한국투자증권(KIS) REST API로 받는 **읽기전용 백업 시장데이터** 소스. [[키움 시세 소스]]와 같은 "서버측 단일 자격증명·공용 데이터·읽기전용" 성격이지만 둘이 다르다: **(1) 1차가 아니라 백업** — 현재가 조회의 1차 소스(KR=키움, US=yfinance)가 실패할 때만 발동하는 폴백이다(체인 KR=키움→KIS→Naver, US=yfinance→KIS). **(2) KR+US 둘 다 커버** — 키움이 KR 전용인 것과 달리 KIS는 국내·해외주식을 모두 제공해 US 폴백도 된다. 단 US 시세는 기본 15분 지연·주요지수 구성종목 중심이라 "백업"으로만 충분하다(실시간·전체커버는 유료/별도). 주문·계좌 TR은 키움과 동일하게 **연동하지 않는다**(읽기전용). **자격증명 미설정이 안전 기본값** — 서버에 키가 없으면 KIS는 휴면하고 기존 체인(키움/Naver/yfinance)만 동작하며, 키를 주입하면 폴백이 활성화된다. 정본 경계는 ADR-0011.
_Avoid_: "KIS = 1차 시세"(백업이다), "KIS로 계좌·주문 연동"(읽기전용 시세만), "US도 실시간"(기본 15분 지연)

## 공매도 추이 (Short-Sell Trend)

종목별 **일별 공매도 *거래*** 시계열 — 그 날 체결된 공매도 거래량·거래대금과 전체 거래 대비 **공매도 비중(%)**. 키움 ka10014([[키움 시세 소스]]의 읽기전용·KR 전용 경계 안)로 받는다. **공매도 *잔고*(미상환 누적 공매도, KRX가 T+2로 별도 공시)와 다르다** — ka10014는 *거래* 추이지 잔고가 아니므로, 잔고/잔고비중은 응답에 없으면 키움 범위 밖(KRX 등 별도 소스 후속). 리포트 상세 "기술·수급" 하위탭에서 [[수급 추이]] 옆에 per-stock으로 표시.
_Avoid_: 공매도 잔고(미상환 누적분 — 별도 데이터셋이라 ka10014에 없을 수 있음), 대차잔고(차입 잔고 = 금융위 lending 지표로 공매도의 원천이나 별개)

## 공시 피드 (Disclosure Feed)

보유·관심 KR 종목의 **DART 원시 공시 목록**을 자동 수집한 시계열 — 공시 일자·제목(report_nm)·유형(pblntf_ty)·접수번호(rcept_no, DART 뷰어 링크). DART `list.json`(corp_code별)로 받으며 [[수주잔고]]와 같은 DART 연동(corp_code 매핑·`DART_API_KEY`)을 재사용한다. **핵심 유형만** 수집한다 — A(정기·실적)·B(주요사항: 유증·자사주·합병·대규모계약·CB)·C(발행)·D(지분: 대량보유); E·F·I·J(기타·외감·거래소·공정위) 노이즈는 제외. KR 전용·읽기전용. 리포트 상세 "최신 공시" 섹션 + 일일 다이제스트(=일일 텔레그램 전달)에 노출.
_Avoid_: **`recent_disclosures`와 혼동 금지** — 그건 외부 Cowork가 쓰는 **애널리스트 코멘터리(분석 텍스트)**이고, 공시 피드는 **자동 수집한 원시 공시 목록**이다. 둘은 별도 저장소(피드는 `stock_disclosures` 테이블, 코멘터리는 `tickers.recent_disclosures`)이며 공시 피드는 코멘터리를 덮지 않는다.

## 뉴스 (News)

보유·관심/랭킹 종목의 **언론 기사 헤드라인**(제목·링크·출처·시각) — `scraper.get_news`가 시장별 라이브 스크레이프(KR=Naver, US=yfinance). 링크 기준 중복제거·최신순. **전용 저장 테이블 없음** — 리포트 상세는 요청 시 **라이브 fetch**(스냅샷 `data.news`는 폴백), 다이제스트는 아침 리포트가 박제한 스냅샷 news를 **읽어** 노출(배치 스크레이프 없음).
_Avoid_: **[[공시 피드]](DART 원시 공시)·`recent_disclosures`(Cowork 애널리스트 코멘터리)와 혼동 금지** — 셋 다 리포트 상세 "최근 공시 & 뉴스" 근처에 병치되지만 출처·저장소가 전부 다르다: 뉴스=언론 기사(스크레이프·무저장), 공시 피드=DART 규제 공시(`stock_disclosures`), recent_disclosures=AI 요약 텍스트(`tickers`).

## 매크로 신호 (Macro Signals)

경기·신용·유동성을 가늠하는 **FRED 거시 시계열 + 그 해석 신호** — 장단기 금리차(T10Y2Y; <0=수익률곡선 역전=침체 경고), 하이일드 스프레드(BAMLH0A0HYM2; 급확대=신용 스트레스), M2(유동성), 기준금리(DFF). 기존 [[경제지표]](CPI·실업률)와 같은 FRED `_fetch_series` 패턴·`market_cache` 저장을 재사용하되, 금리차·HY는 **일간 갱신**이라 별도 일배치(`macro_signals_fetch`)다. 출처국 미국이라 시장 분류는 **해외**(FRED=US, [[배치 시장 분류]] 일관). MarketHub 시장지표 탭에 노출.
_Avoid_: **매크로 *상관*(Macro Correlation)과 혼동 금지** — 그건 포트폴리오 분석탭 MacroTab의 **보유 종목–매크로 자산(TLT/UUP/USO/VIX) 90일 상관관계**(`analysis_service.MACRO_TICKERS`)이고, 매크로 *신호*는 **FRED 거시지표의 침체/신용 신호 시계열**이다. "매크로" 한 단어에 두 다른 기능이 걸려 있다.

## 시장지수 밸류에이션 (Market-Index Valuation)

시장 *전체*가 역사적으로 비싼지 가늠하는 **지수 단위 멀티플** — 현재는 US S&P500 Shiller CAPE(경기조정 PER: 최근 10년 실질이익 평균 대비)의 현재값+역사 통계(평균/중앙/최소/최대)뿐이다. 함께 묶이는 **시장지수 레벨**(KOSPI·KOSDAQ·S&P500 일간 레벨·등락)은 포트폴리오의 벤치마크 데이터다. 둘 다 [[매크로 신호]]·fx처럼 MarketHub 시장지표 탭에 노출.
_Avoid_: **per-종목 밸류에이션(PER/PBR/목표가)과 혼동 금지** — 그건 *개별종목*이 싼지 비싼지고, 시장지수 밸류에이션은 *시장 전체*의 과열도다. [[매크로 신호]](FRED 거시 침체/신용 신호)와도 다른 축. 출처 주의: **FRED엔 주식 CAPE 시리즈가 없다**(FRED "Case-Shiller"는 *주택가격* 지수) — `multpl.com` 크롤이 무료 출처다.

## 시장 센티먼트 지수 (Fear & Greed)

시장 전체의 투자심리를 **0~100 단일 수치**로 나타내는 CNN 공포·탐욕 지수(0=극단적 공포, 100=극단적 탐욕) + rating(공포/중립/탐욕). **US 시장 대상**(KR 무료 F&G 소스 부재 — [[시장지수 밸류에이션]]의 S&P CAPE가 US 전용인 것과 같은 결). CNN **비공식** 엔드포인트라 전체 브라우저 헤더(UA+Accept+Origin+Referer+sec-ch-ua)가 있어야 응답하고(불완전하면 418), 언제든 막힐 수 있어 **실패 시 직전 저장값으로 graceful**. [[매크로 신호]]·VIX처럼 시장지표 탭에 노출.
_Avoid_: **VIX(변동성지수)와 혼동 금지** — VIX는 옵션 내재변동성 단일 지표(프론트가 관례적으로 "공포지수"로 라벨)이고, Fear&Greed는 7개 하위지표(모멘텀·주가강도·주가폭·풋콜·변동성·안전자산·정크본드 수요) **합성** 0~100 심리지수다. [[매크로 신호]](FRED 거시 침체/신용 신호)와도 다른 축(그건 거시지표, 이건 시장 투자심리).

## 다음날 코스피 신호 (Next-day KOSPI Signal)

전 거래일 KR 장마감 후의 **오버나잇 해외 시장 움직임**(S&P500·나스닥 등락 + USD/KRW 변화)을 합성해 **다음 거래일 코스피의 방향**을 강세/중립/약세로 예측하는 지표. 매 거래일 개장 전(08:30 KST) 신호를 시점 박제하고, 그날 코스피 실제 결과(시가 갭·종가 등락)와 대조해 **적중률을 누적**한다(라이브 체크). **적중의 의미(task#203 확정)**: 방향성(강세/약세) 적중 = 종가 등락의 **부호 일치**(크기 무관 — "방향" 신호이므로), 중립 적중 = 종가 등락이 밴드 이내(별도 집계). 휴장일에 만들어진 신호는 예측 대상이 없으므로 무효(시리즈에서 제거). 코스피 *선물*이 반영하는 것이 결국 미국 오버나잇+환율이라, 이 프록시로 방향을 예측한다(실제 선물 데이터는 [[코스피200 선물]]로 별도 표시). **실제 (야간)선물 오버나잇을 이 신호의 드라이버로 편입하는 안은 검토 후 기각** — KRX 야간선물(18:00~06:00)이 KIS 시세 TR에 노출되지 않아(2026-07-08 야간세션 중 라이브 프로브로 확인: `FHMIF10000000`이 정규장 종가만 반환) 08:30 배치 시점 선물가는 어제 종가라 오버나잇 신호가 0이고, 그 오버나잇도 대부분 이미 쓰는 미국 프록시와 겹친다. 소스는 US지수+환율이나 대상이 코스피라 [[배치 시장 분류]]는 국내(KR). MarketHub 시장지표 탭에 노출.
_Avoid_: **[[매크로 신호]](FRED 거시 절대신호)·매크로 상관(보유종목–매크로 자산 상관)과 혼동 금지** — 셋 다 "신호/매크로"지만 이건 *다음날 코스피 방향* 예측이다. 실제 [[코스피200 선물]](KIS 선물 일봉 차트)과도 구분 — 이건 선물이 아니라 미국 오버나잇 프록시다.

## 코스피200 선물 (KOSPI200 Futures)

KRX 상장 KOSPI200 지수선물의 **최근월물 일봉 시계열 + 현재 베이시스**를 시장지표 탭에 표시하는 정보성 지표. [[백업 시세 소스]](KIS)의 국내선물 시세 TR로 받으며(경계 확장 ADR-0022), 최근월물 코드는 공식(`"A01"+연%10+월`, 분기월)으로 계산하고 만기는 응답 `futs_last_tr_date`로 롤오버한다. **베이시스**(선물−현물 = 콘탱고/백워데이션)가 선물-고유 인사이트다. KR 유일 소스가 KIS라 키 미설정 시 휴면.
_Avoid_: **[[다음날 코스피 신호]]와 혼동 금지** — 그건 선물이 아니라 *미국 오버나잇 프록시*로 다음날 방향을 예측하는 것이고, 이건 *실제 KOSPI200 선물*의 일봉/베이시스 표시다(정보성, 예측 아님). 최근월물은 **연속선물이 아니다** — 분기마다 코드가 바뀌므로 증분 병합/스티칭이 계약을 뒤섞는다(요청마다 전체 윈도우 fetch).

## 신규 창업 신청 (Business Applications)

미국 인구통계국(Census) **사업체 형성 통계(BFS)**가 월별로 집계하는 **신규 사업자 등록 신청 건수**. 부문은 NAICS 2자리로 갈리며 우리가 표시하는 것은 **정보(51)**와 **전문·과학·기술 서비스(54)** 두 부문이다(FRED `BABANAICS51SAUS`·`BABANAICS54SAUS`, 계절조정). "AI 에이전트가 1인 창업을 가속하는가"를 읽는 선행지표로 쓴다. 출처국 미국이라 [[배치 시장 분류]]는 **해외**. MarketHub 시장지표 탭에 노출.
_Avoid_: **실제 창업(Business Formations)과 혼동 금지** — *신청*은 등록 서류를 낸 건수이고 *창업*은 그중 실제로 사업을 개시한 것(FRED `BFPBF4Q…`)이라 항상 신청 > 창업이다. **고성향 신청(High-Propensity, `BAHBA…`)** 도 별개 지표로, 고용 창출 확률이 높은 신청만 골라낸 부분집합이다(정보 부문에서 전체의 약 1/7). 셋을 같은 축에 올리지 말 것.

## 고용 조사 격차 (Employment Survey Divergence)

미국 고용을 **서로 다른 두 조사**가 다르게 집계해 생기는 벌어짐 — **기업조사(Establishment, FRED `PAYEMS`)**는 사업체 급여명부상의 *일자리* 수이고, **가계조사(Household, FRED `CE16OV`)**는 가구에 물어 세는 *취업자* 수다. 비농업 고용(NFP) 헤드라인은 기업조사이므로, 가계조사가 꺾이는데 기업조사가 오르면 "NFP를 어디까지 믿을 것인가"라는 질문이 생긴다. MarketHub 시장지표 탭에 노출.
_Avoid_: **두 값의 절대 수준 차를 "격차"로 읽지 말 것** — 정의가 달라(가계=자영업·농업 포함, 기업=재직 복수면 중복집계) 수준 차이는 상시 존재하며 그 자체로 이상 신호가 아니다. 의미가 있는 것은 **추이의 발산**(같은 기간 증감 부호가 갈리는 것)이다. 그래서 차트는 두 선을 겹쳐 보이되 판정 근거는 **12개월 증감 수치**로 따로 제시한다. [[경제지표]]의 실업률(가계조사 파생 비율)과도 다른 축이다.

## 절사평균 물가 (Trimmed-Mean Inflation)

바스켓에서 **가장 크게 오른·내린 품목을 잘라낸 뒤** 평균한 물가 상승률. 일시적 극단값(에너지 급등, 특정 품목 세일)에 덜 흔들려 **기조적 인플레이션**을 보는 데 쓴다. 두 기관이 서로 다른 바스켓으로 발행한다 — **Dallas Fed 절사평균(PCE 기반, `PCETRIM12M159SFRBDAL`)**, **Cleveland Fed 16% 절사평균(CPI 기반, `TRMMEANCPIM159SFRBCLE`)**. 헤드라인 PCE(`PCEPI`)·코어 PCE(`PCEPILFE`)와 나란히 놓아 "코어가 높은 것이 광범위한 물가 압력인가, 소수 품목 탓인가"를 가른다. 출처국 미국이라 [[배치 시장 분류]]는 **해외**.
_Avoid_: **코어(Core)와 혼동 금지** — 코어는 *식품·에너지라는 정해진 범주*를 항상 빼는 것이고, 절사평균은 *그 달에 극단이었던 품목*을 그때그때 빼는 것이다. 그래서 코어가 오르는데 절사평균이 안 오르면 "특정 품목 문제"라는 해석이 나온다. 또 **단위 혼동 주의** — 절사평균 2종은 FRED가 이미 전년동월비(%)로 발행하지만 PCE·코어 PCE는 *지수*라 YoY를 직접 계산해야 한다. [[매크로 신호]](금리차·신용스프레드)와도 다른 축이다.

## 데이터 소스 (Data Source)

한 [[배치]]가 데이터를 **읽어오는 외부 출처(fetch origin)** — 키움·KIS·yfinance·Naver·FnGuide·FRED·KOFIA·DART·관세청·dataroma 등. `batch_registry`의 `source` 필드(list)로 갖고 [[배치 현황]] 카드에 표시한다. **[[사용처]](Usage)와 반대 방향**이다 — 사용처는 그 배치가 *만든* 데이터를 **소비하는 UI 위치**, 데이터 소스는 그 배치가 *읽어오는* **외부 API**다. 정적 메타데이터라 배치의 fetch 소스가 바뀌면 `source`도 함께 갱신해야 한다(CLAUDE.md 규칙·DoD).
_Avoid_: [[사용처]](소비 UI)와 혼동 — 방향이 정반대다(소스=입력 출처, 사용처=출력 소비처).

## 단계 라벨 (Stage Label)

리포트 "장기 성장 계획"의 각 **이니셔티브가 어느 진행 단계에 있는지 보여주는 짧은 문구**(칩으로 표시). 이 문구는 **종목 도메인에 맞게 작성자(외부 Cowork)가 기입하는 자유문구**다 — 제약은 "임상3상", 반도체는 "양산 램프업", SaaS는 "정식 출시"처럼 산업마다 다르다. **`status`(launched/phase2/phase3/announced/completed)와 구분**한다: `status`는 칩 **색상**을 정하는 거친 진행도 신호일 뿐 표시 단어가 아니다. 산업별 마일스톤 어휘는 무한하므로 고정 enum이나 섹터 추론으로는 정확히 못 담고, 맥락을 아는 작성자가 단어를 정해야 정확하다(고정 enum/섹터 분기는 반례를 못 막음 — 제약사의 *비*임상 이니셔티브를 "임상"으로 오표기 등).
_Avoid_: **`status`를 단계 라벨로 혼동 금지** — 과거엔 프론트가 `phase3`→"임상3상"으로 하드코딩해 모든 종목(예: 삼성전자)에 임상 라벨이 잘못 붙었다. 이제 라벨은 작성자 기입 문구가 정본이고, status는 색상용 폴백이다.

## 수급 스코어 (Supply/Demand Score)

보유·관심 KR 종목별로 **종목 단위 수급 데이터를 합성해 매긴 우호/중립/경계 3단계 밴드** + 그 근거 플래그 묶음. 입력은 **per-종목 데이터 둘뿐** — [[공매도 추이]](`market_short_sell`: 공매도 비중·잔량)와 외국인/기관 수급(`market_investor_trend`: 외인+기관 순매수·외인보유율)이다. **신용잔고·대차잔고는 시장 전체 집계라 종목 점수에서 제외**하고, Market 허브의 시장 백드롭으로만 둔다(입자 불일치 — 시장 단위 값을 개별 종목 점수에 투영하면 변별력이 사라지고 오도된다). 점수 형태는 **단일 수치가 아니라 플래그→밴드**다: '공매도 비중 급증'·'외인·기관 동반 순매도' 같은 근거 보이는 플래그를 최근 5거래일 vs 직전 20거래일 *상대* 비교로 켜고(가중치 없음), 경계 플래그 개수로 밴드를 판정한다(균형 규칙: 경계 플래그 ≥2 또는 강한 단일 → 경계). `supply_score_fetch` 일배치가 사전계산해 `stock_supply_score`에 저장하고, 대시보드 배지·리포트 상세 기술·수급 탭은 **저장값만 읽는다**(요청경로 계산 0). KR 전용 — US 종목·결측은 '해당 없음'. 정본 경계는 ADR-0014.
_Avoid_: **[[매크로 신호]]·시장 수급지표(신용/대차)와 혼동 금지** — 그건 시장 전체 집계 시계열이고, 수급 스코어는 *종목별* per-stock 신호다. 단일 0~100 점수 아님(플래그+밴드). [[데이터 소스]] 표기상 출처는 키움(per-stock 시세 파생)이다.

## 지분공시 신호 (Insider / Major-Holder Trading Signal)

보유·관심 KR 종목의 **내부자·대량보유자 지분 변동**을 DART 상세 공시에서 구조화해 뽑은 신호 — 누가(보고자·직위), 몇 주를(증감주식수 +/−), 거래 후 보유비율(%)을, 언제. 두 출처: **임원·주요주주 소유상황보고**(`elestock.json` — 내부자 1주 단위 매매)와 **주식등의 대량보유상황보고(5%룰)**(`majorstock.json` — 큰손 진입/이탈·행동주의). DART 연동(corp_code 매핑·`DART_API_KEY`)과 [[공시 피드]]의 수집·배치 패턴을 재사용한다. **per-종목 순매수/순매도 신호**는 최근 N일 증감주식수 합으로 파생한다(저장 line item에서 SQL 집계, 요청경로 라이브 호출 0). KR 전용·읽기전용. 리포트 상세 '내부자·5% 지분변동' 섹션 + 종목 신호 배지 + 일일 다이제스트에 노출.
_Avoid_: **[[공시 피드]]와 혼동 금지** — 공시 피드는 DART `list.json`의 **원시 공시 제목 목록**(D 지분 유형을 포함하나 제목·접수번호만)이고, 지분공시 신호는 `elestock`/`majorstock` **상세를 파싱한 구조화 거래 line item + 순매수 파생**이다(한 층 더 깊다). **[[수급 스코어]]와도 다름** — 수급 스코어는 외국인/기관·공매도 *거래흐름* 합성 밴드, 지분공시 신호는 *내부자·대량보유자가 보고한 지분 변동*이다. 신호 배지 색은 KR 가격 토큰(`success`/`danger`) 금지·전용색([[수급 스코어]] SupplyBadge 규약과 동일).

## 구루 보유 (Guru Holding)

**dataroma가 집계하는 미국 13F 기관 운용역(구루)의 신고 보유 종목**. 주간 크롤(`guru_crawl`) 1회가 전 매니저를 훑어 전역 단일 행에 박제하며, 매니저 단위 데이터는 운용사·포트폴리오 규모·보유 종목수·종목별 비중이다. **구루 비중**은 그 매니저의 13F 포트폴리오 가치 대비 해당 종목의 비중(%)으로, dataroma 신고 기준 값을 그대로 쓴다. 저장은 **두 층**이다: **상위 10종목(`top10`)** = 화면 공용 요약층으로 리포트 상세의 보유 구루 드릴다운·[[추천]] 카드의 구루 보유 수·인기순(top10에 담은 매니저 수)·가중치(Σ 1/순위) 통계가 전부 이 층만 읽고, **전 종목(`holdings`)** = 매니저 상세 화면과 **서버측 [[구루 자산 배분]] 집계**가 읽는 층으로, 목록 API 응답에는 싣지 않는다(공용 소비처 페이로드 보호 — [[구루 활동]]의 전량매도 목록도 같은 이유로 상세 전용이다. 집계는 서버가 이 층을 훑어 결과만 내보내므로 이 원칙과 어긋나지 않는다). 상위 10종목이 덮는 비중은 매니저마다 19~100%로 크게 갈리며, 그 커버리지 자체가 집중도 신호다. **신고 분기**(`period`·`portfolio_date`)는 매니저마다 다를 수 있다 — 신고 시점이 갈리므로 전역 상수로 취급하면 안 된다. US 전용.
_Avoid_: **"현재 포지션"으로 읽지 말 것** — 13F는 분기 단위 지연 신고라 크롤 시점의 실제 포지션이 아니다. **[[노출·집중도]]와 혼동 금지** — 그건 *내* 포트폴리오 안의 종목 비중이고, 구루 비중은 *남의 펀드* 안의 비중이다. "구루를 KR에"(dataroma는 US 13F 전용). **[[구루 활동]]과 혼동 금지** — 보유는 *지금 얼마나 갖고 있나*(스냅샷), 활동은 *직전 분기 대비 얼마나 움직였나*(델타)다.

## 구루 활동 (Guru Activity)

**한 [[구루 보유]] 매니저가 직전 분기 대비 각 종목을 얼마나 움직였는지**. dataroma가 신고 기준으로 이미 제공하므로 우리가 스냅샷 이력을 쌓아 비교하지 않는다. 종류는 **신규매수·추가매수·축소·전량매도** 넷이고, 변동이 없는 종목은 활동이 *없다*(빈 값이 아니라 부재). 값은 두 가지 축으로 읽는다:

- **주식수 증감률** — 운용역이 얼마나 세게 움직였나(예: 주식수 3배 = 추가 203.99%). 전 보유 종목에 대해 완전하다.
- **비중 임팩트** — 그 거래가 포트폴리오 구성을 얼마나 바꿨나. **엄밀히는 `이전비중 → 현재비중` 차이가 아니라 `현재비중 × 증감주식수/현재주식수`**(= 이번 분기 거래분이 현재 포트폴리오에서 차지하는 비중)다. 두 축은 크게 어긋날 수 있다 — 주식수를 3배로 늘려도 비중 임팩트는 4%p 수준일 수 있고, 반대로 신규매수 하나가 15%p를 차지할 수도 있다.

**전량매도**는 보유 목록에서 사라지므로 보유 층에 얹을 수 없고 **별도 목록**으로 둔다(직전 비중을 함께 갖는다). US 전용이고 [[구루 보유]]와 같은 주간 크롤이 만든다.

_Avoid_: **"비중 임팩트를 빼서 이전 분기 비중을 역산"**(위 정의상 틀린다). **"축소 = 전량매도"** 금지 — 부분 축소와 전량매도는 별개 종류이고 후자만 별도 목록에 있다. **"활동 = 매매 시점 신호"**로 읽지 말 것 — [[구루 보유]]와 같은 분기 지연 신고라 이미 지난 움직임이다. 표시 색에 **KR 가격 토큰(up/down) 금지** — 매매 방향이므로 [[수급 스코어]]·지분공시 신호와 같은 전용색(매수=초록·매도=주황) 규약을 따른다.

## 구루 자산 배분 (Guru Allocation)

**여러 [[구루 보유]] 매니저를 하나의 자금 풀로 보고, 그 돈이 종목별로 얼마씩 들어가 있는지**. 매니저 한 명 안의 순위가 아니라 **합산 관점**이라는 점이 [[구루 보유]]의 매니저별 비중과 갈리는 지점이다. 세 값으로 읽는다:

- **합산 대상 구루** — 자금 풀에 넣을 매니저 집합. 전체일 수도 있고, **포트폴리오 규모(13F 신고 자산) 상위 N명**으로 좁힐 수도 있다. 좁히면 큰 자금의 배분만 남고 소형 펀드의 꼬리 보유가 빠지지만, 대신 최상위 몇 명의 장부 색이 결과를 지배한다(상위 10명으로 좁히면 1위 매니저 한 명이 그 풀 자산의 1/3을 차지한다). 좁힐수록 [[구루 보유]]의 신고 분기 혼재도 줄어든다.
- **구루 투자금** — 한 종목에 합산 대상 구루가 넣은 **신고 금액의 합**. 정본은 dataroma가 종목 행에 주는 신고 금액이고, 그 값이 없을 때만 `매니저 비중 % × 매니저 포트폴리오 가치`로 추정한다(상위권 오차는 0.1% 수준이나 비중이 0.1% 미만인 꼬리 구간에서는 크게 벌어지므로 추정은 어디까지나 폴백이다).
- **구루 자산 비중** — 그 투자금이 **합산 대상 구루의 자산 총합**에서 차지하는 몫(%). 분모는 특정 매니저가 아니라 그 풀 전체이므로, 전 종목의 비중을 더하면 100%가 된다. **합산 대상을 바꾸면 분모가 바뀌어 같은 종목의 비중도 달라진다** — 비중은 풀에 상대적인 값이고 절대 상수가 아니다(같은 종목이 상위 10명 풀에서 7.7%, 전체 풀에서 6.3%).

**보유 구루 수**도 합산 대상 안에서 센 값이다(전체 매니저 기준이 아니다). 집계 단위는 **티커**다 — 13F가 티커 단위 신고이므로 듀얼클래스(GOOGL/GOOG, BRK.A/BRK.B)는 **합치지 않고 별개 종목으로 센다**. 집계 대상은 [[구루 보유]]의 **전 종목 층**이며(상위 10종목 층이 아니다), 매니저마다 [[구루 보유]]의 신고 분기가 다를 수 있으므로 합산 결과는 **여러 분기가 섞인 값**이다.

**같은 개념의 이름이 셋이다** — 정본은 **합산 대상 구루**, 화면에서 그것을 고르는 선택 필은 **스코프**(10명·20명·50명·전체), 그 선택이 확정한 매니저 집합은 **코호트**다. 스코프는 *고르는 손잡이*이고 코호트는 *그 결과 집합*이므로 같은 말이 아니다 — 스코프를 바꾸면 코호트가 바뀌고, 그에 따라 구루 자산 비중의 분모도 바뀐다.

_Avoid_: **"보유 구루 수"와 혼동 금지** — 몇 명이 들고 있나(인기)와 얼마가 들어가 있나(자산 배분)는 서로 다른 신호이고 순위가 실제로 뒤집힌다(AAPL 24명 $67.3B ↔ GOOGL 40명 $32.8B). **[[구루 보유]]의 매니저별 비중과 혼동 금지** — 그건 *한 펀드 안*에서의 몫이고, 구루 자산 비중은 *합산 대상 구루의 자금 풀* 안에서의 몫이다. **[[노출·집중도]]와도 다르다**(그건 *내* 포트폴리오). "투자금 = 현재 평가액"으로 읽지 말 것 — 분기 지연 신고 시점의 금액이다. **합산 대상 구루를 "표시 줄 수"로 읽지 말 것** — 상위 N명은 *몇 명의 돈을 합치나*이지 *몇 종목을 보여주나*가 아니다(상위 10명만 합쳐도 종목은 수백 개다). **좁힌 결과를 "전체 구루의 판단"으로 일반화하지 말 것** — 상위 소수의 장부가 지배한다.

## 명부 (Roster)

**dataroma가 "현재 이 사람들이 구루다"라고 게시하는 운용역 목록** — [[구루 보유]] 크롤이 매 회차 처음 읽는 것이고, 각 매니저의 보유 상세를 받아오기 전에 *누구를 훑을지*를 정한다. 명부의 존재 이유는 목록 그 자체가 아니라 **판단 축**이다: 어떤 매니저가 이번 크롤 결과에 없을 때, 그것이 **실패해서 빠진 것**(보유 페이지 요청이 죽음 → 직전값으로 백필해야 한다)인지 **은퇴해서 사라진 것**(더 이상 구루가 아님 → 저장에서 지워야 한다)인지를 가르는 **유일한 단서**다. 명부가 없으면 그 둘을 구별할 수 없어 백필도 드롭도 할 수 없다.

그래서 명부는 **신뢰성 자체가 load-bearing**이다 — 명부가 실제보다 짧게 읽히면 살아 있는 매니저가 "은퇴"로 오분류돼 저장에서 빠진다. **명부의 열화는 두 종류이고 성질이 다르다**: **전량 실패**(0건)는 결과가 비므로 저장 생략으로 자연히 막히지만, **부분 열화**(일부만 읽힘)는 예외도 빈 결과도 아니어서 정상적인 짧은 명부와 구별되지 않는다. 후자를 가르는 건 **직전 저장분 대비 규모**뿐이고, 그 판정이 임계 미만이면 그 회차는 **드롭을 보류**한다(은퇴 반영이 한 회차 늦어지는 비용 < 살아 있는 매니저를 지우는 비용).

_Avoid_: **"명부 = 크롤 결과"로 읽지 말 것** — 명부는 *훑을 대상*이고 결과는 *성공한 것*이라, 결과가 명부보다 짧은 건 정상이다(그 차이가 백필 대상이다). **"예외가 안 났으니 명부는 온전하다"** 금지 — HTTP 200 + 마크업 변경이면 선택자가 덜 매칭돼 **짧은 명부가 조용히 반환**된다. **"드롭 = 영구 삭제"로 읽지 말 것** — 저장은 외부 소스의 캐시라 명부가 회복된 다음 크롤이 복원한다(피해는 그때까지의 일시 소실이다). **[[구루 보유]]의 매니저 목록과 혼동 금지** — 그건 *저장된 것*이고 명부는 *상류가 지금 게시하는 것*이다.

## 추천 (Recommendation)

보유·관심 여부와 무관하게 **"지금 살펴볼 종목"을 합성 점수로 골라 제시**하는 기능. 세 산출이 한 화면(Research 허브 '추천' 탭)에 모인다:
- **발굴(Discovery)** — 내가 아직 보유·관심에 안 담은 종목 중 점수 상위. [[랭킹]]·관심종목과 다르다: 랭킹은 시장 전체 *거래* 상위(중립적 사실)이고, 발굴은 *내가 안 가진* 종목을 *합성 점수*로 골라준 것이다.
- **관심 재정렬** — 내 관심종목을 추천 점수순으로 정렬(무엇을 먼저 볼지).
- **보유 액션** — 내 보유종목에 추매/익절/홀딩 신호(추천 점수 + 내 포지션 맥락).

점수는 **멀티팩터 합성 0~100**(밸류=목표가 상승여력·모멘텀·스마트머니)이고, "왜 추천"은 [[수급 스코어]]·[[지분공시 신호]]처럼 **정량 플래그**로 보인다(백엔드 LLM 0). 세 섹션은 저장된 *글로벌* 점수를 요청 시 그 유저의 보유/관심으로 partition한 것이다(점수는 종목 공유, 섹션은 per-user). 정본 경계는 ADR-0015·0016(결측군 합성은 0016이 중립 채움으로 대체).
_Avoid_: "[[랭킹]] = 추천"(랭킹은 거래 상위 *사실*, 추천은 점수 *선별*), "발굴이 AI가 쓴 분석"(근거는 정량 플래그; AI 내러티브는 [[딥다이브]]로 별도·비동기), "[[수급 스코어]] = 추천"(수급은 *한 축*의 종목 밴드, 추천은 *여러 축 합성* 선별 — 수급 스코어가 추천의 한 입력일 수 있다).

## 발굴 유니버스 (Discovery Universe)

[[추천]] 점수를 매기는 **후보 종목 집합**. 최종 목표는 전체 시장(~2700 KR + 503 US)이나 **점진 확장**한다 — v1은 KR 시총 상위 ~200 + US S&P500 + 전 유저 추적종목(+US 구루 보유). 비용 통제를 위해 **2단 깔때기**로 좁힌다: 싼 신호로 후보를 거른 뒤, 후보에만 비싼 *리치* 신호(OHLC 모멘텀·컨센서스·KR 수급/지분공시)를 붙인다. 후보 선별은 **KR만 시총 랭킹**(시총 상위 N — 성장 다이얼)이고 **US는 S&P500 전량 + 구루 보유**(S&P500 자체가 시총 큐레이션 — US 개별 시총 데이터는 없다), **추적종목은 무조건 후보 통과**다(ADR-0021). 구루 신호는 **US 전용**(dataroma 13F). 항상 전 유저 추적종목을 포함해 [[추천]]의 관심 재정렬·보유 액션이 점수를 잃지 않게 한다.
_Avoid_: "리치 신호를 전 종목에"(비용상 불가 — 깔때기 후보만 enrich), "시총 랭킹이 US에도 적용"(US 행엔 시총이 없어 랭킹이 무의미했고 그게 커버리지 붕괴의 근본원인 — ADR-0021), "구루를 KR에"(US 전용), "유니버스 = 추적종목"(추적종목은 부분집합 — 발굴은 미추적까지), "구루 유니버스 = 우량주만"(US 13F엔 저유동성 OTC/외국 티커가 섞여 있고, 거래량 급증 모멘텀과 결합하면 발굴 상위로 새므로 — CFRHF·HKHHF 등 라이브 UAT 확인 — 저유동성 종목은 점수·저장은 유지하되 발굴(discovery)에서만 제외된다(관심/보유 섹션엔 직접 담으면 그대로 노출), task#68).

## 딥다이브 (Deep-dive)

[[추천]] 종목의 **AI 분석을 요청**하는 동작. 백엔드엔 LLM이 없고 분석 텍스트는 외부 Cowork가 enrich API로 쓰므로, 딥다이브 = **그 종목을 관심종목에 추가**하는 위임이다 → 기존 "추적 시 Cowork 분석" 흐름이 다음 Cowork run에 *비동기로* 채운다(즉시 생성 아님). 후보마다 AI를 돌리지 않아 Cowork(외부 LLM) 비용이 사용자 행동에만 든다.
_Avoid_: "딥다이브 = 즉시 AI 리포트 생성"(비동기 — 백엔드가 Cowork를 못 돌림), "추천이 분석 큐를 신설"(관심추가로 위임 — 큐 없음).

## 사용자 목표가·손절가 (User Target / Stop)

사용자가 보유 종목에 **직접 설정**하는 익절 목표가와 손절 기준가. **애널리스트 컨센서스 목표가**([[추천]]·리포트가 쓰는 `daily_consensus_mart`/스냅샷 `target_mean` 등, 외부 증권사 집계)와는 **다른 축**이다 — 컨센서스는 시장의 예측이고, 사용자 목표가/손절가는 그 유저의 매매 계획이다. `user_stocks`에 per-유저로 저장하며(종목 공유 마스터 `tickers`·스냅샷 아님), 종목 native 통화(KR=원·US=달러, `avg_cost`와 동일 축). 대시보드 카드에 현재가 대비 거리(%)로 표시된다.
_Avoid_: "목표가 = 컨센서스 목표가"(별개 — 사용자 설정 vs 애널리스트 집계), "손절가를 컨센서스/시스템이 채운다"(사용자만 설정), "target_price를 tickers·스냅샷에 저장"(user_stocks per-유저).

## 노출·집중도 (Exposure / Concentration)

보유 포트폴리오가 **특정 섹터·통화(시장)·단일종목에 얼마나 쏠려 있는지**를 비중으로 본 것. 세 축이다: **통화 노출**(KR/US 시장별 비중), **섹터 노출**(섹터별 비중), **단일종목 집중도**(종목별 비중 내림차순 + top-N 집중비율 + 임계 초과 경고). 여기에 **포트폴리오 베타**(베타가중 노출 = Σ(비중×베타) = 포트 시장민감도)를 정보성 지표로 더한다 — 베타를 아는 보유만의 가중평균(가중치 재정규화)이라 **커버리지%**를 함께 표기하고, per-종목 beta 결측을 대비해 배치가 사전계산해 둔 저장값(`stock_beta`)만 읽는다. 비중 기준은 [[사용자 목표가·손절가]]가 아니라 리밸런싱과 같은 **전체-포트 KRW 환산 분모**다. **보유(holding)만** 대상 — 관심종목은 아직 담지 않은 자산이라 제외한다. 섹터를 모르는 종목(리포트 미생성 US·업종 역인덱스 배치 전 KR)은 `기타`로, FX 환산 불가한 US 종목은 집계에서 제외하고 별도 표기한다. Portfolio 분석 하위탭 '노출'에 표시.
_Avoid_: **종목별 리스크 서술(`tickers.risks`, Cowork 내러티브)과 혼동 금지** — 그건 한 종목의 정성 리스크 텍스트고, 노출·집중도는 *포트폴리오 전체*의 쏠림을 정량 비중으로 본 것이다. [[수급 스코어]](종목 수급 밴드)·[[매크로 신호]](시장 거시)와도 다른 축이다. 경고 배지 색은 KR 가격 토큰(`success`=빨강/`danger`=파랑) 금지·전용색([[수급 스코어]] SupplyBadge 규약과 동일).

## 거래소 코드 (Exchange Code)

KR 종목이 어느 거래소 소속인지를 가리키는 **앱 내부 정본 코드**: `KS`=KOSPI, `KQ`=KOSDAQ, `''`(빈 문자열)=비-KR(US 등). 종목 저장(user_stocks·tickers)·[[랭킹]]·[[추천]] 응답·MarketBadge 표시·yfinance 폴백 심볼(`.KS`/`.KQ`)이 **이 코드 하나로** 시장 세분을 표현한다. Naver marketValue API의 `stockExchangeType.code`가 이미 `KS`/`KQ`를 그대로 주므로 별도 변환이 없고, Naver 검색 API는 `typeCode`(KOSPI/KOSDAQ/ETF)를 `KS`/`KQ`로 매핑한다([[키움 시세 소스]]가 아니라 Naver가 출처). [[딥다이브]](관심추가)·[[랭킹]]에서 종목을 watchlist에 담을 때 이 코드가 정확해야 KOSDAQ이 KOSPI로 오표시되거나 yfinance 폴백이 `.KS`로 틀리지 않는다.
_Avoid_: "KS = 한국 전체"(KS=KOSPI 한정 — KOSDAQ은 KQ), "exchange는 표시용일 뿐"(시세 주경로는 6자리라 무영향이나 yfinance 폴백 심볼엔 영향 — `wrong < missing`), "비-KR도 코드를 채운다"(US는 빈 문자열).

## 배당 스케줄 (Dividend Schedule)

보유·관심 종목의 **다가오는 배당 일정 타임라인**: 종목별 배당락일·(US)지급일·주당배당액·(보유)예상 수령액을 날짜순으로 본 것. 리서치 허브 '배당' 탭에 목록으로 표시한다. 데이터는 [[배치]](`dividend_fetch`)가 종목별 yfinance `t.dividends` 이력에서 사전계산해 `stock_dividend_schedule`에 저장하고, 뷰는 저장값만 read한다(요청경로 라이브 fetch 금지).
_Avoid_: **대시보드의 연 예상배당(`total_expected_annual_income_krw`, [[배당]] 연 DPS 기반)과 혼동 금지** — 그건 *1년 합계 금액*이고, 배당 스케줄은 *언제 얼마가 들어오는지의 시점 타임라인*이다. 캘린더의 배당락 이벤트와도 다르다(캘린더는 exact-only·단일 이벤트, [[배당 예상]] 참조).

## 배당 예상 (Dividend Projection)

[[배당 스케줄]]에서 미래 배당락일을 **이력의 배당 주기(분기/반기/연)로 투영한 추정 이벤트**. yfinance는 미래 배당일을 신뢰성 있게 주지 않으므로(특히 KR — `t.calendar` 값이 과거인 경우 다수), 이력 기반 투영이 forward 커버리지의 유일한 수단이다. '**예상**' 라벨로 명시 표시하며 예상금액=직전 실금액. US는 `t.calendar`로 최근접 건을 '**확정**'으로 보강한다. 단 **US 확정은 종목별 `t.calendar` 신선도에 의존** — 미래 ex-date가 신선한 종목만 확정(예: MSFT), stale(과거값)이면 KR과 동일하게 예상 폴백(예: AAPL·KO). 즉 '확정' 부재는 버그가 아니라 그 종목 calendar가 아직 미래 배당일을 안 준 것.
_Avoid_: **캘린더의 배당락일과 혼동 금지** — 캘린더(`routers/calendar.py`)는 task#119 이후 **exact-only**(이력 추정 금지)를 유지한다. Projection은 오직 [[배당 스케줄]] 뷰에만 존재한다. 목적이 다르다: 캘린더=정확성, 배당 목록=forward 커버리지(ADR-0023).

## 배당 (Dividend)

종목의 배당 데이터. 두 층으로 나뉜다: **연 층**(`stock_dividends`, 연 주당배당·시가배당률 — US=yfinance info, KR=DART alotMatter; 대시보드 `yield_on_cost`·연 예상수령액 계산용) vs **스케줄 층**([[배당 스케줄]], 시점별 배당락/금액). 둘은 소스·저장·소비처가 다르다.

## Peer 할인/할증 (Peer Discount/Premium)

내 종목의 밸류에이션 멀티플(PER/PBR/PSR/EV/EBITDA)이 **경쟁사(peer) 중앙값 대비 몇 % 낮은지(할인)/높은지(할증)** — "싼지 비싼지"의 동종업계 비교 기준점. peer 집합은 리포트의 경쟁사 목록에서 자기 자신(is_self)을 제외한 것이고, 해당 지표 값이 있는 peer가 **2개 미만이면 판정하지 않는다**(wrong<missing). 기준은 평균이 아니라 **중앙값** — peer가 2~5개 소표본이라 outlier 1개에 평균이 쉽게 오염된다. 리포트 상세 경쟁사 섹션 상단에 지표별 칩으로 노출.
**단 중앙값도 소표본에서 outlier를 견디지 못한다(라이브 반증)** — 중앙값은 outlier의 *값*엔 둔감하지만 그 *순위*엔 민감하고, peer가 짝수(예 4개)면 중앙값이 **중간 두 값의 평균**이라 outlier가 상위 절반에 들어오는 순간 중앙값 자체가 끌려간다. 005930 리포트에서 TSM의 오값 PBR(81.87)이 그렇게 peer 중앙값을 3.89 → 6.545로 밀어 삼성전자 할인을 **−25% → −56%로 2배 넘게 왜곡**했다. 그래서 중앙값 선택만으로는 부족하고 **[[피어 멀티플]]이 소스 단계에서 이상치를 배제한 값이어야** 이 판정이 성립한다.
**왜곡 폭은 peer 구성에 따라 달라지므로 특정 수치를 기준선으로 못박지 말 것** — 위 −25%/−56%는 peer 4개(000660·TSM·MU·INTC) 전제였고, 이후 INTC가 경쟁사 목록에서 빠져 peer 3개가 되자 같은 오값이 중앙값을 9.80으로 밀어 왜곡이 **−71%**가 됐다(라이브 재측정). 즉 이 항목의 수치는 *사례*이지 회귀 기준이 아니다 — 검증은 리터럴이 아니라 배수 불변식으로 해야 한다.
_Avoid_: **[[시장지수 밸류에이션]]과 혼동 금지** — 그건 시장 *전체*의 역사적 과열도(지수 단위 CAPE), 이건 *개별종목 vs 동종업계*의 상대 위치다. 또한 할인=**싸다는 신호일 뿐 "좋다" 판정이 아니다**(저평가엔 이유가 있을 수 있음 — 판단 보조 정보로만).

## 피어 멀티플 (Peer Multiples)

경쟁사 목록(**자사 포함**)의 밸류에이션 멀티플 묶음 — PER·PBR·PSR·EV/EBITDA(+R&D 집약도). [[Peer 할인/할증]]의 입력이자 [[심층 리포트]] 발행 시 박제되는 숫자 블록이며, 소비처가 **둘**(리포트 상세 경쟁사 섹션·발행물)이라 오값은 두 화면을 동시에 오염시킨다.
핵심 성질은 **자사 값과 peer 값의 출처가 다르다**는 것이다 — 자사 값은 리포트 생성이 자기 시세·재무로 계산하고, peer 값은 외부 시세 소스에서 그대로 받는다(US=yfinance 파생 지표, KR=Naver). 그 비대칭이 **신뢰도 비대칭**을 만든다: peer가 ADR이거나 재무제표 통화가 상장 통화와 다르면(예 TSM = 1 ADR : 보통주 5주 · TWD 재무제표) 외부 소스의 지표별 분모 단위가 엇갈려 **한 종목 안에서 필드마다 반대 방향으로** 틀릴 수 있다(라이브 실측: TSM PBR 81.87 ≈ 10배 과대, 같은 판의 PSR 0.458 ≈ 20배 과소, 반면 PER·EV/EBITDA는 정상). 파싱은 성공하므로 예외도 경고도 없다 — [[구루 자산 배분]]의 신고값 오정렬과 같은 "그럴듯한 오값" 계열.
그래서 peer 값은 **지표별로** 중앙값 대비 대칭 밴드를 벗어나면 결측으로 둔다(wrong<missing) — 종목 단위로 버리지 않는다(멀쩡한 지표를 함께 잃는다).
이 판정에서 **[[판정 대상]]과 [[기준 표본]]은 서로 다른 역할**이며 자사 값의 소속이 둘에서 갈린다 — 자사는 **판정 대상이 아니지만**(비교의 주체다) **기준 표본에는 포함된다**(표본을 1개 늘려 소표본에서 중앙값이 끌려가는 것을 막는다). 초기 구현은 "출처가 달라 신뢰도가 비대칭"이라는 이유로 자사를 *양쪽에서* 뺐는데, 그 비대칭은 자사가 *덜* 믿을 만한 방향이 아니라 *더* 믿을 만한 방향이었고(라이브 반증, ADR-0030) 표본을 깎아 정상 peer가 결측되는 역효과를 냈다.
_Avoid_: **[[Peer 할인/할증]]과 혼동 금지** — 이건 비교에 쓰이는 *숫자 묶음*이고, 그건 그 숫자로 낸 *판정 결과*(내 종목이 몇 % 싼가)다. 또한 **[[경쟁사 기술·경쟁력 비교]]와도 다르다**(그건 사업 경쟁력의 정량·정성 서술).

## 판정 대상 (Judged Value)

이상치 가드가 **버릴지 살릴지 결정하는 그 값** — [[피어 멀티플]]에서는 peer 행의 한 지표다. 자사 값은 판정 대상이 **아니다**: 비교의 주체이고, 틀렸다면 [[Peer 할인/할증]]의 분자가 틀린 것이라 결측 처리로 고칠 수 있는 문제가 아니다(그 검증은 peer 대조가 아니라 자기 과거값 대조여야 하므로 별개 메커니즘).
_Avoid_: **[[기준 표본]]과 혼동 금지** — 어떤 값이 판정 대상이 아니라는 말은 **표본에서도 빠진다는 뜻이 아니다**. 두 역할은 독립이고, 자사는 "판정 대상 아님 + 표본 포함"이다. 이 둘을 한 조건으로 묶으면 표본이 깎여 정상값이 결측된다(ADR-0030).

## 기준 표본 (Reference Sample)

이상치 판정의 **중앙값을 계산하는 값 묶음** — [[피어 멀티플]]에서는 그 지표의 값이 있는 peer 전체 + 자사다. 판정 대상 자신도 표본에 남는다(leave-one-out을 쓰지 않는다). **표본이 3개 미만이면 판정을 생략한다** — 2개면 중앙값이 "중간값"이 아니라 "두 값의 평균"이 되어 오값이 표본의 50% 지분을 갖고, 그 상태에서는 배수가 원리적으로 (0,2) 안에만 머물러 밴드가 발동할 수 없다(생략이 정확한 서술이다).
_Avoid_: **[[Peer 할인/할증]]의 `<2` 임계와 혼동 금지** — 그건 *칩을 표시할지* 정하는 유효 peer 수 임계(자사 제외)이고, 이건 *가드가 판정할지* 정하는 표본 크기 임계(자사 포함)다. 숫자가 비슷해 통합하고 싶어지지만 세는 대상이 다르다. **[[판정 대상]]과도 혼동 금지**.

## 핵심 자원 (Key Resource)

업종마다 다른, 그 회사 경쟁력의 **원천이 되는 핵심 투입자원 + 그 자원의 정량 건강도 + 유지 동력**을 외부 Cowork가 분석해 리포트에 싣는 enrich 필드(`tickers.key_resource`, moat·[[단계 라벨]]과 같은 Cowork 작성 계열). IT·SW·컨설팅은 **인력**이 대표 예 — 직원수·1인당 매출·1인당 영업이익의 **분기별 추이(series)**와 그 인력을 붙잡는 **유지 동력(리텐션 인센티브: 스톡보상·이직률 등)**을 본다. 업종이 바뀌면 자원도 바뀐다(반도체·하드웨어=생산능력/가동률·CapEx, 제약·바이오=R&D 파이프라인, 자동차·EV=생산능력, 에너지·인프라·건설=[[수주잔고]]). 업종별로 "무엇을 핵심자원으로 보고 어떤 지표를 채울지"는 Cowork 가이드(`CLAUDE_COWORK_API.md`)의 업종별 표가 지침하며, 그 표는 [[단계 라벨]] 어휘 표와 **같은 5개 업종 버킷에 정렬**한다. 정량 수치는 **AI가 조사·기입**한다(백엔드 자동계산 아님 — 분기별 직원수의 안정적 소스가 없어 재무÷직원수 자동계산이 불가). 리포트 심층분석 탭에서 경제적 해자(moat) 옆에 표시.
_Avoid_: **경제적 해자(moat)와 혼동 금지** — moat는 경쟁우위가 *왜 지속되는가*(특허·브랜드·규모의 진입장벽)이고, 핵심 자원은 그 업종의 *핵심 투입자원이 무엇이며 정량적으로 건강한가*(인력이면 1인당 생산성·이직률)다. 인접하지만 축이 다르다. [[수주잔고]]와도 다름 — 에너지/건설에선 수주잔고가 핵심자원 지표의 하나로 *인용*될 수 있으나, 핵심자원은 그 값의 DART 자동추출이 아니라 Cowork의 업종 해석 서술이다.

## 경쟁사 기술·경쟁력 비교 (Competitor Edge)

경쟁사 섹션의 각 경쟁사(자사 포함)가 **그 업종의 핵심 경쟁축(기술력·원가·브랜드·규모 등)에서 어디에 서 있는지**의 비교. 두 층의 병합이다: **정량축**은 크롤링(R&D 집약도 = R&D비/매출; US=yfinance, KR=DART best-effort — 검산 실패 시 결측, wrong<missing), **정성 서술**은 외부 Cowork가 enrich 필드로 기입한다. 경쟁축은 업종마다 달라 고정 enum으로 못 담고 작성자가 업종 맥락으로 고른다([[핵심 자원]]·[[단계 라벨]]과 같은 가이드 표 패턴 — 스키마는 공통 1개, 업종별 지침은 Cowork 가이드 표).
_Avoid_: **[[Peer 할인/할증]]과 혼동 금지** — 그건 밸류에이션 멀티플의 상대 위치(*싼가*)이고, 이건 사업 경쟁력의 상대 위치(*강한가*)다. "기술비교"라는 이름이지만 비-기술 업종에선 축이 기술이 아닐 수 있다(축 선택은 작성자 몫).

## 시장 전망 (Market Outlook)

회사가 속한 **전방시장의 규모·성장 예상** — 현재/예상 시장규모(연도 포함), 성장률(CAGR), 회사 점유율/포지션, 출처 — 을 외부 Cowork가 조사·기입하는 enrich 필드. TAM·시장 성장률의 무료 자동 수집 소스가 없어 AI 조사·기입이 유일 수단이다([[핵심 자원]] 정량치와 같은 결, 출처 표기 필수). 화면에선 크롤링된 회사 재무의 매출 성장률과 대조해 "시장보다 빨리/느리게 크는가"를 보인다(정량 대조는 기존 스냅샷 재무 재활용). 이 필드는 **회사 단위 한 층**이고, 그 아래 부문별 분해는 같은 필드 안의 `segments[]`가 담는다([[사업부문 시장 분석]]).
_Avoid_: **growth_plan(장기 성장 계획)과 혼동 금지** — 그건 *회사의* 전략·이니셔티브이고, 시장 전망은 *시장 자체*의 크기/성장이다. [[시장지수 밸류에이션]](지수 과열도)·[[매크로 신호]](거시 신호)와도 다른 축. AI 기입 수치이므로 출처 없는 값은 싣지 않는다.

## 사업부문 시장 분석 (Segment Market Analysis)

종목을 **사업부문 단위로 갈라 "무엇으로 버나 · 뭐가 크고 뭐가 줄고 · 그 시장이 앞으로 얼마나 커지나 · 거기서 몇 % 먹고 돈으로 얼마인가"를 한 화면에 보이는 분석**. 정본은 [[시장 전망]] enrich 필드 안의 `segments[]` **배열 하나**이고, 두 화면이 **같은 렌더러**로 파생한다 — 일반 리포트 「심층분석」 탭(스냅샷 최신)과 [[애널리스트 리포트]](발행 시점 박제). AI(=[[루틴]])는 **%만 기입**하고(부문 비중 당기·전기 · 시장 규모·CAGR · 자사 점유율 · 출처), **금액은 전부 렌더러가 환산**한다(부문 매출 = 스냅샷 총매출 × 비중, 시장 기회 = 시장 규모 × 점유율) — [[수주잔고]] ×100 오저장 계열의 단위 함정을 원천 차단하려는 것이고, 크기·길이 인코딩도 전부 % 축이라 부문마다 시장 통화가 달라도 그림이 거짓말하지 않는다. 환산에는 **두 게이트**가 걸린다: 비중의 **기준 기간(period)이 실적 행과 일치**할 것, **비중 합이 100%를 유의하게 넘지 않을 것**(미달은 '기타' 생략이라 정상). 실패하면 **금액만 생략**하고 부문명·증감·시장 전망은 그대로 보인다 — 정상값까지 지우지 않는다([[기준 표본]] 과보수 함정의 교훈). 미래 환산은 **"점유율 유지 가정"을 라벨로 명시한 시나리오**이며, AI가 미래 점유율을 따로 주면 라벨이 "회사 전망"으로 바뀐다.
_Avoid_: **[[사업부문 분해]]와 혼동 금지** — 그건 [[수주잔고]]를 부문·법인으로 나눈 것(DART 공시 표 자동추출, Σ==합계 검산)이고, 이건 *매출과 시장*을 부문으로 나눈 AI 조사값이다(자동 수집 소스 없음). **[[시장 전망]]의 회사 단위 수치와도 다름** — 같은 필드에 살지만 층이 다르다(회사 1개 시장 vs 부문별 N개 시장).

## 주식 용어집 (Stock Glossary)

**최종 사용자에게** 어려운 주식 용어(PER·매물대·베이시스 등)를 설명하는 앱 내 용어 사전. 정본은 프론트 정적 모듈(용어→설명 맵, DB/API 없음)이고, 노출은 두 방식이다: ① 리포트 상세의 AI 자유 텍스트에서 **자동 매칭**된 단어(밑줄+클릭), ② 차트 **범례/지표 라벨**에 명시 배선된 용어. 클릭하면 단어 근처 **앵커 팝오버**(레이어)로 설명이 뜬다. 별도 브라우즈 화면은 없다(팝업 전용).
_Avoid_: **개발 용어집(.forge/CONTEXT.md — 이 문서)과 혼동 금지** — 그건 팀의 도메인 언어 정본이고, 주식 용어집은 최종 사용자 대상 학습 콘텐츠다. "용어집 = 별도 페이지"(아니다 — 인라인 팝오버 전용).

## 애널리스트 리포트 (Analyst Report)

**선별 종목에 대해 발행하는, 발행 시점이 고정된 심층 분석 문서**(발행물). 구성은 증권사 리포트 표준을 따른다: 헤더(투자의견 매수/중립/매도 · 적정주가 밴드 · 발행 시점 현재가 · 컨센서스 목표가 병기) → 한줄 논지(제목) → 투자 포인트 2~3개 → 밸류에이션(산정방식 서술 + PER 밴드 + 피어 멀티플) → 실적 추정 테이블 → 리스크 요인. 생산은 하이브리드: **판단·서사는 외부 AI 클라이언트(초기 Cowork 수동, 현재 [[루틴]] 자동)**가 발행 API로 쓰고, **숫자(발행 시점 시세·forward 추정치·피어 멀티플·PER 밴드)는 서버가 발행 순간 자동 첨부해 박제**한다. 발행 주체는 루틴 재량 + 가드레일(**admin이 지정한 전역 대상 목록**(`analyst_target`, opt-in 전용 — 비면 자동 발행 스킵, 보유+관심 지정 가능) 중 최신 발행 7일+ 경과 또는 유의미한 변화 종목만, 회당 최대 2종목 — ADR-0027 개정)이며 수동 fire 지시로도 발행 가능(지정 무관). ticker+발행일 단위로 누적 보관하며(과거 판 열람 가능), 다음 날 갱신되지 않는다 — 발행 시점의 판단·데이터가 문서의 정체성이다. 열람은 로그인 사용자 전체. **발행물 목록은 종목당 최신 1건**만 노출한다(목록의 정체성 = "그 종목에 대한 현재 판단"), **과거 판(이력)은 문서 상세에서 이동**해 본다 — 목록이 판 이력을 나열하면 종목이 아니라 판이 단위가 되어 "지금 어떤 종목을 어떻게 보는가"가 묻힌다(ADR-0027 개정). 발행물은 불변이지만 **admin은 종목 단위로 발행물 전체를 삭제**할 수 있다(오발행·대상 해제 종목 정리 — 수정은 여전히 새 판 발행).
_Avoid_: **리포트(일일 스냅샷)와 혼동 금지** — 그건 전 종목 대상 매일 자동 생성·최신 유지되는 시장 데이터 박제이고, 애널리스트 리포트는 선별 종목 대상 판단 문서다. **enrich 필드(moat·insights 등)와도 다름** — enrich는 종목당 최신 상태 1개만 유지되는 tickers 컬럼이고, 애널리스트 리포트는 별도 테이블의 발행물 누적이다(ADR-0027). insights의 한줄 코멘트는 대시보드/요약 탭용 액션 신호, 애널리스트 리포트의 한줄 논지는 문서 제목 — 역할이 다르다.

## 적정주가 밴드 (Fair-Value Band)

애널리스트 리포트 헤더에 싣는 **Cowork 판단의 적정주가 범위(하단~상단) + 산정방식 서술**(예: forward EPS × 목표 PER 근거). 단일값이 아니라 밴드로 제시하고, 시장 컨센서스 평균 목표가와 **병기**해 대조한다.
_Avoid_: **컨센서스 목표가와 혼동 금지** — 그건 증권사 애널리스트들의 평균값(consensus mart 자동 수집)이고, 적정주가 밴드는 Cowork 자체 판단이다. [[사용자 목표가·손절가]]와도 다름 — 그건 사용자 개인의 매매 기준값.

## 컨센서스 근거 (Consensus Basis)

컨센서스 목표가 **평균 하나의 뒤에 있는 원천**: ① 증권사별 개별 의견(`raw_reports` — 증권사명·의견·목표가·표준화 점수·리포트 날짜, 마트와 같은 90일 창 증권사별 최신행) ② 마트 집계 분포(`daily_consensus_mart` — 목표가 최고/최저/평균·평균 의견점수·애널리스트 수·매수/보유/매도). [[애널리스트 리포트]]에서는 발행 순간 data 블록에 **박제**되고(`consensus_detail`), "현재 대비"만 라이브 마트 최신 행과 병기한다. US의 `__consensus__` 행은 증권사가 아니라 집계 placeholder라 근거 목록에서 제외. **박제 시 이원 소스 보충 규칙(task#260 라이브 발견)**: `target_mean`과 매수/보유/매도 분포는 **스냅샷 박제값이 우선**이고, 스냅샷이 비어 있을 때만(KR은 `target_mean=null`·분포 전부 0이 실재) 마트 값(`avg_target_price`·`buy/hold/sell_count`)으로 **보충**한다 — 덮어쓰지 않는다. 안 하면 애널리스트 23명인데 "매수 0 · 보유 0 · 매도 0"으로 표시돼 근거가 오해를 만든다.
_Avoid_: **컨센서스 추이와 혼동 금지** — 추이는 시계열 차트(일반 리포트 상세 ConsensusChart)이고, 근거는 특정 시점의 구성(누가·얼마·언제). **리포트의 판단 근거(투자 포인트)와도 다름** — 그건 Cowork 서사이고, 컨센서스 근거는 외부 증권사 데이터다.

## 선도기술 리포트 (Frontier Technology Report)

개별 종목이 아니라 **선도기술 하나를 단위로 발행하는 심층 문서**(발행물). 첫 대상 4종은 재사용 로켓·전고체 배터리·SMR·로봇. 상세 화면의 구성은 **지표·표가 먼저, 산문은 하단**이다(task#280 — 결론·비교가 4,700자 산문 뒤에 있으면 스크롤 없이는 읽히지 않았다): `기술명 h1` → `리드 문단`(한줄 제목. 이미 결론을 담고 있어 자르지 않고 격만 낮춘다) → `KPI 스트립`(기술난이도 · 선두 업체 · 시장 규모 · CAGR · 주요 업체 수 · 양산상용 업체 수 — 결측은 추정하지 않고 `—`) → **전역 목차**(렌더된 섹션에서 파생한 앵커 칩 — sticky가 아니고, 항목이 1개 이하면 렌더하지 않는다. **리드 밑이 아니라 KPI 스트립 아래**다: 리드 밑에 두면 목차 128px이 KPI 칩을 첫 화면 밖으로 밀어낸다, task#296) → **핵심 포인트**(결론 카드 3~4장, 지표 칩 ≤4 + 1~2문장) → **진척 타임라인**(연도축 + 상태 마커) → **주요업체 표**(업체 · [[기술 성숙 단계]] · 선두 대비 격차 년수 · 시장점유율 — **전 행이 결측인 열은 통째 생략**되고 국가·정부주도 배지·상장 티커·보유/관심 배지는 열이 아니라 업체 셀 안 메타줄이다. 업체별 코멘트는 접기 없이 **상시 노출**. 자체 가로 스크롤러를 두지 않아 모바일 278px에서도 페이지가 가로로 넘치지 않는다, task#296) → 기술수준 비교 밴드 → **[[기술 계열]] 비교**(축마다 소제목 + 2열 표: 계열·대표 사례 | 이점 `+`·대가 `−`. 축 최대 2, 축마다 계열 2개 이상 — 계보 분류와 **병존**한다: 이건 *계열의 성질*, 계보 분류는 *업체의 소속*이다) → **계보 분류**(계열별 업체 그룹 칩) → 점유율 → 해결해야 할 난제 → **[[확인할 지표]]**(번호 체크리스트 — 판정문 + 상세 + 「신호 아님」을 `--warn` 오커로 본문과 분리. 난제가 *안 풀린 관문*이라면 이건 *지켜볼 신호*다) → 시장 규모·성장(실측 실선 + 예상 점선) → **[[기관별 시장 추정 편차]]**(조사기관별 가로 막대, 성장 곡선과 같은 절의 하위 표시 — 값이 없으면 조용히 생략) → 연관기술 관계도(전제→대상→파생 3열) → **상세 설명**(산문 전문 — 접기 없이 상시 노출, 소제목마다 앵커 + `\n\n` 기준 문단 분리) → 출처. 데이터가 없는 섹션은 제목째 생략된다. **산문 구획은 데이터 계약이 아니라 [[루틴]] 프롬프트의 지시다** — `description`의 `[기술 개요]`·`[어디까지 왔나]`·`[시장 규모]`·`[투자 관점]` 대괄호 헤딩(단독 줄)을 화면이 **항상 보이는** 소제목(`<h3>` + 앵커 id)으로 승격하되, 미준수 판은 전문을 담은 단일 블록으로 폴백한다(파싱 실패가 정상 입력이고 정보 손실은 0). **연관기술은 4분류이고 방향성이 배치를 가른다** — `전제·파생`은 방향이 있어 3열 DAG로 그리고, `보완·경합`은 방향이 없어 하단 칩 그룹으로 분리한다(방향 없는 관계를 억지로 DAG에 넣으면 화살표가 거짓을 말한다). 같은 근거로 **계보 분류(`players[].category`)도 DAG가 아니라 칩 그룹**이다 — 계열 간에는 방향 관계가 없다. **요약 레이어 3종은 산문이 아니라 발행 스키마의 구조 필드다**(`key_points`·`milestones`·`players[].category`, task#281) — 프론트가 `description` 산문에서 결론·연표를 추출하지 않으므로([[루틴]]이 쓴 것만 표시한다), 루틴이 필드를 비우면 그 섹션은 조용히 생략된다. 여기서 **차트를 그리는 수치와 요약 칩의 경계**가 갈린다 — 곡선·축·밴드를 그리는 값(시장 금액 · `milestones[].year` · [[기술 성숙 단계]] · 점유율)은 반드시 구조 데이터이고, 그리지 않는 요약 칩(`key_points[].metrics[].value`)만 표시용 문자열이다(ADR-0034 — ADR-0033이 기각한 "표시용 문자열로 받기"는 *그래프를 그리는 수치* 이야기였다). 이 프로젝트 **최초의 비-티커 리소스**다 — 정체성이 종목이 아니라 기술이고, 참여자도 상장사에 한정되지 않는다(SpaceX·Rosatom·CASC처럼 비상장·국영이 오히려 선두인 기술이 있다). 상장 업체엔 티커를 **선택적으로** 매핑해 보유·관심 배지를 얹는다(연결은 부수 가치, 기술 이해가 주). 저장 모델은 [[애널리스트 리포트]]와 같은 발행물(키 = 기술 slug + 발행일, 같은 날 재발행은 upsert, 다른 날은 누적·불변)이지만 **하이브리드 생산이 성립하지 않는다** — 기술수준·기술격차·시장규모·점유율에 자동 수집 소스가 하나도 없어 서사와 수치를 **전부 [[루틴]]이 조사·기입**한다. 그 대가로 단위·출처 규율을 스키마가 강제한다(통화·단위는 enum, 출처 필수, 실측/예상 배열 분리, 모르면 생략 — ADR-0033). 기술 목록의 정본은 백엔드 상수이며(테이블 없음), 목록에 없는 slug 발행은 422로 거부된다.
_Avoid_: **[[애널리스트 리포트]]와 혼동 금지** — 그건 종목 단위 투자 판단 문서(투자의견·[[적정주가 밴드]])이고, 선도기술 리포트는 기술 단위 산업 지형 문서다(투자의견 없음). **[[경쟁사 기술·경쟁력 비교]]와도 다름** — 그건 *한 종목의* 경쟁사를 그 업종 축에서 비교하는 enrich 필드이고, 이건 *한 기술의* 전 세계 참여자를 상장 여부 무관하게 비교한다. **[[시장 전망]]·[[사업부문 시장 분석]]과도 다름** — 그 둘은 회사·부문에 딸린 시장이고, 이건 기술 자체가 단위다(그래서 종목 없이도 성립한다).

## 기술 성숙 단계 (Technology Maturity Stage)

[[선도기술 리포트]]가 쓰는 **공통 5단계 이산 척도** — `1 기초연구 · 2 시제품 · 3 실증 · 4 초기상용 · 5 양산상용`. 기술 4종 전부에 같은 라벨을 적용해 화면이 한 축으로 읽히게 한다. **이산으로 고정한 이유는 허위정밀 차단**이다 — 0~100 점수는 AI가 설명할 수 없는 차이(87 vs 91)를 만들고, 다음 판과 비교할 때 그게 진짜 변화인지 노이즈인지 가릴 수 없다. 여기서 반드시 갈라야 하는 세 축: **기술수준**은 *업체별* 성숙 단계(업체 표의 칸), **기술난이도**는 *기술 자체*의 진입 난이도(1~5 + 근거 서술, 기술 단위 필드 하나), **기술격차**는 *선두 업체 대비 몇 년 뒤인가*(선두사명 병기, 0년 = 선두).
_Avoid_: **TRL(NASA 9단계)과 혼동 금지** — 개념은 닮았지만 이 5단계는 상용화 관점으로 압축한 자체 척도다. **기술수준과 기술난이도를 뒤섞지 말 것** — 난이도가 높은 기술에서도 선두 업체의 수준은 높을 수 있다(두 축은 독립이다). **점유율과도 독립** — 수준 5인 업체가 점유율 0일 수 있고(신규 진입), 상용 시장이 아직 없는 기술은 점유율 자체가 결측이 정상이다.

## 기관별 시장 추정 편차 (Market Estimate Spread)

[[선도기술 리포트]]에서 **같은 기술·같은 연도의 시장 규모를 조사기관마다 다르게 추정한 폭**. 재사용 로켓 2025년이 최소 24.9억달러 ~ 최대 84.4억달러로 **3.4배** 벌어진 실측이 이 용어의 존재 이유다 — 편차의 원인은 데이터 품질이 아니라 **집계 범위**이고(발사 서비스 매출만 세느냐, 기체 제조·회수 인프라·정비까지 포함하느냐), 그래서 이 기술의 시장 규모는 **절대값이 아니라 성장 방향으로 읽어야 한다**는 판단이 화면에 드러나야 한다. 저장은 `market.estimates[]`(기관별 최대 6건, ADR-0034 개정) — **기관별 건은 구조 데이터다**: `institution`·`year`·`size{value,currency,unit}`는 곡선(`history`/`forecast`)과 같은 타입 필드이고, **`scope`(집계 범위 차이를 짧게 적는 표시 문자열)만 자유 텍스트**다. 비교가 성립하려면 **연도·통화·단위가 배열 안에서 전부 같아야** 하며(섞이면 막대 길이나 배수가 거짓을 말하므로 발행 시점에 거부한다), 이는 "렌더러는 절대 추측·환산하지 않는다"(ADR-0033)의 직접 귀결이다. 성장 곡선이 채택한 **정본 기관은 `is_basis: true` 플래그 1건으로 표시**하고(문자열·부동소수 일치로 추론하지 않는다 — 그건 휴리스틱이다), 배열 안 `is_basis=true`는 최대 1건이다.
_Avoid_: **[[선도기술 리포트]]의 시장 규모 시계열과 혼동 금지** — 그건 이 리포트가 *채택한 정본* 하나(실측 + 예상, 연도축 곡선)이고, 편차는 *채택하지 않은 다른 기관들까지* 한 연도에 늘어놓은 비교다(축이 연도가 아니라 기관이다). **[[시장 전망]]·[[사업부문 시장 분석]]과도 다름** — 그 둘은 회사·부문에 딸린 시장이고 기관 간 편차를 다루지 않는다. **정본 표시는 "가장 큰 값"이 아니다** — 정본이 최대인 것은 우연이며, 중앙값·평균을 정본으로 삼지도 않는다(그건 근거 없는 합성이다).

## 기술 계열 (Technology Variant)

[[선도기술 리포트]]에서 **하나의 기술이 갈라지는 접근 방식들과 각 방식이 지불하는 대가**. 발행물 4종 전수에서 확인된 축이다 — SMR은 노형(경수형·비등수형·고온가스로·소듐냉각고속로), 재사용 로켓은 회수 방식(추진 수직착륙·캐치·그물 포획·해상 연착수), 전고체 배터리는 고체 전해질 계열(황화물·산화물·고분자·할라이드), 로봇은 기체 구성(구동계·말단조작계·전원계·VLA 정책모델)과 형태(이족보행·휠베이스). **축의 이름이 기술마다 다르므로 축 라벨 자체가 데이터이며**(고정 enum이 아니다) 한 기술이 두 축을 가질 수 있다. 이 용어의 존재 이유는 **계열 선택이 곧 공급망·공정·상용화 시점 선택**이라는 사실이다 — 고온가스로·고속로 계열은 TRISO·HALEU 별도 연료 라인이 선행돼야 해서 경수형보다 상용화가 뒤로 밀리고, 황화물계는 이온전도도를 얻는 대가로 제조환경 전체를 초저습으로 유지해야 한다. 그래서 각 계열은 **이점과 대가가 쌍으로** 기록되며, 어느 계열이 우월하다는 순위는 두지 않는다(순위를 두면 화면이 발행물에 없는 판단을 말한다). 저장은 `variants[]`(축 최대 2 · 축마다 계열 2개 이상 — 하나뿐이면 비교가 아니라 서술이므로 산문에 둔다).
_Avoid_: **계보 분류(`players[].category`)와 혼동 금지** — 그건 *업체가 어느 계열에 속하는가*이고 이건 *계열 자체가 어떤 성질인가*다. 둘은 같은 계열 어휘를 쓰지만 담는 사실이 다르므로(소속 vs 트레이드오프) 중복이 아니다. **[[기술 성숙 단계]]와도 다름** — 계열은 성숙 순서가 아니라 병렬 갈래이고, 같은 계열 안에 1단계 업체와 5단계 업체가 함께 있다. **대표 사례는 표시 문자열이다**(`중국 ACP100 125MWe`) — 그 값으로 어떤 축·곡선도 그리지 않으므로 구조 데이터로 받지 않는다(ADR-0034 결정 3의 경계).

## 확인할 지표 (Watch Item)

[[선도기술 리포트]]에서 **앞으로 무엇이 관측되면 이 기술의 진척으로 인정하는가**를 미리 못 박은 판정 신호. 발행물 4종 전수에 존재한다 — SMR "링룽 1호의 실제 계통연결이 IAEA에 등재되는가", 재사용 로켓 "회전율(같은 기체를 몇 번 돌리는가)", 전고체 배터리 "고객사 양산 승인·수율 공개·전해질 톤 단위 장기계약", 로봇 "누적 인도 대수가 아니라 누적 가동시간". 이 용어의 핵심은 **짝으로 오는 오독 경고**다 — 파일럿 라인 준공·샘플 공개·양산 목표 재확인·캐파 발표는 *일정이 유지된다*는 신호일 뿐 진척이 아니며, 그것을 진척으로 읽는 것이 이 섹터들의 대표적 오독이다(로봇 산문은 그런 발표를 "수요 신호가 아니라 보조금과 자본시장을 향한 신호"로 읽으라고 명시한다). 그래서 항목마다 **"이건 신호가 아니다"가 본문과 시각적으로 분리돼** 기록된다. 저장은 `watch_items[]`.
_Avoid_: **해결해야 할 난제(`challenges`)와 혼동 금지** — 난제는 *지금 무엇이 안 풀렸는가*(기술 관문)이고, 확인할 지표는 *무엇을 지켜보면 풀렸는지 알 수 있는가*(관측 신호)다. **진척 타임라인(`milestones`)과도 다름** — 타임라인은 *이미 일어난 일과 공표된 목표*를 연도축에 놓고, 확인할 지표는 연도를 특정하지 않는 **판정 기준**이다(그래서 지표는 목표 시점이 밀려도 유효하다). **투자의견이 아니다** — 매수·매도 판단을 담지 않는다([[선도기술 리포트]]에는 투자의견이 없다).

## 루틴 (Routine / 자동 분석 루틴)

**서버 호스트(Mac)에서 headless `claude -p`로 도는 자동 분석 에이전트** — 포트폴리온이 fire(HTTP POST)로 로컬 리스너(launchd 데몬, 127.0.0.1:8787)를 깨우면 리스너가 정책 프롬프트(`scripts/cowork-routine-prompt.md`)+지시문으로 `claude -p`를 스폰해 CLAUDE_COWORK_API.md 워크플로우(enrich·애널리스트 리포트 발행·선도기술 리포트 발행) 3종을 순서대로 검토·수행하고 API로 결과를 쓴다. **스케줄은 포트폴리온이 소유**한다: 일일 리포트 배치(daily_report_kr/us) 완료 직후 자동 fire + admin 수동 fire(`POST /api/admin/cowork/fire`). 사용자 claude **구독**(keychain OAuth)으로 실행되며(Anthropic API 토큰 과금 계정 불필요), fire 토큰·URL은 `.env.docker` 보관, 쓰기 키는 로컬에만 상주. 자동 경로 정책(멱등, 정본은 프롬프트 파일): enrich는 enriched_at 누락·7일+ 오래된 순 rolling 최대 5종목/회, 애널리스트 리포트 발행은 재량+가드레일(애널리스트 리포트 항목 참조), 선도기술 리포트 발행은 회당 최대 1건 + 그 기술의 최신 발행이 30일 이상 지났거나 미발행일 때만(조건 미충족이면 발행하지 않는 것이 올바른 판단). 실행 로그: `~/portfolion-routine-runs/<ts>/run.log`. (ADR-0028 개정 — 클라우드 루틴은 샌드박스 egress 차단으로 기각·비활성 보존)
**트리거 본문(fire의 `text`)은 컨텍스트·가중이지 범위 제한이 아니다(task#279)** — 일배치 완료·수동 fire 모두 "프롬프트에 정의된 전 정책을 순서대로 검토해 수행하라"만 지시하고 개별 정책명·상한값을 열거하지 않는다. 정책 정본은 항상 `scripts/cowork-routine-prompt.md`이며, 트리거 지시는 그중 무엇을 우선 검토할지 가중할 뿐 나머지를 배제하지 않는다(단, "이 종목만 발행해라"처럼 명시적으로 범위를 재지정하면 그건 예외로 우선한다). 트리거 본문에 정책을 열거하면 그 열거가 프롬프트와 드리프트해 stale 목록이 정본을 이겨버린다 — 선도기술 리포트 0건 발행이 정확히 이 경로로 발생했다.
_Avoid_: **Cowork(수동 세션)와 혼동 금지** — Cowork는 사람이 claude.ai에서 직접 여는 대화 세션이고, 루틴은 이벤트로 기동되는 무인 실행이다. 루틴 도입으로 정기 enrich/발행의 Cowork 수동 세션 의존이 사라진다(문서 CLAUDE_COWORK_API.md는 루틴 프롬프트의 소스로 계속 유효). **배치와도 다름** — 배치는 백엔드 APScheduler 잡(시장 데이터 수집)이고, 루틴은 백엔드 컨테이너 밖(호스트 claude CLI)에서 도는 LLM 분석이다(백엔드 무LLM 원칙 유지 — fire는 HTTP POST 1개). **claude.ai 클라우드 루틴(Routines 기능)과도 다름** — 그건 시도했다 egress 차단으로 기각된 경로다. **트리거 본문에 정책을 열거하지 말 것** — daily_text/manual_text(`cowork_trigger.py`)가 유일한 산지이며, 정책명·상한값은 프롬프트 파일에만 쓴다(위 문단).

# Coding principles

You are a lazy senior developer. Lazy means efficient, not careless. The best code is the code never written.

Before writing any code, stop at the first rung that holds:

1. Does this need to be built at all? (YAGNI)
2. Does the standard library already do this? Use it.
3. Does a native platform feature cover it? Use it.
4. Does an already-installed dependency solve it? Use it.
5. Can this be one line? Make it one line.
6. Only then: write the minimum code that works.

Rules:

- No abstractions that weren't explicitly requested.
- No new dependency if it can be avoided.
- No boilerplate nobody asked for.
- Deletion over addition. Boring over clever. Fewest files possible.
- Question complex requests: "Do you actually need X, or does Y cover it?"
- Pick the edge-case-correct option when two stdlib approaches are the same size.
- Mark intentional simplifications with a `ponytail:` comment naming the ceiling and upgrade path.

Not lazy about: input validation at trust boundaries, error handling that prevents data loss, security, accessibility, anything explicitly requested.
