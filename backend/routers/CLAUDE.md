# backend/routers/ — 요청/응답 계약·Pydantic 입력 검증

`backend/routers/` 아래 작업 시 자동 로드된다. 루트 `CLAUDE.md`에서 **원문 그대로** 옮겨 온 항목들이다(doctor 정리, 2026-10-10). 본문의 「위·아래 항목」·「이 문서의 ~ 항목」은 원래 루트 파일의 순서·위치를 가리키므로, 찾는 항목이 여기 없으면 루트·`backend/`·`frontend/`의 CLAUDE.md와 `.claude/skills/verification-gates`·`.claude/skills/deploy-ops`를 볼 것.

- **엔드포인트 응답을 비-additive로(배열→객체 등) 바꾸면 그 엔드포인트를 fetch하는 *모든* 프론트 소비처를 전수 grep**: `grep -rn '<엔드포인트 경로>' frontend/src/`로 독립 fetcher까지 찾아 전부 갱신할 것. 한 소비처만 고치면 다른 곳(예: `Analytics.jsx`가 훅과 별개로 `/api/stocks/dashboard`를 직접 fetch)이 `res.data`를 옛 형태(배열)로 취급해 조용히 깨진다(task52: 대시보드 배열→`{holdings,totals}` 변경 시 상관관계 탭이 항상 "보유종목 없음" — 워크플로우·적대적 리뷰 둘 다 놓치고 메인 세션 grep이 포착). 가능하면 **additive(필드 추가)**를 선호하고, reshape가 불가피하면 소비처 전수 감사를 DoD에 포함. (배치 id 4표면 grep의 프론트-계약판.)

- **대시보드 빌드는 "holdings=N → 항상 N카드" 불변식 — 500-to-empty 금지(task#102)**: `GET /api/stocks/dashboard`의 `_build_all`(`routers/stocks.py`)은 `get_quotes_batch`(try/except→{}) + 카드당 `_safe`(throw→`_minimal_card`)로 감싸 **일괄시세·per-card enrichment(snapshot/consensus/배당/수급/내부자) 실패에도 전체 500을 안 낸다**. 콜드 첫 호출에 **10-워커 ThreadPool×카드당 다중 DB read가 풀 경합(PoolError, CONCERNS §4)/throw → 500 → 프론트 `usePortfolioData.fetchDashboard` catch가 silent로 삼킴 → 빈 그리드**였고, 헤더(`/api/portfolio`=단일 쿼리·ThreadPool 없음)는 N 정상이라 "헤더 N·그리드 빈"이 됐다(첫 로딩만, 재네비=풀 warm면 정상). 프론트도 방어: `Portfolio.jsx` `DashboardGrid`는 `stocks>0`이면 빈상태 대신 Skeleton(헤더↔그리드 모순 제거), self-heal은 one-shot이 아니라 **bounded 재시도(최대 3)** — 첫 콜드 실패에 한 방 헛쓰고 재마운트 전까지 stuck하던 회귀 차단. **헤더 N인데 그리드 빈** 증상을 보면 dashboard 빌드 throw(풀 경합 등)와 **프론트 silent catch**를 의심할 것. (풀 sizing 자체 튜닝은 별도 후속 — 이 가드는 증상 차단.) **단, 실제 근본은 per-card throw가 아니라 `_portfolio_totals` NaN→직렬화 500이었다(task#104)**: `_usdkrw_rate()`가 저장 FX의 비유한값(nan)을 그대로 반환→`if fx is None` 가드를 통과(NaN≠None)→US 카드 totals=NaN→starlette `allow_nan=False` 직렬화 500. cold·warm 무관 결정적 500(per-card 가드 *위* 단계라 task#102가 못 막음). 수정: ① `_usdkrw_rate`에 `math.isfinite` 가드(비유한→None, US totals graceful 제외) ② `_build_all` 반환을 `services.utils.sanitize`로 감싸 NaN/inf→None(출처 불문 직렬화 500 안전망, CONCERNS §3). 외부시세서 흘러든 NaN은 응답 dict 어디든 들어갈 수 있으니 **시세/합산을 응답에 싣는 엔드포인트는 sanitize 또는 소스 isfinite 가드 필수**. **세 번째 minimal-card 트리거 — 배당 `float/Decimal` TypeError(commit d666cdd2)**: `_build_card`의 `yield_on_cost = annual_div / avg_cost`·`expected_income = annual_div * qty`에서 `avg_cost`/`qty`는 DB NUMERIC→**Decimal**, `annual_div`(stock_dividends)는 **float**이라 `float/Decimal` 연산이 `TypeError`→배당 있는 *모든* 보유종목 카드가 throw→`_minimal_card` 폴백→RSI·컨센서스·매물대·배당이 통째 blank(스냅샷·시세는 정상). task#102(풀 경합·cold-only)·#104(NaN 직렬화 500)와 달리 **결정적이고 500도 안 나서(graceful 폴백) 더 은밀** — 에러 토스트 없이 enrichment만 조용히 사라진다. **헤더/시세는 정상인데 enrichment(RSI·컨센서스·매물대·배당)만 일괄 blank면 `docker logs portfolion-backend-1 | grep '최소카드 폴백'`로 per-card 예외부터 확인**(minimal-card 가드가 근본원인을 마스킹하므로 로그가 유일한 단서). 수정: 배당 계산 양변 `float()` 정규화. 회귀 테스트는 **Decimal** avg_cost로(기존 fixture가 float만 써 못 잡던 fixture-pass-live-fail — DB는 NUMERIC→Decimal). DB NUMERIC 컬럼(avg_cost·quantity 등)을 float·외부값과 산술하는 경로는 어디든 동일 위험.

- **응답에 NaN/inf 가능 float를 싣는 엔드포인트는 NaN/inf를 가드할 것** — starlette `JSONResponse`는 `allow_nan=False`라 응답 dict에 `NaN`/`inf`가 있으면 직렬화에서 **500**(`Out of range float values are not JSON compliant`)이 난다. 특히 위험한 건 폴백이 *다르게* 가린다는 점: PostgreSQL은 `json` 컬럼에 NaN을 거부(저장 실패)하지만 **파이썬 `json.dumps`는 기본 `allow_nan=True`라 파일 폴백은 통과**해, DB저장 실패→파일 성공→응답 직렬화 실패로 증상이 엇갈려 진단이 늦어진다. 외부 시세(yfinance `Close`가 NaN, FX/usdkrw가 NaN 등)에서 흘러든 NaN이 합산값(`total_value` 등)을 오염시키는 게 전형. 가드는 **소스에서**(예: `math.isfinite` 체크 후 "시세 없음" 처리) 하는 게 출력 일괄 sanitize보다 깨끗하다. (다이제스트 생성 500 사례 8cd70a42.)

- **입력 경로의 NaN은 3중으로 통과한다 — Pydantic float은 기본 `allow_inf_nan=True`, NaN 비교는 항상 False, 그리고 422 detail이 NaN을 echo해 500이 된다(task#211)**: 위 "응답에 NaN 가드" 가토가 *출력* 방어라면 이건 *입력* 방어다. raw JSON 본문의 `NaN` 토큰은 ① `json.loads`가 허용하고 ② Pydantic v2 float 필드가 기본 `allow_inf_nan=True`로 통과시키고 ③ `low <= high` 같은 범위 검증은 NaN에서 **항상 False**라 조건을 뒤집어도 안 걸려서, **불변이어야 할 문서(발행물 등)에 NaN이 조용히 저장**됐다(적대 리뷰가 라이브 재현). → **float 필드엔 `allow_inf_nan=False`를 명시**하고 범위 검증 전에 NaN을 배제할 것. 연쇄 함정: NaN을 거부하면 FastAPI 기본 검증 에러 응답이 **입력 NaN을 그대로 echo**하고 starlette는 `allow_nan=False`라 422가 **500**으로 터진다 → `main.py`의 `RequestValidationError` 커스텀 핸들러(+`sanitize`)가 앱 전역에서 막는다(엔드포인트별 문제가 아님). **⭐ 그리고 위 3중은 *요청 본문* 경로의 이야기다 — 외부소스 문자열 파싱에는 네 번째 통로가 따로 있다: `float("nan")`·`float("inf")`·`float("Infinity")`는 **ValueError를 던지지 않는다**(task#292 B52). 그래서 `try: float(s) except (ValueError, KeyError): pass`로 감싼 숫자 파싱은 그 토큰들을 **예외 없이 통과시켜** 비유한값을 컬렉션에 넣고, 뒤이은 `sum(xs)/len(xs)`·`max(xs)`가 통째로 NaN이 된다(`market/kr.py::get_analyst_data_kr`의 `TARGET_PRC`·`AVG_PRC`가 실사례). 연쇄로 더 위험한 것은 **진리값 가드가 NaN을 막지 못한다**는 점이다 — `bool(float('nan')) == True`이므로 `if x:`는 NaN을 통과시킨다(`consensus_pipeline.py::run_daily`의 KR override가 같은 파일이 도입한 `math.isfinite` 초크포인트 *옆을* 지나갔다). PostgreSQL `numeric`은 `NaN`을 저장하므로 UPDATE는 성공하고 행이 **영구 오염**된다. 실천: ⓐ 외부 문자열→float 파싱은 `except`만으로 부족하고 **`math.isfinite` 검사가 쌍으로** 필요하다 ⓑ 비유한값 게이트는 `if x:`가 아니라 `if x is not None and math.isfinite(x):`로 쓸 것 ⓒ 파일 안에 초크포인트를 만들었으면 **같은 파일의 다른 쓰기 경로가 그 옆을 지나가지 않는지** grep할 것. **⭐ 그리고 네 번째 통로의 *반대편* — 방어가 겹치면 「이빨 검사」가 거짓 음성을 낸다(task#305)**: 위 세 통로가 「NaN이 새어 들어오는」 이야기라면 이건 **「막긴 막았는데 무엇이 막았는지 모르는」** 경우다. `composition.share_pct`에 `allow_inf_nan=False`를 넣고 task#250 관례대로 그것을 **일시 제거해 이빨을 확인**하려 했는데 **테스트가 계속 통과했다.** 원인은 방어가 **셋**이었기 때문이다 — ⓐ `allow_inf_nan=False` ⓑ 5% 그리드 검증자의 `round(nan)`이 **ValueError**를 던져 pydantic이 422로 바꿔줌 ⓒ **`ge=0, le=100` 자체**(NaN은 모든 비교가 False라 범위 검증에서 탈락). 셋을 **전부** 걷어내고 `Infinity`를 보내야 비로소 실패했다. 여기서 두 사실이 나온다: **(가) 두 비유한값의 운명이 갈린다 — `round(nan)`은 ValueError(→422)인데 `round(inf)`는 **OverflowError**라 pydantic이 잡지 않아 **500**이 된다.** 그러니 이 경로를 암묵 의존으로 두지 말고 검증자 첫 줄에 `math.isfinite` 명시 가드를 둘 것(그러면 두 값이 같은 422로 수렴한다). **(나) 「이빨이 안 잡힌다」는 테스트가 무의미하다는 뜻이 아니라, 방어가 중복돼 *어느 하나도 단독으로 load-bearing이 아니라는* 뜻일 수 있다** — 그 구별을 계측 없이 추정했으면 멀쩡한 가드를 "쓸모없다"며 지웠을 것이다. 실천: 이빨 확인이 실패하면 **그 축을 지키는 방어를 전부 열거해 하나씩이 아니라 *모두* 제거**해 보고, 그때도 통과하면 그제야 테스트를 의심할 것. **⭐ 그리고 그 *반대 방향* — 이빨을 **체계적으로** 재보면 「아무도 지키지 않는 축」이 드러난다(task#315·#316)**: 위 (나)가 「방어가 중복돼 이빨이 안 잡힌다」였다면 이건 **「방어가 0이라 이빨이 안 잡힌다」**다. 두 경우는 **같은 관측**(제거해도 통과)에서 나오므로, 구별하려면 **여러 축에 같은 fault-injection을 돌려 비교**해야 한다 — 한 축만 재면 어느 쪽인지 알 수 없다. 실측 2건: ⓐ 순수 함수에 4종을 주입했더니 3종은 각각 1~2건 실패했는데 **전문가 축 필터 제거만 0 fail**이었다(= 그 축을 아무 테스트도 지키지 않았다) → 대조군 테스트를 추가하고 방어 2겹을 *모두* 제거해야 깨짐을 확인했다 ⓑ 오버레이 신규 6축이 전부 *선언*만 재서 `pointerEvents:'none'` 주입에 **6축 모두 초록**이었다(오버레이를 무력화하는 가장 자연스러운 변경이 통째로 안 잡혔다) → 그 핀을 신설했다. **실천**: 새 가드의 이빨을 **한 축만** 확인하지 말고 같은 파일의 인접 축에도 같은 주입을 돌려 볼 것 — **0 fail이 나오는 축이 곧 「선언만 재는 테스트」**다. **⭐⭐ 그리고 무이빨의 *세 번째 원인* — 방어의 수가 아니라 **표시와 게이팅이 갈린 것**이다(task#359 실측)**: 위 두 경우가 방어가 **중복**(#305)이거나 **0**(#315·#316)이어서 주입이 안 잡히는 것이었다면, 이건 **주입이 애초에 표시에 닿지 않는** 경우다. 기술 리포트 단 헤더에서 렌더 여부는 `SECTIONS[].stage`가 게이팅하고 보이는 글자는 **JSX 리터럴**(`<GroupHeader>우위</GroupHeader>`)이었다 — 그래서 `stage`를 `'ZZ우위'`로 주입해도 게이팅만 바뀌고 화면 글자는 그대로라 **51축 전부 초록**이었다. 라벨을 `{stageHeadAt[id]}`로 바꿔 **SECTIONS 단일 소스**로 만든 뒤 같은 주입을 하니 정확히 2축이 FAIL했다. **구별법**: 주입 대상(여기선 `stage`)과 단언 대상(렌더된 텍스트) 사이에 **데이터 흐름이 실제로 있는지** 물을 것 — 없으면 그 주입은 축을 시험한 적이 없다. **처방이 앞의 둘과 다르다** — #305는 「방어를 전부 걷어내라」, #315는 「대조군 축을 신설하라」인데, 여기서는 테스트를 건드릴 일이 아니라 **구현에서 이중 소스를 없애는 것**이 답이다(그러면 축은 이미 옳았다). 일반화: **같은 개념이 「분기용 값」과 「표시용 리터럴」로 두 번 적혀 있으면 그 둘은 드리프트하고, 어떤 축도 그것을 알리지 않는다**([[역할 수를 세라]] 계열의 *역방향* — 저쪽은 한 필드가 역할을 겸직하는 것이고 이건 한 역할이 두 곳에 흩어진 것이다). **⭐⭐ 그리고 「방어가 겹쳐 이빨이 없다」는 판정 자체가 오진일 수 있다 — 겹친다고 기록하기 전에 **그 상태를 단독으로 소비하는 다른 렌더 지점**을 찾아라(task#379→#381 실측)**: Calendar 월 이펙트의 `.finally` 게이트를 지워도 0 FAIL이라 「`events == null`이면 스켈레톤 분기가 옛 finally를 가린다 — 방어 중복」으로 기록하고 봉인했는데, `loading`은 스켈레톤만이 아니라 **새로고침 버튼 `disabled={loading}`**도 읽고 있었다. 옛 finally가 로딩을 끄면 새 달 로딩 중에 그 버튼이 켜진다 — 단언 1줄로 주입이 정확히 FAIL했다. 즉 이빨이 없던 이유는 방어 중복(#305)이 아니라 **단언 누락**이었고, 그 오진 때문에 루프 정지조건이 미충족으로 남아 fix-forward·재배포 1회가 더 붙었다. 실천: 주입이 0 FAIL이면 #305(전부 걷어내기)로 가기 전에 `grep -n '<상태명>' <파일>`로 **그 상태의 소비처를 전부 열거**하고, 겹친다던 방어가 가리지 않는 소비처(버튼 `disabled`·aria 속성·카운트 표시 등)가 있으면 그것을 단언할 것.

- **선택 필드를 `x: float = Field(None)`으로 쓰면 *키 생략은 통과하고 명시적 `null`만 422*가 된다 — 그 비대칭이 요청 **전체**를 죽인다(task#250)**: 위 task#211 가토의 형제(둘 다 Pydantic v2 입력 검증). pydantic v2는 **`validate_default=False`가 기본**이라 기본값 `None`은 검증을 안 타지만, 클라이언트가 **명시적으로 보낸 `null`** 은 선언 타입(`float`)의 검증을 탄다 → `float_type` 422. 그래서 **생략한 요청은 잘 되는데 `"change_pct": null`을 보낸 요청만 죽는** 형태가 되고, 그 필드가 중첩 배열(발행물 지표 칩) 안에 있으면 **칩 하나 때문에 발행 요청 전체가 422**로 막힌다(버그리포트 H1 전체차단). 생략 케이스만 단언하는 테스트는 이걸 **원리적으로 못 잡는다**(`test_publish_with_point_metrics`가 정확히 그랬다). → **선택 필드는 반드시 `Optional[X] = Field(None, ...)`**(로컬 `.venv`가 py3.9라 PEP604 `X | None` 금지 — 위 가토 참조). **`Optional`로 바꿔도 `allow_inf_nan=False`의 NaN 차단은 유지된다**(로컬 py3.9 + 컨테이너 py3.12/pydantic 2.13.4 양쪽 실측: 생략→None · `null`→None · `7.5`→7.5 · `NaN`/`Infinity`→422 `finite_number` · `"abc"`→422). 회귀 테스트는 **명시적 null 케이스**와 **NaN 거부 핀** 두 개를 쌍으로 둘 것 — 후자는 red-first가 원리적으로 불가하니(수정 전에도 통과) 대신 `allow_inf_nan=False`를 일시 제거해 실제로 실패하는지 **이빨 검증**하고 원복할 것. 동종 패턴 탐지: `grep -rn "= Field(None\|= Field(default=None" backend/routers/ backend/services/`. **⚠️ 그런데 그 탐지 grep은 *배열 변형*에 원리적으로 블라인드하다 — 실측 위반 1건이 그것 때문에 25일간 생존했다(task#218 → 2026-08-20 일괄 승급에서 발견)**: 같은 함정의 배열형은 `List[X] = Field(default_factory=list)`·`Field([])`이고, 위 grep은 **그것을 한 글자도 잡지 못한다**(실측: 38건 히트 중 대상 0건). 배열형 규약은 이 가토가 아니라 **ADR-0034 보정 ③**에 「선택 배열은 **예외 없이** `Optional[List[X]] = Field(None)`」으로 따로 적혀 있어서, **한쪽만 읽으면 한쪽만 고친다** — 실제로 `analyst_reports.py`의 `PointMetric.change_pct`(스칼라)는 이 가토를 인용한 주석과 함께 올바르게 고쳐져 있는데 **바로 다음 줄**의 `ReportPoint.metrics`(배열)는 옛 형태로 남았다(`:36`). 로컬 실증(pydantic 2.13.4): 키 생략 → OK · **명시적 `null` → 422 `list_type`** · `[]` → OK. `points`는 발행 본문의 배열이므로 **포인트 하나의 `"metrics": null`이 발행 요청 전체를 막는다**(형제 `tech_reports.KeyPoint.metrics`는 `Optional[...]`이라 통과한다). 현재는 dormant다 — 루틴 프롬프트가 `metrics`를 항상 배열로 넣도록 지시하지만 그 절엔 **「없으면 생략하라」가 없다**(형제 tech 절은 `change_pct`에 그것을 명시한다). **실천 2가지**: ⓐ 「선택 필드」 규약을 적용할 땐 **스칼라와 배열을 한 목록으로 세라**(같은 `validate_default=False`에서 나오는 같은 함정이다) ⓑ **탐지 grep을 처방문에 적을 때는 그 grep이 함정의 *모든 표현형*을 덮는지 한 번 돌려 확인할 것** — 덮지 않는 처방은 「감사했다」는 거짓 안심만 만든다. 넓힌 패턴: `grep -rnE "List\[.*\] = Field\((default_factory=list|\[\])" backend/routers/ backend/services/`. 이것은 인증 문서의 「감사 패턴을 좁히면 그 감사는 통과해도 무의미하다」와 **같은 결함의 세 번째 사례**이고, 이번엔 **가토 자신이 그 좁은 패턴을 처방문으로 박제**하고 있었다.

- **⭐ 신규 구조 필드를 만들 땐 「가장 닮은 형제」의 `model_validator`를 전부 열거해 각각 "이 필드에도 필요한가"를 물을 것 — 그 목록이 곧 체크리스트다(task#297, 적대 리뷰 HIGH)**: 위 두 가토가 *타입·Optional* 규약이라면 이건 **교차필드 불변식**이다. `variants[]`(계보 비교축)를 신설할 때 형제 `market.estimates[]`에는 있던 중복 방어(`Market._estimates_consistency` — 통화·단위·연도 동일성 + `is_basis` 최대 1개)의 **짝을 만들지 않아**, `options[].name`이 같은 옵션 2개와 `axis_label`이 같은 축 2개가 **201로 통과**했다(리뷰가 TestClient로 재현, 무쓰기 확인). 중복이 통과하면 렌더러가 같은 이름의 행을 두 번, 같은 제목의 표를 두 개 그려 **독자가 서로 다른 둘로 읽는다.** 같은 라운드에 두 번째 결함도 나왔다 — `strength`·`tradeoff`가 **둘 다** 결측인 옵션이 통과해 비교표 행이 이름만 남았다(배열 하한 `min_length=2`가 *축* 수준에서 막으려던 「비교가 아니라 서술」이 *행* 수준에서 되살아난 것). **어느 자동 게이트도 이 클래스를 못 잡는다** — 타입은 맞고 상·하한도 지켜지므로 pydantic이 통과시키고, `test_api_doc_sync.py`는 엔드포인트 *존재*만 본다. 부수 교훈 2가지: ⓐ **문서가 검증 강도를 과대 서술할 수 있다** — 「이점과 대가를 **반드시** 쌍으로」가 ADR·CONTEXT·Cowork 문서 **세 곳**에 있었는데 스키마엔 그 강제가 없었다. 문서의 강한 단어(반드시·항상·최소)는 실제 `Field(...)`·validator와 대조할 것. ⓑ **완화 판단은 양성 테스트로 못박아야 되돌려지지 않는다** — 「최소 하나이고 **둘 다는 아님**」은 음성 테스트만으론 표현되지 않는다(쌍을 강제해도 음성 테스트는 그대로 통과한다). 한쪽만 있는 입력이 **201임을 단언하는 테스트**를 쌍으로 두고, 왜 하한을 하나로 뒀는지(한쪽만 아는 계열에서 발행 전체를 422로 막는 대가가 이득보다 크다)를 그 테스트에 적을 것.

- **⭐ 스키마가 있는 쓰기 API를 호출할 땐 규약 산문이 아니라 *검증기*를 직독하고, 호출 전 로컬 교차검증을 만들 것 — 재시도 예산보다 압도적으로 싸다(task#322 실측 422 **0회 / 7종**)**: 위 세 가토(task#211 NaN 3중 통과 · #250 `Optional` 비대칭 · #297 형제 `model_validator` 열거)가 전부 「스키마를 *만들* 때」의 이야기라면 이건 **그 스키마에 *쓸* 때**의 이야기다. 주요기술 리포트 7종을 발행하는 태스크에서 계획은 「422 지뢰밭」을 예상해 파일럿 1건으로 지뢰를 다 밟게 하고 나머지 6종에 slug당 3회(총 21회) 재시도 예산을 뒀는데, **실제 422는 0회**였고 예산은 한 번도 쓰이지 않았다. 갈림은 하나였다 — 규약 문서(`scripts/cowork-routine-prompt.md` §3)만 읽지 않고 **`backend/routers/tech_reports.py`의 Pydantic 모델과 `model_validator`를 전부 직독**해 `max_length`·`min_length`·`ge/le`·`Literal` enum·교차필드 검증을 그대로 옮긴 것이다. **규약 산문은 상·하한의 정본이 아니다** — 사람이 읽을 문서라 「최대 4개」류는 적히지만 `min_length=1`·`max_length=40`·`Literal["done","in_progress","planned"]` 같은 것은 전부 적히지 않거나 일부만 적힌다(그리고 위 #297 가토가 기록한 반대 방향도 있다 — 문서가 스키마보다 *강하게* 서술하는 경우). 그 위에 **호출 직전 로컬 사전검증**을 붙였다: 축별 합 100 · `share_pct` 5의 배수 · 배열 항목수 상·하한 · `composition.tech[].leaders` ⊆ `players[].name` · `minerals[].used_in` ⊆ `tech[].name` · `estimates` 전 원소의 year/currency/unit 동일성 · `metrics` 개수 · `status` enum. **이 사전검증은 한 번 만들면 형제 대상 전체에 그대로 이전된다** — 병렬 서브에이전트 6명 전원의 프롬프트에 「POST 전에 이 검증을 반드시 돌려라」를 필수 게이트로 박았고 6/6이 첫 호출에서 201을 받았다. 실천 3가지: ⓐ **재시도 예산을 짜기 전에 검증기를 직독**할 것(예산은 실패를 전제하는 설계이고, 사전검증은 실패를 없애는 설계다 — 후자가 싸다) ⓑ 교차필드 참조(`leaders`⊆`players` 류 dangling reference)는 **로컬에서 집합 차집합 한 줄로** 잡히니 왕복에 맡기지 말 것 ⓒ 되돌릴 수 없는 쓰기(이 저장소의 발행물은 `slug`당 1행이고 삭제가 admin 세션 전용이다)에서는 사전검증이 안전장치까지 겸한다 — 422는 아무것도 쓰지 않으므로 **검증 실패가 곧 무해한 실패**이고, 그 성질을 활용해 위험을 왕복에서 로컬로 옮기는 것이다.
