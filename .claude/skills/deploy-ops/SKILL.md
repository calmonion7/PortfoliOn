# 배포·운영 런북

루트 `CLAUDE.md`에서 **원문 그대로** 옮겨 온 항목들이다(doctor 정리, 2026-10-10). 본문의 「위·아래 항목」·「이 문서의 ~ 항목」은 원래 루트 파일의 순서·위치를 가리키므로, 찾는 항목이 여기 없으면 루트·`backend/`·`frontend/`의 CLAUDE.md와 `.claude/skills/verification-gates`·`.claude/skills/deploy-ops`를 볼 것. 배포의 **금지 규칙 요약은 루트 `CLAUDE.md` Deployment 절에 남아 있다** — 여기는 그 근거와 증상별 진단이다.

- **프론트 서빙**: nginx가 `./frontend/dist`를 `:ro` 볼륨마운트로 직접 서빙. 로컬 `cd frontend && npm run build`가 **즉시 라이브**(서빙 번들 해시=로컬 빌드 해시로 검증 가능). `git push`는 폴러 재배포/영속용이며, **백엔드 변경은 폴러 재배포 후에야 라이브** 반영된다(프론트만 먼저 빌드하면 백엔드 의존 기능이 미동작). ⚠️ **단 그 비대칭은 *로컬 빌드를 했을 때*의 이야기다 — `deploy.sh:25`가 `(cd frontend && npm install --silent && npm run build --silent)`를 돌리므로 푸시 하나로 프론트도 자동 라이브가 된다(task#290 실측: 커밋 push → `gh run list` 배포 success 20초 → `frontend/dist/*` mtime이 그 시각 → 라이브 번들 == 로컬 `dist`).** 이 사실이 이 절에 빠져 있어서 **task#290 계획이 S6를 「commit+push → `npm run build` → 프로브」로 짜고 "빌드 전에 프로브를 돌려 라이브 red-first를 확보할 수 있다"를 적었는데, 별도 빌드는 불필요했고 라이브 red-first는 push-first 순서에서 원리적으로 불가능했다**(푸시 ~20초 뒤면 새 번들이 서빙돼 옛 번들을 잴 창이 없다). 실천 2가지: ⓐ **라이브 red-first가 필요하면 푸시 *전에* 돌릴 것** ⓑ 배포가 작업트리의 `frontend/dist`를 갱신하므로 **라이브를 재는 에이전트가 도는 동안 푸시도 배포성 행위**다(빌드만이 아니다 — 아래 ⑥ 4번째 관측의 자기적용판). **⚠️ 단 ⓐ는 충분조건이 아니다 — 푸시 *전에* 돌려도 red가 원리적으로 안 나오는 경우가 있다(task#318 실측)**: task#290이 「푸시 *후*엔 옛 번들을 잴 창이 없다」였다면 이건 「푸시 *전*에도 red가 없다」는 **다른 메커니즘**이다. 조건은 **프로브의 기대값이 그 변경으로 신설되는 백엔드 필드에서 파생될 때**다 — 푸시 전에는 프론트만 옛 번들인 게 아니라 **백엔드도 옛 코드**라 그 필드가 없고, 그러면 기대값이 0으로 degenerate해 **관측 0과 일치하며 통과한다**(task#318: 신규 9축이 전부 「표본 0 — 미검증」으로 PASS). 계획서는 「옛 번들이라 원리적으로 red여야 한다」고 적었지만 그 추론은 **백엔드가 이미 새 코드일 때만** 성립하고, 그 창(백엔드 새 + 프론트 옛)은 `deploy.sh`가 프론트를 먼저 라이브로 만들기 때문에 **이 저장소에서 자연 발생하지 않는다**(비대칭의 방향이 반대다). 실천: 프론트·백엔드를 함께 건드리는 변경의 라이브 판별력은 red-first에 기대지 말고 **배포 후 fault injection**으로 얻을 것(대상 셀렉터·기대값을 의도적으로 깨뜨려 축이 실제로 FAIL하는지 확인 → 원복). task#318이 그렇게 해서 **축 하나가 표본 0에서 공허하게 통과하던 것**을 찾았다(`.claude/skills/live-uat-probes` ⓨ).

- **배포**: `git push origin main` 시 자동 배포된다 — 자동 경로는 둘이다: self-hosted 러너(task#384에서 arm64로 복구, 아래 러너 항목)와 **launchd 폴러(task#382부터 실제로 배포한다, B84 해소)** — 둘 다 같은 배포 기록을 대조하므로 먼저 도착한 쪽이 배포하고 다른 쪽은 건너뛴다. 폴러는 push 후 ≤~2분(폴 주기) 안에 배포를 시작하므로 수동 `bash deploy.sh`는 **선택**이다(폴러 배포와 겹치면 잠금을 보고 exit 2로 거부될 뿐이다). 배포 판정은 폴러 로그 `~/Library/Logs/com.portfolion.auto-deploy-poll.log`의 `Deploy complete: <SHA>`·`배포된 커밋:` 줄과 `~/.portfolion-deployed-sha`로 한다. `docker compose build` / `docker compose up` 같은 *ad-hoc* 재빌드는 하지 말 것.

- **배포 메커니즘 주의 (검증된 사실, task#104·106 → task#382 갱신)**: 배포 경로는 **self-hosted GitHub Actions 러너**와 **폴러(`scripts/auto-deploy-poll.sh`)** 둘이다. task#382 전까지 폴러는 배포를 못 했다 — 잠금 자기충돌 · launchd PATH에 npm/docker 부재 · 「HEAD 뒤처짐」만 보는 트리거의 세 겹 때문이었다(B84). 지금 폴러의 트리거는 **배포 기록 SHA 대조**다: `deploy.sh`가 성공 끝에 배포한 SHA를 `~/.portfolion-deployed-sha`(`DEPLOY_MARKER`)에 쓰고, 폴러는 `origin/main`이 그것과 다르면 배포한다 — HEAD == origin이면 바로, **뒤처졌으면 `git merge --ff-only` 후** 배포, 앞섬·갈라짐이면 손대지 않는다(`reset --hard` 없음, task#377). 러너 잡(`.github/workflows/deploy.yml` → `scripts/runner-deploy.sh`, task#384)도 같은 기록을 대조한다 — 기록 == origin/main이면 「이미 배포됨」으로 끝나고, 배포 중이면 잠금이 풀릴 때까지(기본 15분) 기다린 뒤 기록을 **다시** 대조하며, 작업트리를 되돌리지 않는다. task#384 전의 러너 잡은 기록을 보지 않고 작업트리를 origin에 강제로 맞춘 뒤 무조건 배포했으므로 이 보장이 러너 쪽에서는 성립하지 않았다(러너가 offline이라 발현만 안 됐다). 수동 `bash deploy.sh`는 기록과 무관한 **강제 재배포**다(기록 skip은 러너 래퍼에만 있다). 잠금은 `deploy.sh`만 잡는다. **실패 1회 정책**: `deploy.sh`가 exit 2(사전 거부)면 다음 폴에서 재시도하고, 그 밖의 비0이면 그 SHA를 `~/.portfolion-deploy-failed-sha`에 쓰고 **같은 커밋을 다시 시도하지 않는다**(폴러 로그 `Deploy FAILED (exit N) — <sha> 재시도 안 함`) — 새 push나 수동 `deploy.sh` 성공으로 풀린다. task#377 이전의 폴러는 양방향으로 origin에 맞춰 되돌렸고, 그래서 push 안 한 로컬 커밋이 소실된 사례가 있었다(fg-map 지도 커밋 → cherry-pick+push 복구, task#106). 그 경로는 닫혔지만 **commit과 push를 묶는 습관은 유지**할 것 — 러너와 폴러는 둘 다 origin/main(=push된 것)만 배포한다. **백엔드가 옛 코드/이상 동작으로 보이면**: ① 도커 재기동 churn(컨테이너 uptime 제각각·일부 미기동)을 **먼저** 의심하고(`docker ps`로 uptime 확인 — backend는 `docker run`이라 `docker compose ps`엔 안 잡힘), ② 필요 시 정식 스크립트 **`bash deploy.sh` 1회**로 백엔드 컨테이너 재생성(working tree rebuild+stop/rm/run — 금지된 ad-hoc `docker compose`가 아님). 프론트는 nginx가 `frontend/dist` 직접 서빙이라 `npm run build`로 즉시 라이브(배포 무관). ⚠️ **그 비대칭이 만드는 창을 잊지 말 것 — 프론트는 즉시 라이브인데 백엔드는 러너/폴러 재배포 후라, 그 사이 "새 프론트 ↔ 옛 백엔드"가 실제로 돌아간다(task#267)**: 백엔드가 *새로 추가한* 응답 필드를 프론트가 읽으면 그 창에서 `undefined`로 렌더된다(구루 크롤 완료 문구가 `완료: undefined명`). **여기서 옛 필드로 폴백하면 고치려던 오값이 그대로 되살아난다** — `data.fresh ?? data.done`은 `done`이 시도 총계(=바로 그 버그)라 최악의 폴백이다. 정답은 **숫자를 빼는 것**(`fresh != null ? '완료: N명 갱신됨' : '완료: 갱신됨'`) — 틀린 값보다 없는 값이 낫다(`wrong < missing`). 관리자 수동 조작이라 창은 수 분이지만, 신규 백엔드 필드를 프론트가 소비하는 변경은 **그 창에서 무엇이 렌더되는지 한 줄 확인**할 것. ※ task#104에서 "in-checkout push는 절대 배포 안 됨"으로 단정했으나 그건 폴러 로그만 보고 러너를 놓친 과잉결론. **task#105에서 "미확정"이 규명됨 — 러너는 *dead*였다**(아래 러너 격리 항목): in-checkout 푸시는 러너에만 의존하는데 PortfoliOn 러너가 lab-taebro로 재등록돼 사라져 06-22~06-27 무음 미배포. **백엔드가 옛 코드면 폴러 footgun 단정 전에 러너부터 확인**: `gh run list`(잡이 `queued`/`cancelled(24h)`면 러너 부재)·`gh api repos/calmonion7/PortfoliOn/actions/runners --jq '.runners[]|{name,status}'`(online 러너 존재?).

- **⭐ 셸 스크립트에 `set -o pipefail`을 걸면 *조기종료 파이프라인*을 전수 세라 — `cmd | head -c N`·`cmd | grep -q`가 스크립트를 **에러 메시지 하나 없이** 죽인다(task#334)**: 바로 위 task#300 가토가 「0바이트 로그가 죽음과 정상 진행을 동시에 뜻한다」였다면 이건 그 **셸 판**이다 — 이번엔 **아무 출력도 없음**이 「성공」과 「즉사」를 동시에 뜻했다. 메커니즘: 파이프의 **우변이 먼저 끝나면**(`head`는 N바이트에서, `grep -q`는 첫 매치에서) 좌변이 **SIGPIPE(141)**를 받고, `set -o pipefail`이 그 141을 파이프라인 종료코드로 올리고, `set -e`가 조용히 종료시킨다. 실측(task#334 `scripts/rotate-postgres-password.sh`): `NEWPW=$(tr -dc 'A-Za-z0-9' < /dev/urandom | head -c 32)`에서 **exit=141**, 다음 줄 미도달. 그 줄이 백업 생성 *이전*이라 **실행 흔적조차 남지 않아**, 사용자에게는 "실행했는데 아무 일도 안 일어났다"로만 보였다(내가 원인을 찾기 전까지 회전이 실패한 줄도 몰랐다). **⚠️ 하나만 고치면 안 된다 — 같은 클래스가 4곳이었고 셋은 성격이 달랐다**: ⓐ 비밀번호 생성 — **확정적** 종료 ⓑ `docker ps | grep -qx "$NAME"` 2곳 — 좌변이 SIGPIPE를 받으면 **멀쩡한데 die** 한다(출력이 작아 보통은 통과하는 **flaky**) ⓒ `docker logs | grep -qi 'error'` — **검사가 뒤집힌다.** 실패가 *발견되면* grep이 먼저 끝나 파이프라인이 141을 반환하고 `if`가 거짓이 되어 **진짜 실패일수록 통과한다**(대조군 실측: 소량 로그는 정상 감지, 출력이 파이프 버퍼를 넘으면 exit=141로 미감지 — 즉 크기 의존 잠재 결함이지 확정적 역전은 아니다). **처방 2가지**: ⓐ 출력을 **변수로 받아 here-string으로 검사**할 것(`OUT=$(cmd); grep -q p <<< "$OUT"` — here-string은 파이프라인이 아니라 SIGPIPE가 없다), 생성은 파이프 없는 형태로(`python3 -c` `secrets` 등) ⓑ **`ERR` 트랩을 기본으로 달 것** — `trap 'ec=$?; echo "❌ 예기치 못한 종료: line $LINENO, exit $ec" >&2' ERR`(`die`류 명시적 `exit`와 이중으로 울리지 않음을 확인했다). 이 사건의 본질은 「죽었다」가 아니라 **「죽었는데 아무도 모른다」**였다. 이 저장소는 `deploy.sh`·`scripts/auto-deploy-poll.sh`·`smoke.sh` 등 bash가 배포 경로에 있으므로 표면이 넓다. **⭐⭐ 같은 표면의 두 번째 조용한 즉사 — `\` 연속행 *안*에 주석을 넣으면 `#`이 나머지 인자를 통째로 삼키고, `bash -n`은 통과한다(task#339)**: 위가 「파이프라인이 스크립트를 죽인다」였다면 이건 **「명령이 인자를 잃은 채 성공한다」**다. 백슬래시 연속은 주석 해석보다 **먼저** 줄을 잇기 때문에, `docker run \` 다음 줄에 `# 설명` 을 끼우면 그 뒤 인자가 전부 주석이 된다. 실측(`deploy.sh`의 nginx `docker run`) — nginx가 `-p`도 볼륨 마운트도 `--restart`도 없이 뜨고, `-p 127.0.0.1:80:80`은 **독립 명령으로** 실행돼 not-found(exit 127)가 된다. 즉 **사이트가 내려간다.** ⚠️ **`bash -n`은 이것을 못 잡는다** — 구문은 완전히 유효하기 때문이다. 그래서 「문법 확인했다」가 알리바이가 되지 않는다. **실천 3가지**: ⓐ 주석은 연속행 블록 **위**에 둘 것(블록 안에 설명이 꼭 필요하면 그 줄을 연속에서 빼라) ⓑ 검증은 구문 검사가 아니라 **대상 명령을 echo 스텁으로 치환해 인자 수를 세는 것**이다(`docker(){ echo "$#"; }` 후 그 절을 실행 — task#339는 인자 15개가 온전함을 그렇게 실증했다) ⓒ 이 결함은 **배포된 뒤 회귀 가드가 잡는다** — 잡히긴 하지만 그때는 이미 라이브가 내려간 뒤이므로, 배포 경로의 셸을 편집했으면 푸시 **전에** ⓑ를 돌릴 것. 부수 — 같은 태스크에서 **내가 주석에 적은 리터럴이 내 감사 패턴에 걸려 거짓 FAIL**을 냈고(`grep -oE '\-p [0-9.:]+'`가 코드 1건 + 주석 1건 = 2건), 그 이빨 검사는 **`grep -c`가 *줄*을 세는 바람에**(두 플래그가 한 줄) 빈 값을 내 「이빨 없음」으로 오판할 뻔했다: **감사 대상 파일의 주석에 감사 패턴과 같은 리터럴을 적지 말고, `grep -c`(줄)와 `grep -o | wc -l`(히트)를 구별할 것.**

- **⭐⭐ 그 「계측 실패를 판정으로 오독」 가족의 네 번째 표면 — 불완전한 *응답*은 **상대의 로그를** 거짓말하게 한다(task#346)**: 앞의 셋(#300 0바이트 로그 · #334 SIGPIPE 침묵 · #334 면제된 인증 경로)이 전부 **내가 읽는 계측**이 틀리는 경우였다면, 이건 **내가 보내는 응답이 상대의 기록을 오염**시키는 경우다. 실측 — `scripts/cowork-fire-listener.py`의 거부 경로가 `send_response(401); end_headers()`뿐이라 **`Content-Length`가 없었다**. 그러면 클라이언트가 바디를 읽을 때 서버가 이미 연결을 닫아 `ConnectionResetError`가 나고, 호출측 로그에는 **「401」이 아니라 「연결 끊김」**이 남는다. 즉 **인증 거부를 받았다는 사실 자체가 상대편 기록에서 증발한다** — 진단이 목적인 로그에서 가장 나쁜 형태다. 재현은 **6회 중 2회**로 간헐이었고(응답이 작아 대개는 버퍼에 들어간다) 그래서 더 은밀하다. 처방: 바디 없는 거부에도 `send_header("Content-Length", "0")`을 붙이고, 그것을 **결정적 축으로** 못박을 것(헤더 존재 단언 — 주입 시 3/3 실패로 이빨 확인). **부수 교훈이 본체만큼 중요하다 — 간헐 실패를 「테스트가 불안정하다」로 읽으면 진짜 결함을 삼킨다.** 그 자리에서 자연스러운 손길은 `try: e.read() except: pass`였고, 그랬으면 테스트는 초록이 되고 결함만 남았을 것이다(task#319~321의 「FAIL을 보면 축을 의심하기 전에 등가로 좁혀라」의 **flake판** — flake도 FAIL이다). 이 저장소에서 같은 패턴을 찾으려면 `grep -n "send_response(.*); *self.end_headers()"` 처럼 **바디 없는 응답**을 훑을 것.
