# 배포·운영 런북

루트 `CLAUDE.md`에서 **원문 그대로** 옮겨 온 항목들이다(doctor 정리, 2026-10-10). 본문의 「위·아래 항목」·「이 문서의 ~ 항목」은 원래 루트 파일의 순서·위치를 가리키므로, 찾는 항목이 여기 없으면 루트·`backend/`·`frontend/`의 CLAUDE.md와 `.claude/skills/verification-gates`·`.claude/skills/deploy-ops`를 볼 것. 배포의 **금지 규칙 요약은 루트 `CLAUDE.md` Deployment 절에 남아 있다** — 여기는 그 근거와 증상별 진단이다.

- **프론트 서빙**: nginx가 프론트 `dist`를 **이미지에 구워** 서빙한다(`nginx/Dockerfile` 멀티스테이지 — `node:24-alpine`에서 `npm ci && npm run build` → `nginx:alpine`, task#386). 그래서 로컬 `cd frontend && npm run build`는 **라이브에 닿지 않고**, 프론트와 백엔드는 **같은 배포로 함께** 라이브가 된다(push → 러너 빌드 → 기동, 수 분). 「로컬 빌드가 즉시 라이브」·「프론트 먼저/백엔드 나중의 비대칭」은 옛 경로(nginx가 작업트리 `frontend/dist`를 `:ro` 마운트하던 시절, task#386에서 은퇴)의 사실이다. 그 시절의 교훈 중 지금도 유효한 것: ⓐ **라이브 red-first가 필요하면 푸시 *전에* 돌릴 것** — 푸시 뒤엔 새 번들이 서빙돼 옛 번들을 잴 창이 없다(task#290). ⓑ **라이브를 재는 에이전트가 도는 동안 푸시는 배포성 행위**다. ⓒ **푸시 *전에* 돌려도 red가 원리적으로 안 나오는 경우가 있다(task#318 실측)** — 프로브의 기대값이 그 변경으로 신설되는 백엔드 필드에서 파생되면, 푸시 전에는 백엔드도 옛 코드라 그 필드가 없어 기대값이 0으로 degenerate해 **관측 0과 일치하며 통과한다**(task#318: 신규 9축이 전부 「표본 0 — 미검증」으로 PASS). 「백엔드 새 + 프론트 옛」 창은 이 저장소에서 자연 발생하지 않는다(지금은 둘이 같은 배포로 나간다). 실천: 프론트·백엔드를 함께 건드리는 변경의 라이브 판별력은 red-first에 기대지 말고 **배포 후 fault injection**으로 얻을 것(대상 셀렉터·기대값을 의도적으로 깨뜨려 축이 실제로 FAIL하는지 확인 → 원복). task#318이 그렇게 해서 **축 하나가 표본 0에서 공허하게 통과하던 것**을 찾았다(`.claude/skills/live-uat-probes` ⓨ).

- **배포(표준 배포, task#386 — ADR `261011-074335`)**: `git push origin main` → self-hosted 러너가 `.github/workflows/deploy.yml`(taebro-infra 계약 v5 4절 그대로 — `paths-ignore: ['.forge/**', '**/*.md']`, `concurrency`, `runs-on: [self-hosted, ARM64]`, PR 트리거 금지) → **`~/runtime/taebro-infra/bin/deploy portfolion prod`**. `bin/deploy`(infra 소유, 정본 `~/runtime/taebro-infra/docs/CONTRACT.md`)의 흐름: 사전 검사(포트표·잠금·실행 자리 `.env`·`deploy/taebro.env`·모든 서비스 `mem_limit`) → 러너 체크아웃에서 빌드(이미지 `portfolion-backend`·`portfolion-nginx`) → **실제로 돌던 컨테이너의 이미지**를 `:prev`로 태그 → `docker-compose.yml`만 실행 자리 `~/runtime/portfolion/prod/`로 복사 → 거기서 `up -d --no-build --force-recreate` → 헬스(`deploy/taebro.env`: `HEALTH_PATH=/health`, 본문에 `HEALTH_EXPECT=portfolion`, `HEALTH_TIMEOUT=600` — 아래 기동 배치 항목 때문에 600) → 세대 기록 → 실패하면 `:prev`로 자동 롤백. **종료코드**: 0 성공 · 1 실패·롤백 성공(서비스 유지) · 2 실패·롤백 실패 또는 `:prev` 없음(첫 배포 — 다운 가능, 사람 필요) · 3 시작 전 거부(아무것도 안 바꿈 — 잠금·실행 자리/`.env` 없음·`mem_limit` 누락 등). **같은 커밋 자동 재시도는 없다.** **배포 판정**: `gh run list --workflow deploy.yml --branch main --json conclusion,headSha`에서 **`headSha`로** success를 찾을 것(브랜치명만 보면 같은 파일 이름의 옛 「Deploy to Production」 run이 섞여 착수 전부터 통과한다) + run 로그 `완료 — portfolion 세대 <세대>` + `~/runtime/portfolion/prod/.taebro-deploy`의 `generation=<YYMMDD-HHMMSS>-<커밋7자>`. **수동 재배포** = `gh workflow run deploy.yml --ref main`(같은 커밋도 다시 빌드·재생성 — env 파일 변경 반영에 쓴다). **늦은 롤백** = `~/runtime/taebro-infra/bin/deploy --rollback portfolion prod <세대>`(현재 세대가 그 값일 때만). `docker compose build`/`up`을 손으로 하지 말 것 — 실행 자리 밖에서 띄우면 `.env`·라벨이 어긋난다. 잠금은 실행 자리의 `.taebro-deploy.lock`(mkdir 원자 잠금, infra 소유 — 죽은 배포가 남기면 사람이 `rmdir`).

- **표준 배포의 구조적 결정 3가지(ADR `261011-074335`)**: ⓐ **prod postgres는 배포 compose 밖이다** — `bin/deploy`는 매 배포 `up --force-recreate`라 넣으면 배포마다 유일한 prod DB 컨테이너가 재생성된다. `portfolion-postgres-1`(볼륨 `portfolion_pgdata`)은 compose orphan으로 남고(`bin/deploy`에 `--remove-orphans`가 없어 안전, 매 배포 「Found orphan containers」 경고는 정상), backend는 같은 기본 네트워크 `portfolion_default`의 별칭 `postgres:5432`로 붙는다. 수동 재생성 정의는 `deploy/legacy-postgres.compose.yml`(`-p portfolion --env-file .env` 필수 — 그 파일 헤더 참조; 서비스 정의가 옛 것과 같아 config-hash가 돌던 컨테이너와 일치함을 task#386에서 확인). ⑥-2(공용 `taebro-postgres` 이전)에서 없어진다. ⓑ **prod 비밀 정본은 `~/runtime/portfolion/prod/.env`(600)이고 `backend/.env.docker`는 그것을 가리키는 심링크**다 — 보조 스크립트(`cowork-fire-listener.py` 등)가 `backend/.env.docker`를 직접 읽으므로 두 벌로 두면 회전 때 한쪽만 바뀐다. 쓰기는 `cp`·`open(p,'w')`처럼 심링크를 따라가는 방식만(`mv`·원자적 교체는 심링크를 일반 파일로 바꾼다). ⓒ **dev 스택은 외부 키가 없고 `SCHEDULER_ENABLED=false`**다(task#387) — dev DB가 prod 복사본이라 키가 있으면 키움·KIS 토큰 재발급(prod 토큰 무효화)·루틴 발사가 dev에서 일어난다. dev backend만 공용 postgres 네트워크 `taebro-db`에 붙는데, 방법은 dev 실행 자리 `.env`의 `COMPOSE_FILE=docker-compose.yml:deploy/dev-db.compose.yml`이다 — 덧붙임 파일은 `RUNTIME_FILES`로 prod 실행 자리에도 복사되지만 prod `.env`에 `COMPOSE_FILE`이 없어 읽히지 않는다. 그래서 ⑥-2 전까지 **prod `.env`에 `COMPOSE_FILE`을 넣거나 기본 `docker-compose.yml`에 `taebro-db`를 넣지 말 것** — `taebro-db`에서 `taebro-postgres-1`이 별칭 `postgres`를 가져 prod `DATABASE_URL`의 호스트가 공용 DB로 풀릴 수 있다(에러 없이). `backend/tests/test_compose_dev_network.py`가 기본 compose 쪽을 지킨다. **백엔드가 옛 코드/이상 동작으로 보이면**: ① 도커 재기동 churn(`docker ps` uptime — backend·nginx는 이제 compose 소유라 `docker compose -p portfolion ps`에도 잡힌다) ② 러너·Deploy run(아래 러너 항목) ③ 필요하면 `gh workflow run deploy.yml --ref main` 1회. 옛 경로(task#386 은퇴 — 러너+launchd 폴러가 배포 기록 `~/.portfolion-deployed-sha`를 대조하고 `deploy.sh`가 `docker run`으로 띄우던 시절)의 교훈 중 남는 것: 「배포가 안 됐다」를 폴러/스크립트 footgun으로 단정하기 전에 **러너부터** 볼 것(task#105 — 러너가 타 레포로 재등록돼 무음 미배포), 그리고 신규 백엔드 필드를 프론트가 소비할 때 **틀린 값보다 없는 값**(`wrong < missing` — task#267, `data.fresh ?? data.done` 같은 옛 필드 폴백은 고치려던 오값을 되살린다).

- **⚠️ 라이브가 502인데 `docker ps` 전부 `Up`·백엔드 포트도 열려 있으면 Docker의 `127.0.0.1:80` 포워딩 stuck을 먼저 의심 — 재배포는 못 고치고 nginx 컨테이너 stop/start가 고친다(task#354 실측 2026-09-16 — 당시는 옛 경로 `deploy.sh`, task#386 은퇴)**: 배포 재기동(17:47) 뒤 `curl http://127.0.0.1/ → 000`(`Recv failure: Connection reset by peer`), cloudflared err 로그도 `read: connection reset by peer`. 컨테이너 **안**에서는 nginx가 정상(내부 wget → 401)이고 `docker logs`에 요청이 한 건도 없다 — 즉 트래픽이 컨테이너에 닿지 못한다. 다른 프로젝트의 `0.0.0.0:8090`과 **새로 띄운** `127.0.0.1:8099` 테스트 컨테이너는 정상이므로 포트 80의 기존 포워드 엔트리만 stuck이다. **push로 재배포(옛 경로 `deploy.sh`의 nginx `docker rm`+`run`)를 다시 돌려도 회복되지 않았고**, `docker stop portfolion-nginx-1`(호스트 `lsof -iTCP:80` 리스너 소멸 확인) → `docker start`로 즉시 회복됐다. 09-15 12:50 배포 뒤에도 같은 증상이 2분간 있다가 자연 회복한 기록이 있어 배포 직후엔 잠깐 기다려 볼 만하지만, 10분 넘게 지속되면 위 stop/start 1회. ⚠️ **단 stop 직후 바로 start하면 회복되지 않을 수 있다(task#381 실측 2026-10-08)** — `docker stop` → `lsof -iTCP:80 -sTCP:LISTEN`으로 리스너 소멸 확인 → **~10초 대기** → `docker start`에서야 회복됐다(즉시 재시작 1회는 local 000이 그대로였다). 대조군으로 새 `127.0.0.1:8099` 컨테이너가 정상인지 보면 「포트 80 엔트리만 stuck」이 확정된다. 표준 배포에서도 첫 배포·`--force-recreate` 직후 같은 증상이 나면 이 회복을 쓴다(task#386 `scripts/cutover/02-prod-cutover.sh`가 그 절차를 담는다). 진단 순서: `curl 127.0.0.1:80`(000이면 이 항목) → 러너·Deploy run(위 항목) → 아래 기동 배치 항목.

- **옛 경로 `deploy.sh`의 사후 기록(task#372·#377·#382 — task#386에서 은퇴)**: 손으로 돌린 `deploy.sh`가 exit 0·`/health` ok로 끝났는데 실제로는 직전 커밋 트리를 빌드한 사건(task#372 — 폴러가 push 전 origin으로 되돌린 탓)이 「exit 0·health ok는 *무엇이* 배포됐는지를 말하지 않는다」를 남겼다. 표준 배포에서 그 역할은 **세대 기록(`.taebro-deploy`의 커밋 7자)과 Deploy run의 `headSha`**가 한다 — 판정은 언제나 *무엇이* 배포됐는지를 담은 값으로 할 것. 옛 가드(미커밋 거부·ff·종료코드 2/1·`scripts/test_deploy_guard.py`)와 배포 기록 파일은 대상과 함께 은퇴했다(ADR `261009-105247` superseded).

- **⚠️ 배포 직후 백엔드가 `Up`이고 로그도 활발한데 API가 수 분간 무응답일 수 있다 — 기동 배치가 끝나야 포트가 서비스된다(실측, task#250)**: 위 "배포 메커니즘 주의"가 *배포가 안 된* 경우라면 이건 *배포는 됐는데 아직 못 받는* 경우다. 실측 타임라인 — 컨테이너 시작 `22:00:24` → lifespan 완료 `22:00:25`(**0.6초**; `main.py:241` lifespan = `_migrate()` + `sched.start()` + 데몬 스레드) → 그런데 포트 8000은 계속 `Connection refused`였고 기동 배치의 **마지막 로그 `22:05:41` 직후**에야 열렸다(분당 로그 49·19·22·20·20 → **4** → 2, 첫 요청 처리 `22:06:06`). 즉 **총 ~5분 15초**. 그동안 `docker ps`는 `Up`, `docker logs`는 활발해서 **완전히 건강해 보인다** — 여기서 "배포 깨졌다"로 오진해 재배포 같은 불필요한 조치를 하기 쉽다(표준 배포가 `HEALTH_TIMEOUT=600`을 두는 이유 — 기본 120초면 정상 기동을 실패로 보고 롤백한다). **배포 후 라이브 스모크는 포트 바인딩을 폴링한 뒤 실행할 것**: `docker exec <c> python -c "import socket;print(socket.socket().connect_ex(('127.0.0.1',8000)))"` 가 `0`이 될 때까지 대기(111=refused). 증폭 조건: **배포가 배치 예정 시각과 겹치면** 배치가 기동 즉시 뜬다(`daily_report_us` 07:00 KST · `daily_report_kr` 20:30 KST — task#250 배포가 정확히 07:00 KST에 떨어져 관측됐다) → 그 시간대 배포는 라이브 API가 5분+ 다운된다고 예상할 것(현재는 기록만, 조치 없음). ⚠️ **주의 — 이 항목은 원인을 두 번 고쳐 썼다**: 처음엔 "uvicorn이 lifespan을 끝낸 뒤에야 바인딩하므로 기동 배치가 그 시간을 먹는다"로 적었는데 **틀렸다**(lifespan 0.6초, 배치는 스케줄러 스레드라 비블로킹). 정확한 메커니즘(GIL/이벤트 루프 기아)은 **미확정**이며 그렇게 남긴다 — task#246의 "원인을 추정으로 귀속하지 말고 계측으로 확정하라"가 회고 기술 자체에도 적용된 사례다.

- **⭐ 셸 스크립트에 `set -o pipefail`을 걸면 *조기종료 파이프라인*을 전수 세라 — `cmd | head -c N`·`cmd | grep -q`가 스크립트를 **에러 메시지 하나 없이** 죽인다(task#334)**: 바로 위 task#300 가토가 「0바이트 로그가 죽음과 정상 진행을 동시에 뜻한다」였다면 이건 그 **셸 판**이다 — 이번엔 **아무 출력도 없음**이 「성공」과 「즉사」를 동시에 뜻했다. 메커니즘: 파이프의 **우변이 먼저 끝나면**(`head`는 N바이트에서, `grep -q`는 첫 매치에서) 좌변이 **SIGPIPE(141)**를 받고, `set -o pipefail`이 그 141을 파이프라인 종료코드로 올리고, `set -e`가 조용히 종료시킨다. 실측(task#334 `scripts/rotate-postgres-password.sh`): `NEWPW=$(tr -dc 'A-Za-z0-9' < /dev/urandom | head -c 32)`에서 **exit=141**, 다음 줄 미도달. 그 줄이 백업 생성 *이전*이라 **실행 흔적조차 남지 않아**, 사용자에게는 "실행했는데 아무 일도 안 일어났다"로만 보였다(내가 원인을 찾기 전까지 회전이 실패한 줄도 몰랐다). **⚠️ 하나만 고치면 안 된다 — 같은 클래스가 4곳이었고 셋은 성격이 달랐다**: ⓐ 비밀번호 생성 — **확정적** 종료 ⓑ `docker ps | grep -qx "$NAME"` 2곳 — 좌변이 SIGPIPE를 받으면 **멀쩡한데 die** 한다(출력이 작아 보통은 통과하는 **flaky**) ⓒ `docker logs | grep -qi 'error'` — **검사가 뒤집힌다.** 실패가 *발견되면* grep이 먼저 끝나 파이프라인이 141을 반환하고 `if`가 거짓이 되어 **진짜 실패일수록 통과한다**(대조군 실측: 소량 로그는 정상 감지, 출력이 파이프 버퍼를 넘으면 exit=141로 미감지 — 즉 크기 의존 잠재 결함이지 확정적 역전은 아니다). **처방 2가지**: ⓐ 출력을 **변수로 받아 here-string으로 검사**할 것(`OUT=$(cmd); grep -q p <<< "$OUT"` — here-string은 파이프라인이 아니라 SIGPIPE가 없다), 생성은 파이프 없는 형태로(`python3 -c` `secrets` 등) ⓑ **`ERR` 트랩을 기본으로 달 것** — `trap 'ec=$?; echo "❌ 예기치 못한 종료: line $LINENO, exit $ec" >&2' ERR`(`die`류 명시적 `exit`와 이중으로 울리지 않음을 확인했다). 이 사건의 본질은 「죽었다」가 아니라 **「죽었는데 아무도 모른다」**였다. 이 저장소는 운영 bash(`scripts/rotate-postgres-password.sh`·`scripts/cutover/*.sh` 등 — 옛 경로의 배포 셸은 task#386에서 은퇴)가 있으므로 표면이 남아 있다. **⭐⭐ 같은 표면의 두 번째 조용한 즉사 — `\` 연속행 *안*에 주석을 넣으면 `#`이 나머지 인자를 통째로 삼키고, `bash -n`은 통과한다(task#339)**: 위가 「파이프라인이 스크립트를 죽인다」였다면 이건 **「명령이 인자를 잃은 채 성공한다」**다. 백슬래시 연속은 주석 해석보다 **먼저** 줄을 잇기 때문에, `docker run \` 다음 줄에 `# 설명` 을 끼우면 그 뒤 인자가 전부 주석이 된다. 실측(옛 경로 `deploy.sh`의 nginx `docker run`, task#386 은퇴) — nginx가 `-p`도 볼륨 마운트도 `--restart`도 없이 뜨고, `-p 127.0.0.1:80:80`은 **독립 명령으로** 실행돼 not-found(exit 127)가 된다. 즉 **사이트가 내려간다.** ⚠️ **`bash -n`은 이것을 못 잡는다** — 구문은 완전히 유효하기 때문이다. 그래서 「문법 확인했다」가 알리바이가 되지 않는다. **실천 3가지**: ⓐ 주석은 연속행 블록 **위**에 둘 것(블록 안에 설명이 꼭 필요하면 그 줄을 연속에서 빼라) ⓑ 검증은 구문 검사가 아니라 **대상 명령을 echo 스텁으로 치환해 인자 수를 세는 것**이다(`docker(){ echo "$#"; }` 후 그 절을 실행 — task#339는 인자 15개가 온전함을 그렇게 실증했다) ⓒ 이 결함은 **배포된 뒤 회귀 가드가 잡는다** — 잡히긴 하지만 그때는 이미 라이브가 내려간 뒤이므로, 배포 경로의 셸을 편집했으면 푸시 **전에** ⓑ를 돌릴 것. 부수 — 같은 태스크에서 **내가 주석에 적은 리터럴이 내 감사 패턴에 걸려 거짓 FAIL**을 냈고(`grep -oE '\-p [0-9.:]+'`가 코드 1건 + 주석 1건 = 2건), 그 이빨 검사는 **`grep -c`가 *줄*을 세는 바람에**(두 플래그가 한 줄) 빈 값을 내 「이빨 없음」으로 오판할 뻔했다: **감사 대상 파일의 주석에 감사 패턴과 같은 리터럴을 적지 말고, `grep -c`(줄)와 `grep -o | wc -l`(히트)를 구별할 것.**

- **⭐⭐ 그 「계측 실패를 판정으로 오독」 가족의 네 번째 표면 — 불완전한 *응답*은 **상대의 로그를** 거짓말하게 한다(task#346)**: 앞의 셋(#300 0바이트 로그 · #334 SIGPIPE 침묵 · #334 면제된 인증 경로)이 전부 **내가 읽는 계측**이 틀리는 경우였다면, 이건 **내가 보내는 응답이 상대의 기록을 오염**시키는 경우다. 실측 — `scripts/cowork-fire-listener.py`의 거부 경로가 `send_response(401); end_headers()`뿐이라 **`Content-Length`가 없었다**. 그러면 클라이언트가 바디를 읽을 때 서버가 이미 연결을 닫아 `ConnectionResetError`가 나고, 호출측 로그에는 **「401」이 아니라 「연결 끊김」**이 남는다. 즉 **인증 거부를 받았다는 사실 자체가 상대편 기록에서 증발한다** — 진단이 목적인 로그에서 가장 나쁜 형태다. 재현은 **6회 중 2회**로 간헐이었고(응답이 작아 대개는 버퍼에 들어간다) 그래서 더 은밀하다. 처방: 바디 없는 거부에도 `send_header("Content-Length", "0")`을 붙이고, 그것을 **결정적 축으로** 못박을 것(헤더 존재 단언 — 주입 시 3/3 실패로 이빨 확인). **부수 교훈이 본체만큼 중요하다 — 간헐 실패를 「테스트가 불안정하다」로 읽으면 진짜 결함을 삼킨다.** 그 자리에서 자연스러운 손길은 `try: e.read() except: pass`였고, 그랬으면 테스트는 초록이 되고 결함만 남았을 것이다(task#319~321의 「FAIL을 보면 축을 의심하기 전에 등가로 좁혀라」의 **flake판** — flake도 FAIL이다). 이 저장소에서 같은 패턴을 찾으려면 `grep -n "send_response(.*); *self.end_headers()"` 처럼 **바디 없는 응답**을 훑을 것.
